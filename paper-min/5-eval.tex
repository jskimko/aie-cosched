\label{subsec:setup}

% VALUE: the platform and its software, the designs we rewrite, the five LLMs in three classes, the prompt lengths and decode contexts, and the configurations

% SOURCE: mlir-air a3e26261 (llms/shared/fused_prefill, fused_decode; the runs use npu-gap's 44e8d8f7); mlir_aie wheel 1.4.5.dev22+g35fa6b1; weights FastFlowLM/Qwen3-4B-NPU2 rev 07651f11cac7, the Llama-3.2-1B q4nx bundle, FastFlowLM/Llama-3.1-8B-NPU2 rev 52700648, all sha256-verified (lab-prefill-overlap (23), lab-split-sweep (10)).
We measure on an AMD Ryzen\texttrademark{} AI Max+ 395 with 64\,GB of memory that the NPU shares with the host, running Linux~7.0, the amdxdna driver with XRT~2.25.0~\citep{xdna-driver,xrt-repo}, and NPU firmware 1.1.2.65 in its performance mode.
We rewrite AIR's fused prefill and fused decode~\citep{wang2026mlirair}, compiled by MLIR-AIE~\citep{mlir-aie-repo}, for five LLMs with 4-bit weights in three classes: the dense Llama-3.2-1B~\citep{meta2024llama32}, Qwen3-4B~\citep{qwen2025qwen3}, and Llama-3.1-8B~\citep{meta2024llama31}, the sliding-window Gemma3-4B~\citep{farabet2025gemma3}, and the convolutional LFM2-1.2B~\citep{liquidai2025lfm2}.
Prompts run from 128 to 32{,}768 tokens in powers of two, plus 129, 2{,}049, and 16{,}385 tokens, and decode contexts from 2{,}048 to 30{,}208 cached tokens, or 28{,}800 on Qwen3-4B.

The final sweep measures the original at every supported split (ruling 2026-10-25).
% SOURCE: pre-final; the measured set is the current numbers' rule, and the final sweep replaces it with every supported configuration (core definitions, headline baseline; step 2, section 5 item 3).
% DECISION: FastFlowLM, taken as released, is never a speedup reference; its current release appears once as an absolute comparison, marked as a snapshot.
Each prefill result is relative to the original program on whichever supported configuration, $S_1$, $S_2$, or $S_4$, minimizes its TTFT at that prompt length, among the default and every configuration that the event model predicts within 5\% of the minimum.
This baseline runs on the faster of its own host code and OPCORD's runtime, so only the order and the configuration separate the two.
In decode the baseline is the unmodified design, and results that isolate the order compare the composed and original orders on one configuration.

% VALUE: correctness gate, metrics, the cell, statistics, and pairing across batches; defaults stated once
% SOURCE: protocol (amd-npu ab/FINAL-SWEEP.md: spinner, shared engine, gates; kept iterations max(5, the full spec); decode 5 ABBA repetitions of 256 tokens); 8x2 cap 49.9-55.7 GB/s over the batches (lab-prefill-device (1), lab-split-sweep (4)-(5)).
Every run's logits and KV records are bit-identical to the original program's.

Because the loop pass lets each block's transfer overlap the previous block's compute, the decode gain grows with the context, as attention's share of each token does (Figure~\ref{fig:decode}).
At 30{,}208 tokens, or 28{,}800 on Qwen3-4B, the loop pass lowers the time per token by \DecodeGainLo--\DecodeGainHi$\times$ across the five LLMs.

Renaming only the keys and values, as FLM's authors do by hand for Gemma3~\citep{du2026gemma3}, gains at most 0.3\%, because the shared score buffer still closes the loop's critical cycle, as the bound of Section~\ref{subsec:removal} predicts.

At two chunks, by the event model's split of its prediction into terms, every composed dispatch starts only once the host has finished, which exposes the post-processing that the original order hides behind device work.
The configuration that minimizes TTFT moves with the length too, and on Llama-3.2-1B and Qwen3-4B OPCORD picks $S_1$ at 1{,}024 tokens, $S_2$ at 2{,}048 to 4{,}096, and $S_4$ from 8{,}192.
Both the order and the configuration that pay thus change with the prompt, which is why OPCORD prices them together for each prompt length.
