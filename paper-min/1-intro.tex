\section{Introduction}
\label{sec:intro}

% VALUE: the setting and the problem: the NPU runs an LLM's operators as dataflows on column groups of one spatial array; fused designs avoid reconfiguration, but one in-order CP issues every group's work in the compiled order, so in AIR's fused prefill the groups take turns on independent work; the occupancy a developer can compute still reads 92-97% busy, and the same operators on the same columns reach the first token 1.76x sooner when reissued (Figure 1)
% DECISION: the symptom is "the occupancy a developer can compute reads 92-97% busy", never "invisible to every metric".
On AMD Ryzen\texttrademark{} AI processors, a neural processing unit (NPU), the kind of accelerator that Copilot+ PCs require~\citep{copilotplus-reqs}, serves large language models (LLMs) from a spatial array of AI Engine tiles, where each operator becomes a dataflow on its own group of columns.
Compilers such as MLIR-AIR (AIR)~\citep{wang2026mlirair} and IRON~\citep{hunhoff2025iron} decide what each operator computes and where it runs.
A \emph{fused} design holds several operators in one configuration, so operators on disjoint columns can run at once without reconfiguring the array.
All of its work, however, reaches the array through one in-order command processor (CP), in the order compiled into the design.
In AIR's fused prefill, which runs each layer over 128-token chunks, that order issues one operator per dispatch, stage by stage, so attention and the matrix multiplications (GEMMs) take turns on their columns, although attention on one chunk does not feed later chunks' GEMMs (Figure~\ref{fig:timeline}).

% VALUE: the usual remedies recover none of it: packing dispatches (cited as standard practice) and a second hardware context (shares the array in time); GPUs removed the wait with hardware queues (Related Work), this NPU has one in-order CP per context, so the order must be rewritten in the stream
% DECISION: packing dispatches (batching) is cited as standard practice, never presented as ours. The GPU clause points to Related Work, because only Related Work states that hardware queues removed the wait.
Packing dispatches, as CUDA Graphs~\citep{nvidia-cudagraphs} and XRT's run lists~\citep{xrt-repo} do, amortizes launch cost but recovers none of the lost overlap, and neither does a second hardware context, which shares the whole array in time~\citep{xdna-driver} (Section~\ref{subsec:semantics}).
Unlike GPUs, whose hardware queues removed this kind of wait (Section~\ref{sec:related}), this NPU has one in-order CP per hardware context, so the order must be rewritten in the stream itself.

% VALUE: the insight (core rule); the waits as the two kinds of false dependence (defined once in Background), which save time only on the critical path (cited); the condition that refines that rule on this NPU, with the carve-out, read from the artifacts before any duration; so the partition decides where gains can arise and the prompt length what they are worth
% DECISION: the kinds are used here with a pointer to Background (defined once in Background, whose DECISION records the sources: Kuck for the anti and output classes, Tomasulo for renaming, NVIDIA's Kepler whitepaper for the order kind); the paper claims the condition on this platform and its dependence on the partition and the prompt length, never that false dependences cost time.
The insight of this work is that, on a spatial NPU whose work one in-order command processor issues, that processor's instruction order is the array's schedule, fixed in the compiled artifact.
So the waits that leave the array idle can be read, bounded, and removed from the artifact itself, after compilation.
These waits are false dependences (Section~\ref{sec:background}), order dependences in AIR's prefill and name dependences in its decode.
Removing one can save time only on the critical path~\citep{kelley1961critical}, and on this NPU it frees overlap, beyond what buffers on a shared route let through, only where the freed and the awaited work use disjoint resources and where no true dependence separates them, on the device or through a host step.
This condition's two clauses are read from the artifacts and the host's accesses before any duration is measured, so how a design partitions its work decides where gains can arise and the prompt length what they are worth.

% VALUE: the system built from the insight, in the core rule's order: read the artifact (dependence graph over every agent, closed binaries included, a bound per false dependence); rewrite order and buffers behind checkers; price order and configuration per prompt length with an event model, because both change with the prompt; the general benefit to any developer of this hardware, with its reason
% DECISION: FastFlowLM is described by what it ships, as its current release; no claim about how its order was chosen.
Built on this insight, OPCORD (Section~\ref{sec:method}) reads a design's compiled instruction streams as a graph of dependences among all the agents that touch state and bounds what removing each false dependence could recover before any rewrite is built.
It reads closed binaries too, such as the engines of the current release of FastFlowLM (FLM)~\citep{fastflowlm-repo}.
In open designs, its composer regroups one-operator dispatches into shared ones that issue every group's work before the CP waits on any, its stream pass applies that order within one operator's stream, and its loop pass renames buffers, each behind a checker that refuses any rewrite the artifact and the host's accesses do not show legal.
Attention's work per chunk grows with position while a GEMM's stays fixed, so the order that pays and the configuration that minimizes TTFT, namely how the columns are split between the two, both change with the prompt.
An event model therefore prices each candidate order and configuration from per-operator probes.
For each prompt length, OPCORD runs the candidate with the minimum predicted time.
Since the analysis, the bound, and the stream pass with its checker work on any stack's instruction streams, OPCORD serves designs from open compilers such as AIR and IRON, on which researchers and industry build independently, and a team with a closed stack's source can run the same analysis and checkers on its own designs.

On AIR's fused prefill and decode designs for five LLMs, OPCORD shortens TTFT by \PrefillGainLo--\PrefillGainHi$\times$ at prompts of 1K to 32K tokens against the original program of each design, run on whichever measured configuration minimizes its TTFT, and it lowers the time per token by \DecodeGainLo--\DecodeGainHi$\times$ at contexts of about 30K tokens against the unmodified decode design, with bit-identical outputs in both phases (Section~\ref{subsec:e2e}).
By FLM's own prefill timer, OPCORD's TTFT on AIR's designs is also \AbsGainLo--\AbsGainHi$\times$ lower than that of FLM's current release for every LLM at 1K to 16K tokens.
Priced by the event model alone, in an earlier form with the same constants, OPCORD's picks of order and configuration lose at most \ChoiceOpcordMax\% against the measured minimum at any cell scored, whereas each fixed rule loses \ChoiceAlwaysMax--\ChoiceFixedSTwoMax\% at its worst cell (Section~\ref{subsec:decision}).
Reordering from four chunks on the baseline's configuration, as a hand-edited host program would, loses up to \ChoiceFourBaseMax\% where the reordered dispatches run faster on another one, so the order is chosen with the configuration at each prompt length rather than written once into the design.

The stream pass's checker refuses all 12 illegal rewrites in our controls, and every rewrite it shows illegal that we force onto the device fails there (Section~\ref{subsec:legality-eval}).
All 1{,}685 streams that the analysis reads from three stacks round-trip byte for byte, and its bound holds the measured gain on 185 of 187 AIR prefill cells (Section~\ref{subsec:census}).
Every overlap gain we measure on a released design falls where both clauses hold, and in a two-group design of ours, sharing one direct memory access (DMA) channel between the groups reduces a $1.89\times$ gain to $1.07\times$, within what the bound allows (Section~\ref{subsec:pays}).
The same reading explains why FLM's flash prefill and decode leave little to recover, since both fail both clauses at nearly every boundary, no reorder of the prefill's dispatches frees more than $1.09\times$ from overlap, and removing every false dependence between the decode's dispatches hides host time worth at most $1.01\times$ at the short contexts we recorded.
A fused layer that we write with IRON's interface gains $1.21\times$, so the gains follow the design class rather than the stack.

% VALUE: the three contributions, verbatim from the core (author-only), in MLSys "We" form, the characterization first
In summary, the primary contributions of this work are as follows:
\begin{itemize}
    \item We show that on a spatial NPU whose work one in-order command processor issues, the compiled order is the array's schedule, and that how much rescheduling recovers is set by how a design partitions its work and by the prompt length, as predicted by a condition checkable from the artifacts.
    \item We develop an analysis that reads compiled NPU programs, closed ones included, as dependence graphs over every agent that touches state, bounds what each false dependence can recover, and accepts only rewrites it shows legal.
    \item We design and implement OPCORD, a post-compilation rescheduler that rewrites issue order and buffers behind legality checkers and chooses the order and configuration per prompt length with an analytical event model.
\end{itemize}
