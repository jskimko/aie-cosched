\subsection{Command Semantics}
\label{subsec:semantics}

% VALUE: observation 1: concurrency comes from one command issuing two groups' work before it waits on either, not from queued commands (packing is neutral) or a second hardware context; measured on the existing prefill's own operators with bit-identical outputs
Concurrency on the array comes from one command that issues two groups' work before it waits on either, not from queued commands or a second hardware context.
We pair one attention operator of the existing prefill with one GEMM on disjoint column groups, with outputs bit-identical to those of the operators run alone.
Two commands queued on one hardware context, like one command that holds both streams in sequence, take the sum of the two operators' times less at most one dispatch floor, within 3\% on each of seven pairs.
Packing operators into one command, as MLIR-AIR's multi-launch programs~\citep{wang2026mlirair} also do, therefore creates no overlap on the NPU (Figure~\ref{fig:order}a).
Nor does a second hardware context, because the driver gives every context all eight columns and shares them in time.

% VALUE: one command that issues all of one group's work before any synchronization runs the pair at the longer one's time; the cost appears near the DRAM read cap; because the CP is in order, the order inside a command is itself a scheduling decision, so serial execution is a property of composition, not of the array
In contrast, one command that issues all of the GEMM's work, then the attention operator's stream, and only then the GEMM's synchronizations runs the pair within 6\% of the longer operator's time alone on each of nine pairs (Figure~\ref{fig:order}b).
The small excess appears where the pair's DRAM reads approach the \emph{read cap}, which is the maximum DRAM read rate that the column groups together sustain (Section~\ref{subsec:pricing}).
Because a synchronization on one group delays every later issue to the other (Section~\ref{subsec:platform}), the order of instructions within a command, and not only which operators share it, is a scheduling decision, and the serial execution of the existing prefill is a property of how its commands are composed, not of the array.

\subsection{Recurring Waits}
\label{subsec:losses}

% VALUE: observation 3: the waits recur at three places, each a textbook false dependence (cited): an order dependence where the instruction order puts a wait data does not require, a name dependence where work shares storage it need not share
At three places in the existing designs, from the CP's stream down to one operator's loop, work waits on other work whose results it does not consume, which is a \emph{false dependence} in the textbook sense~\citep{bernstein1966analysis,kuck1981dependence}.
It is an \emph{order} dependence where the instruction order alone places the wait, which reordering removes, or a \emph{name} dependence where two uses share storage they need not share, which renaming removes~\citep{tomasulo1967,lam1988software}.
% DECISION: false dependences, the order and name causes, reordering, and renaming are textbook and cited; the paper claims their analysis on this platform, never the classes. Section 4 classes each wait formally.

\textbf{Column Groups in Prefill.}
% VALUE: one operator per command and no overlap across commands make the prefill's column groups take turns, an order dependence in the CP's stream between operators; the array idles while the device reads busy: the computable occupancy reads 92-97% of TTFT and counts neither idle group; attention's share grows 12% -> 49%
The existing prefill issues one operator per command, about 1{,}500 commands for a 2{,}048-token prompt, so its column groups take turns although neither consumes the other's current work, which is an order dependence in the CP's stream between operators.
The runtime reports nothing per column, and the one occupancy a developer can compute, which sums each operator's time when dispatched alone less the dispatch floor, reads 92--97\% of TTFT, yet columns 1--6 idle while attention runs and columns 0 and 7 idle while the GEMMs run.
Attention's share of TTFT, and with it the GEMM columns' idle time, grows from 12\% to 49\% between 512 and 4{,}096 tokens of the Llama-3.2-1B prefill.

\textbf{Columns of One Operator.}
% VALUE: the same order dependence inside one operator: attention issues column 7 only after waiting on column 0, and alternating the columns lowers attention's device-busy time to 0.67x with equal work per column, so the CP's order is the cause
The existing attention stream issues column~7's inputs only after two synchronizations on column~0's key and value transfers, which complete when column~0 is about half done.
Alternating the two columns' work so that both start before the CP waits on either reduces attention's device-busy time to $0.67\times$ at each of seven chunks of a 2{,}048-token prompt, with the same instructions and bit-identical outputs.
Each column's half alone takes the same time, so the loss comes from the CP's order rather than an imbalance of work.
% SOURCE: decoded from the shipped a_32_4_0_0 stream, mid-stream synchronizations at ops 70, 75 (column 0) and 92, 97 (column 7); column 7's issue (ops 81-91) follows column 0's two mid-stream synchronizations (vault lab-prefill-overlap (4)).
% SOURCE: (alternated - F) / (existing - F) = 0.666-0.668 on 7 pairs, chunks 2-14 at 2,048 tokens; column 7 alone / column 0 alone = 0.994-1.010 (amd-npu 17f7ec3 ovl4/, vault lab-prefill-overlap (5)c); at absolute chunks 16-255: Qwen3-4B 0.66-0.68; Llama-3.2-1B 0.66 / 0.57 / 0.41 / 0.43 / 0.68 / 0.67 / 0.66, lower at its mid-range chunks (vault lab-agent-step (4)).

\textbf{Transfers in Decode.}
% VALUE: a name dependence inside decode attention's loop: attention grows to most of the time per token and reads KV at half the cap; neither the transfer alone nor the CP's order limits it (the measurement chain: appendix-body.tex, app:decode-chain (cut 2026-10-24)); the loop's keys, values, and scores sit in one buffer each, so each block's transfer waits for the previous block's compute (+41% per position), and MLIR-AIR's double-buffering pass declines the loop because the running max and accumulator live across blocks
In decode, attention takes up to 70\% of the time per token at long contexts, yet reads the KV cache at only half the DRAM read cap.
Neither the transfer alone nor the CP's order limits it.
Instead, its loop holds the keys, the values, and the scores passed between its two cores in one buffer each, so each block's transfer waits for the compute on the previous block, which adds 41\% to the time per position.
MLIR-AIR's double-buffering transformation declines the loop because its running maximum and accumulator live across blocks, so all three buffers, whose waits are name dependences, stay single.
