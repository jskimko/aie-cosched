\subsection{Dispatch Semantics}
\label{subsec:semantics}

% VALUE: observation 1: concurrency comes from one dispatch issuing two groups' work before it waits on either, not from queued dispatches (packing is neutral) or a second hardware context; measured on the original prefill's own operators with bit-identical outputs
Concurrency on the array comes from one dispatch that issues two groups' work before it waits on either, not from queued dispatches or a second hardware context.
We pair one attention operator of the original program with one GEMM on disjoint column groups, with outputs bit-identical to those of the operators run alone.
Two dispatches queued on one hardware context, like one dispatch that holds both streams in sequence, take the sum of the two operators' times less at most one dispatch floor, within 3\% on each of seven pairs.
Packing operators into one dispatch, as MLIR-AIR's multi-launch programs also do, therefore creates no overlap on the NPU (Figure~\ref{fig:rewrites}a, before).
Nor does a second hardware context, because the driver gives every context all eight columns and shares them in time~\citep{xdna-driver}.

In contrast, one dispatch that issues all of the GEMM's work, then the attention operator's stream, and only then the GEMM's synchronizations runs the pair within 6\% of the longer operator's time alone on each of nine pairs (Figure~\ref{fig:rewrites}a, after).
The small excess appears where the pair's DRAM reads approach the \emph{read cap}, which is the maximum DRAM read rate that the column groups together sustain.
Because a synchronization on one group delays every later issue to the other (Section~\ref{subsec:platform}), the order of instructions within a dispatch, and not only which operators share it, is a scheduling decision.

\subsection{Where Fused Designs Wait}
\label{subsec:losses}

% VALUE: in the fused LLM designs we study, the waits recur at three places, each a textbook false dependence (cited): an order dependence where the instruction order puts a wait data does not require, a name dependence where work shares storage it need not share
At three places in the fused LLM designs we study, work waits on other work whose results it does not consume, which is a \emph{false dependence} in the textbook sense~\citep{bernstein1966analysis,kuck1981dependence}.
It is an \emph{order} dependence where the instruction order alone places the wait, which reordering removes, or a \emph{name} dependence where two uses share storage they need not share, which renaming removes~\citep{tomasulo1967,lam1988software}.
% DECISION: false dependences, the order and name causes, reordering, and renaming are textbook and cited; the paper claims their analysis on this platform, never the classes. Section 4 classes each wait formally.

\textbf{Column Groups in Prefill.}
% VALUE: one operator per dispatch and no overlap across dispatches make the prefill's column groups take turns, an order dependence in the CP's stream between operators; the array idles while the device reads busy: the computable occupancy reads 92-97% of TTFT and counts neither idle group; attention's share grows 12% -> 49%; the counters show the cores waiting
The original program issues one operator per dispatch, about 1{,}500 dispatches for a 2{,}048-token prompt, so its column groups take turns (Figure~\ref{fig:timeline}), which is an order dependence in the CP's stream between operators.
Attention on one chunk reads the QKV projections of that chunk and earlier ones, and only that chunk's output projection reads its result, so the GEMMs of the layer's later chunks could run beside it.
The host, however, runs each layer stage by stage (Section~\ref{subsec:prefill}), so the CP issues no GEMM beside attention.
The runtime reports nothing per column.
The one occupancy a developer can compute, which sums each operator's time when dispatched alone less the dispatch floor, reads 92--97\% of TTFT, although each column group idles while the other runs.
Attention's share of TTFT, and with it the GEMM columns' idle time, grows from 12\% to 49\% between 512 and 4{,}096 tokens of the Llama-3.2-1B prefill.
In the tiles' performance counters, attention's cores stall on a lock for 81--83\% of a 2{,}048-token prefill and the GEMMs' cores for 44\%, which shows that the cores wait, though not when.

\textbf{Columns of One Operator.}
% VALUE: the same order dependence inside one operator: attention issues column 7 only after waiting on column 0, and alternating the columns lowers attention's device-busy time to 0.67x with equal work per column, so the CP's order is the cause
The original program's attention stream issues column~7's inputs only after two synchronizations on column~0's key and value transfers, which complete when column~0 is about half done.
Alternating the two columns' work so that both start before the CP waits on either reduces attention's device-busy time to $0.67\times$ at each of seven chunks of a 2{,}048-token prompt, with the same instructions and bit-identical outputs.
Each column's half alone takes the same time, so the loss comes from the CP's order rather than an imbalance of work.

\textbf{Transfers in Decode.}
% VALUE: a name dependence inside decode attention's loop: attention grows to most of the time per token and reads KV at half the cap; neither the transfer alone nor the CP's order limits it (the measurement chain: appendix-body.tex, app:decode-chain (cut 2026-10-24)); the loop's keys, values, and scores sit in one buffer each, so each block's transfer waits for the previous block's compute (+41% per position), and MLIR-AIR's double-buffering pass declines the loop because the running max and accumulator live across blocks
In decode, attention takes up to 70\% of the time per token at long contexts, yet reads the KV cache at only half the DRAM read cap.
Neither the transfer, which runs near the cap when measured alone, nor the CP's order, which issues the next weights before it waits on any KV transfer, limits it.
Instead, its loop holds the keys, the values, and the scores passed between its two cores in one buffer each, so each block's transfer waits for the compute on the previous block.
That compute makes up 41\% of the time per position, or 0.71 of the transfer time.
MLIR-AIR's double-buffering transformation declines the loop because its running maximum and accumulator live across blocks, so all three buffers, whose waits are name dependences, stay single.

\subsection{When Removing a Wait Frees Overlap}
\label{subsec:question}

% VALUE: the question the rest of the paper answers: removing a false dependence pays only where the work it frees can overlap on resources a rewrite cannot duplicate, with no true dependence between (each clause from a platform fact); how much work qualifies is set by how the design cuts its work and by the prompt length, so the order that pays changes with length and must be priced; the full claim and its tests are in Section 4.7
% DECISION: the critical-path condition is textbook and cited; the paper's claim is the condition's platform terms (non-duplicable resources, the host as an agent) and its dependence on the cut and the prompt length, never "false dependences cost time".
Removing a false dependence frees overlap only where the work it frees runs on core tiles and DMA channels that the work it waited on does not use.
These are resources a rewrite cannot duplicate, because every engine runs its own work in order, and a buffer can be renamed into several slots whereas a core tile or a DMA channel cannot.
It also frees overlap only where no true dependence, on the device or through a host step that reads one dispatch's output before it issues the next, separates the two pieces of work.
We call these two checkable clauses together the \emph{condition}.
They refine the rule that removing a false dependence gains time only on the critical path~\citep{fields2003interaction}, since on this platform removing one shortens that path only when both hold.
Both clauses name resources and dependences that the analysis reads from the artifacts and the host's accesses (Section~\ref{sec:order}).
The condition therefore screens out the false dependences that cannot free overlap before any duration is measured, whereas the critical-path rule needs durations to say which do.
Durations decide the rest: how much each remaining false dependence frees, whether that exceeds its cost, and what a rewrite saves beyond overlap, such as a dispatch.
The bound of Section~\ref{subsec:removal} and the event model of Section~\ref{subsec:pricing} supply them.

How much work meets both clauses is set by how the design cuts its work, into configurations, into dispatches, and into buffers, and by the prompt length, which sets the balance between attention and the GEMMs.
The issue order that pays therefore changes with the prompt and must be priced per length rather than fixed.
The configuration that pays moves with the same balance, because more attention columns shorten attention but lengthen every GEMM.
We call the designs we read from three stacks our \emph{census}, and Section~\ref{subsec:pays} tests the condition across its design classes and across prompt lengths, and the first clause directly.
