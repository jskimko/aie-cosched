\section{Motivation}
\label{sec:motivation}

% VALUE: the CP's instruction order decides which column groups work at once, and the existing designs serialize groups that could run together; three observations and three challenges follow
The CP's instruction order decides which column groups of the array work at once, and the existing designs serialize groups that could run together.
Three observations show how, and they pose the challenges that the rest of the paper answers.
% DECISION: the lead insight is that the CP's instruction order is the array's schedule and is fixed in the emitted streams; "rationed by false dependences" is its consequence and is never stated as the lead.

\subsection{Command Semantics}
\label{subsec:semantics}

% VALUE: observation 1: concurrency comes from one command issuing two groups' work before it waits on either, not from queued commands (packing is neutral) or a second hardware context; measured on the existing prefill's own operators with bit-identical outputs
Concurrency on the array comes from one command that issues two groups' work before it waits on either, not from queued commands or a second hardware context.
We pair one attention operator of the existing prefill with one GEMM, and every composition below produces outputs bit-identical to those of the operators run alone (Figure~\ref{fig:pairs}).
Two commands queued on one hardware context take as long as one command that holds both streams in sequence, within 3\% on seven pairs, and that command takes the sum of the two operators' times less one dispatch floor, within 2\%.
Packing operators into one dispatch, which CUDA Graphs~\citep{nvidia-cudagraphs}, XRT's run lists~\citep{xrt-repo}, and MLIR-AIR's multi-launch programs~\citep{wang2026mlirair} use to amortize launch cost, thus creates no overlap on the NPU (Figure~\ref{fig:order}b).
Nor does a second hardware context, because the driver allocates every context all eight columns and shares them in time, so a one-column design on two contexts takes $1.97\times$ as long as on one (Appendix~\ref{app:contexts}).

% VALUE: one command that issues all of one group's work before any synchronization runs the pair at the longer one's time; the cost appears near the DRAM read cap; because the CP is in order, the order inside a command is itself a scheduling decision, so serial execution is a property of composition, not of the array
In contrast, one command that issues all of the GEMM's work, then the attention operator's stream, and only then the GEMM's synchronizations runs the two in 1.00--1.06$\times$ the longer one's time on nine pairs that cover three GEMM shapes and attention chunks 0 to 15 (Figure~\ref{fig:order}c).
On six further pairs, the overlap hides 90--96\% of the shorter operator's work beyond the dispatch floor that one command already saves.
The small excess appears where the pair's DRAM reads approach the \emph{read cap}, which is the highest DRAM read rate that the column groups together sustain, 53.9--55.3\,GB/s in these runs (Section~\ref{subsec:removal}).
Because a synchronization on one group delays every later issue to the other (Section~\ref{subsec:platform}), the order of instructions within a command, and not only which operators share it, is a scheduling decision.
The serial execution of the existing prefill is therefore a property of how its commands are composed, not of the array.

\subsection{The Idle Array}
\label{subsec:idle}

% VALUE: observation 2: the array idles while the device reads busy; busy almost all the time but on one group at a time; the runtime reports nothing per column, the computable occupancy reads 92-97% of TTFT and counts neither idle group; attention's share grows 12% -> 49%; the counters' lock stalls show the waits without timing them
\begin{figure}[t]
    \centering
    \includegraphics[width=\linewidth]{fig/busy.pdf}
    % VALUE: in the existing prefill, attention's share grows with prompt length, and each column group idles while the other computes
    \caption{Share of TTFT of the existing Llama-3.2-1B prefill by prompt length. Device-busy parts are each operator's time when dispatched alone, less the dispatch floor, summed over the prefill.}
    \label{fig:busy}
\end{figure}

In the existing Llama-3.2-1B prefill, the device is busy almost all of the time, but on only one column group at a time.
The runtime reports nothing per column, and the one occupancy a developer can compute, which sums each operator's time when dispatched alone less the dispatch floor, reads 92--97\% of TTFT (Figure~\ref{fig:busy}).
Since the commands run one at a time, columns 1--6 idle while attention runs and columns 0 and 7 idle while the GEMMs run, and that sum counts neither idle group.
Attention's share of TTFT, and with it the GEMM columns' idle time, grows from 12\% to 49\% between 512 and 4{,}096 tokens.
In the tiles' performance counters, which we arm through the same instruction stream, attention's cores stall on a lock for 81--83\% of a 2{,}048-token prefill and the GEMMs' cores for 44\%.
These totals also count waits on true dependences and between commands, so they show that the cores wait but not when.

\subsection{Recurring Waits}
\label{subsec:losses}

% VALUE: observation 3: the waits recur at three places, each a textbook false dependence (cited): an order dependence where the instruction order puts a wait data does not require, a name dependence where work shares storage it need not share
At three places in the existing designs, from the CP's stream down to one operator's loop, work waits on other work whose results it does not consume, which is a \emph{false dependence} in the textbook sense~\citep{bernstein1966analysis,kuck1981dependence}.
It is an \emph{order} dependence where the instruction order alone places the wait, which reordering removes, or a \emph{name} dependence where two uses share storage they need not share, which renaming removes~\citep{tomasulo1967,lam1988software}.
% DECISION: false dependences, the order and name causes, reordering, and renaming are textbook and cited; the paper claims their analysis on this platform, never the classes. Section 4 classes each wait formally.

\textbf{Column Groups in Prefill.}
% VALUE: one operator per command and no overlap across commands make the prefill's column groups take turns, an order dependence in the CP's stream between operators
The existing prefill issues one operator per command, about 1{,}500 commands for a 2{,}048-token prompt, so its column groups take turns although neither consumes the other's current work (Sections~\ref{subsec:semantics} and~\ref{subsec:idle}).
This order dependence sits in the CP's stream, between operators.
% SOURCE: commands = 16 layers x chunks x 6 + 11 LM-head commands = 1,547 at 2,048 tokens (vault lab-prefill-census (1)).

\textbf{Columns of One Operator.}
% VALUE: the same order dependence inside one operator: attention issues column 7 only after waiting on column 0, and alternating the columns lowers attention's device-busy time to 0.67x with equal work per column, so the CP's order is the cause; the loss grows with prompt and context
The existing attention stream issues column~7's inputs only after two synchronizations on column~0's key and value transfers, which complete when column~0 is about half done.
Alternating the two columns' work so that both start before the CP waits on either reduces attention's device-busy time to $0.67\times$ at each of seven chunks of a 2{,}048-token prompt, with the same instructions and bit-identical outputs.
Each column's half alone takes the same time within 1\%, so the loss comes from the CP's order rather than an imbalance of work, and it grows with the prompt and the cached context (Appendix~\ref{app:append-waits}).
% SOURCE: decoded from the shipped a_32_4_0_0 stream, mid-stream synchronizations at ops 70, 75 (column 0) and 92, 97 (column 7); column 7's issue (ops 81-91) follows column 0's two mid-stream synchronizations (vault lab-prefill-overlap (4)).
% SOURCE: (alternated - F) / (existing - F) = 0.666-0.668 on 7 pairs, chunks 2-14 at 2,048 tokens; column 7 alone / column 0 alone = 0.994-1.010 (amd-npu 17f7ec3 ovl4/, vault lab-prefill-overlap (5)c); at absolute chunks 16-255: Qwen3-4B 0.66-0.68; Llama-3.2-1B 0.66 / 0.57 / 0.41 / 0.43 / 0.68 / 0.67 / 0.66, lower at its mid-range chunks (vault lab-agent-step (4)).

\textbf{Transfers in Decode.}
% VALUE: a name dependence inside decode attention's loop: attention grows to most of the time per token and reads KV at half the cap; neither the transfer alone nor the CP's order limits it (the measurement chain in the appendix); the loop's keys, values, and scores sit in one buffer each, so each block's transfer waits for the previous block's compute (+41% per position), and MLIR-AIR's double-buffering pass declines the loop because the running max and accumulator live across blocks
In decode, attention reads the KV cache at only 51\% of the DRAM read cap, although its share of the time per token grows to 70\% at a 32{,}704-token context.
Neither the transfer alone nor the CP's order is the limit (Appendix~\ref{app:decode-chain}).
Instead, the KV loop holds its keys, its values, and the scores passed between its two cores in one buffer each, so each block's transfer waits for the compute on the previous block, which adds 41\% to the time per position.
MLIR-AIR's double-buffering transformation declines the whole loop because its running maximum and accumulator live across blocks, so these three buffers, whose waits are name dependences, stay single.
% SOURCE: per-token time = 15.94 ms + 1.156 us x L, max residual 0.2% over L = 2,048-32,704 (Llama-3.2-1B, one 32k-window build, median of 3); 32 KiB per position / 1.156 us = 28.4 GB/s against a same-batch 8x2 cap of 55.2 GB/s; attention 13/23/37/54/70% of per-token time at 2k/4k/8k/16k/32k (vault lab-decode-long-context (5)).
% SOURCE: bytes-only discriminator: ELF window 32,768 vs 2,048 at the same small L, 20.81 ms / 30,720 positions = 0.677 us = 48.4 GB/s = 88% of the 55.2 GB/s cap and 104% of the two-shim probe; serialized compute 1.156 - 0.677 = 0.478 us = 41% of the per-position time (vault lab-decode-long-context (7)).

\subsection{Challenges}
\label{subsec:challenges}

% VALUE: removing these waits from compiled designs poses three challenges, one per section: recover the order from binaries without source (Section 4), price a schedule without running it (Section 5), rewrite legally without the compiler that built the design (Section 6)
Removing these waits from already compiled designs poses three challenges.
First, the order must be recovered from binaries without their source, although even an open design spreads it over the CP's stream, DMA chains, and core loops (Section~\ref{sec:order}).
Second, a schedule must be priced without running it, because the program fixes the order of the work but not its durations, and the candidates multiply with chunks, column divisions, and removals (Section~\ref{sec:pricing}).
Third, a reorder or a rename must be shown legal without the compiler that built the design, from what the instructions alone establish about buffers, locks, and routes (Section~\ref{sec:method}).
