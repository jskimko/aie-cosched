\section{Dependence Analysis}
\label{sec:order}

% VALUE: on XDNA 2 each engine runs its program in order and nothing schedules across engines, so the order of the work and the waits between engines are in the compiled program; the section shows this from measured command semantics, states the execution model, reads a stream into a happens-before graph with a cause per wait, and extends the reading to closed binaries
On XDNA~2, each engine runs its own program in order, and no hardware or runtime scheduler reorders work across engines, while arbitration on shared ports and locks serializes work at run time and enters the analysis as a resource.
The order of the work and the waits between engines are therefore fixed by the compiled program and the host's dispatch sequence, whereas their durations are not.
We first establish how the CP turns instruction streams into concurrency (Section~\ref{subsec:semantics}), then state the execution model the analysis assumes (Section~\ref{subsec:model}), read a stream into a graph of what must finish before what starts, with a cause for each wait (Section~\ref{subsec:reading}), and extend the reading to binaries shipped without source (Section~\ref{subsec:closed}).

\subsection{Command Semantics}
\label{subsec:semantics}

% VALUE: the CP semantics, measured on the existing prefill's own operators, say where concurrency can come from: not from queued commands, but from one command that issues both groups' work before it waits on either
To find where concurrency can come from, we measure how the CP turns instruction streams into overlap on the existing prefill's own operators, pairing one attention operator on columns 0 and 7 with one GEMM operator on columns 1--6.
Every composed command here produces outputs bit-identical to those of the operators run alone.

\begin{figure}[t]

    \caption{Median time of one attention and one GEMM operator on disjoint column groups, normalized to the longer operator alone, over 20 runs per pair. Holding both streams in one command saves one dispatch floor against the sum.}

\textbf{Queued Commands.}
% VALUE: the runtime gives no overlap across commands, and placing two operators in one command is itself neutral, so overlap must come from within a command
Two commands queued on one hardware context, with no wait between them, take as long as one command that holds both streams in sequence, within 3\% on each of the seven pairs where we queue them (Figure~\ref{fig:pairs}).
Holding both streams in sequence in one command takes the sum of the two operators' times minus one dispatch floor, within 2\%, so placing two operators in one command is itself neutral.
This is why packing several operators into one dispatch, which is standard practice for amortizing launch cost, as in CUDA Graphs~\citep{nvidia-cudagraphs}, XRT's run lists~\citep{xrt-repo}, and MLIR-AIR's multi-launch programs~\citep{wang2026mlirair}, removes dispatch cost on the NPU but creates no overlap.
% SOURCE: queued / in-sequence = 1.007-1.029 on 7 pairs (amd-npu 17f7ec3 prefill-overlap/ovl4/, lab-prefill-overlap (5)b); in-sequence / (A + G - F) = 0.996-1.021 over 17 pair runs (ovl/, ovl2/ at 8f13e05 and ovl4/; report.txt H1 column).
% SOURCE: XRT run list, /opt/xilinx/xrt/include/xrt/experimental/xrt_kernel.h:21 (XRT 2.25.0); MLIR-AIR stitch_elf (vault src-mlir-air-llms).

\textbf{Concurrent Issue.}
% VALUE: one command that issues both groups' work before it waits on either runs them concurrently at nearly the longer one's time; the small cost appears when both read DRAM near the cap
When one command issues all of the GEMM's work, then the attention operator's stream, and only then the GEMM's synchronizations, the two operators run concurrently.
Such a command takes 1.00--1.06 times the longer operator's time on 9 pairs that cover three GEMM shapes and attention over chunks 0 to 15 (Figure~\ref{fig:pairs}).
On six further pairs with other shapes and chunks, the overlap hides 90--96\% of the shorter operator's work, after excluding the dispatch floor that the merge already saves.
The overlap costs most when the pair's combined DRAM read rate approaches the read cap, at about 95\% of the cap measured in the same batch.
The serial execution of the existing prefill is therefore a property of how its commands are composed, not of the array or its configuration.
% SOURCE: interleaved / max(A, G) = 0.998-1.058 over 10 pair runs = 9 pairs (c8 + lm measured twice, 1.054 and 1.058; the figure keeps each pair's first measurement); GEMM shapes up, LM head chunk, down; attention chunks 0, 4, 8, 12, 15 (lab-prefill-overlap (3)).
% SOURCE: hidden fraction of the shorter operator's work, (in-sequence - interleaved) / (min(A, G) - F) = 0.90-0.96 on 2+qkv, 6+o, 11+gate, 14+qkv, 6+gate, 11+o (lab-prefill-overlap (5)a).
% SOURCE: DRAM rate during the interleaved command 52.2 GB/s against a same-batch 8x2 cap of 53.9-55.3 GB/s for c8 + lm, the costliest overlap (1.054-1.058) (lab-prefill-overlap (3)).

\textbf{Synchronization Order.}
% VALUE: because the CP is in order, a wait on one group delays the issue of every other group's work; the attention measurement of Section 4.1 isolates this effect, so the instruction order is a scheduling decision of its own
Since the CP executes in order, a synchronization on one group delays every later issue, including the issue of another group's work.
The existing attention operator isolates this effect (Section~\ref{subsec:losses}): its two columns carry equal work, yet alternating their segments lowers its device time to $0.67\times$ at 2{,}048 tokens with the same instructions.
The CP's instruction order, and not only the assignment of operators to commands, is therefore a scheduling decision.
% SOURCE: vault lab-prefill-overlap (4)-(5)c; Section 4.1 carries the numbers.

\textbf{Hardware Contexts.}
% VALUE: a second hardware context gives no concurrency here: the driver's source allocates every context the whole array and shares it in time, and narrower partitions would need contiguous columns, rebuilt designs, and a host round trip at every dependence, so concurrency comes from within one command
Two hardware contexts on disjoint partitions are the obvious alternative, but the driver's source shows that every hardware context on our platform is allocated all eight columns, so co-resident contexts share one partition in time.
Even where narrower partitions are allowed, a partition spans contiguous columns, whereas the existing attention sits on columns 0 and 7, so each group would need its own rebuilt design.
Every dependence between attention and a GEMM would then cross the host, which waits on one context before it submits to the other.
Concurrency on the array therefore comes from within one command, which needs no rebuild and no change to the driver or firmware.

% SOURCE: contiguous partitions, separate 6- and 2-column builds with attention moved onto adjacent columns, and the host round trip (vault lab-prefill-overlap (1)).

\subsection{Execution Model}
\label{subsec:model}

% VALUE: the analysis models a dispatch as operations on engines (CP instructions, BD executions, core loop iterations), each with read and write sets over locations that include every exclusively held resource; under static control one dispatch at given runtime parameters has one static set of operations, a loop with data-dependent control is reported and left out, and durations stay measured inputs
The analysis models a dispatch as operations on engines, each with a set of locations that it reads and a set that it writes.
A command contributes one operation per instruction of its stream on the CP, a DMA engine one per execution of a BD on one channel, and a core one per iteration of each counted loop.
Locations cover every resource that one operation holds exclusively, namely bytes of DRAM, memory tiles, and local memory, as well as BD slots, locks, DMA channels, task-queue slots, stream-switch ports, and configuration registers, so a structural hazard is also a conflict on a location.
For example, a lock acquire reads and writes its lock, a queue push writes a queue slot and reads its BDs, and a BD execution reads its BD slot and its source bytes and writes its destination bytes.
We assume static control: the CP's stream is straight-line, since a synchronization waits but does not branch, and every core loop is counted, with a trip count that depends on the dispatch's runtime parameters rather than on computed data.
A dispatch at given runtime parameters then has one static set of operations, and a loop with data-dependent control is reported as such and left out of the analysis.
A loop whose body holds nested control, or an access the analysis cannot classify, is likewise reported as unsupported and not analysed, which in the decode design applies to every loop outside attention.
We also assume that the host follows static control, issuing commands in an order that depends on the LLM and the lengths of the context and the prompt rather than on data, and its own work enters as a measured cost.
Durations remain measured inputs, because the program fixes the order of each engine's work but not how long the work takes; each operator's duration enters as a probe measured once per configuration (Section~\ref{subsec:pricing}).

% VALUE: happens-before is completion before start, not issue order; each direct edge comes from one of 11 mechanisms at the stream, data-movement, or loop granularity and is attributed to exactly one, and edges no mechanism explains are counted, so the count measures the model's coverage
From these operations, the analysis builds a \emph{happens-before} graph, in which an edge from $a$ to $b$ means that $b$ cannot start until $a$ has completed.
Issue order alone does not create such an edge, because a queue push is issued in order but its transfer completes later.
Each direct edge comes from one of the 11 ordering mechanisms of Table~\ref{tab:mech}, at the granularity of the CP's stream, of data movement, or of a core loop, and an edge that two mechanisms imply is attributed to the first in the table.
An operation whose ordering effect no mechanism describes, such as an unknown opcode or a write outside the known register map, takes edges to its neighbors on the CP, and counting these per stream is how the model's coverage is to be measured.
Edges of mechanism 2 never stall, because their instructions complete at issue, so they are attributed but reported apart from the blocking edges.
% SOURCE: the mechanism table, attribution order, granularities, UNATTRIBUTED, and issue edges (vault lab-cosched-passes (30), item 2); the library AIECoschedDeps (mlir-aie f1725dae1f1, pinned).

% VALUE: each direct edge is classed by the pairs of operations it alone orders: a true dependence if one is read after write, a name dependence if one is write after read or write, an order dependence otherwise; classes say whether renaming or reordering can remove the wait; a wait gating several operations is classed per gated operation, pairs ordered by two disjoint paths are counted as redundant, and data-dependent loops as control
For each direct edge, the analysis computes the pairs of operations that the edge alone orders, namely those ordered with it and not without it.
The edge is a true dependence if one of these pairs reads a location after the other writes it, a name dependence if none does but one writes after the other reads or writes, and an order dependence otherwise.
The first two follow the conflicts that Bernstein's conditions exclude between pieces of work that run in parallel~\citep{bernstein1966analysis}, and the name class covers the anti and output dependences of compilers~\citep{kuck1981dependence}.
Renaming the conflicting locations can therefore remove a name dependence, reordering can remove an order dependence, and a true dependence stays.
A synchronization that gates several operations contributes one edge per gated operation, so each operation's conflicts are classed on their own.
A pair that two disjoint paths order is lost by no single edge, so each edge on those paths may be classed as an order dependence alone, and such pairs are counted as redundant instead of being attributed to either path.
A loop with data-dependent control is counted as control.

We check the recovered order through its consequences rather than against a hardware trace.
Every wait that the analysis classes as false and that our passes remove leaves the outputs bit-identical (Section~\ref{sec:method}), each measured gain is compared with its bound (Section~\ref{subsec:tests}), and the operations that the analysis leaves out are counted per stream.
To show how the CP executes the order, we insert the runtime's record-timer instruction after each synchronization and after each run of issue instructions, so that the firmware writes an identifier and a 1.8~GHz device timer into a buffer that the host reads after the run.
The array's configuration is left unchanged.

\subsection{Closed Binaries}
\label{subsec:closed}

% VALUE: a closed stack ships binaries only, so its streams are recorded at the runtime's boundary without the device and lifted with a byte-identical round trip; each issue is attributed to the column group its data reaches through the configuration's decoded routes; FastFlowLM's prefill then issues one group per command, and serial issue predicts its time where overlap does not
FastFlowLM ships its engines as binaries, so we record their instruction streams at the runtime's boundary, either with a recording library that never opens the device or with an interposer during a device run, and lift each stream into MLIR-AIE's runtime-sequence form.
Every stream recorded offline round-trips through the lifter byte for byte, so the analysis reads exactly what the engine dispatches.
Because FastFlowLM's attention reads through shim tiles of the GEMM columns, attributing an issue to its column would mix the groups, so the analysis decodes the configuration's stream routes and attributes each issue to the group whose compute tiles its data reaches.
Under this attribution, the one capture we analyse, a 1{,}009-token prefill of Gemma-4-E2B, changes column group only at the boundary between two commands, once into attention and once out of it in every layer, so it issues serially, one group per command.
The sum of its commands' times measured alone, each less the dispatch floor and plus the boundary cost between commands, matches its measured time within 10.0\%, whereas full overlap would place it 36.5\% lower, a separation far wider than the batch-to-batch variation of the read cap this machine shows.
A census of which columns carry any instruction, over all 218 recorded streams and over the capture itself, agrees with this attribution without establishing it, since it counts addressed columns rather than the programs they serve; Appendix~A gives the counts.
Since FastFlowLM's closed libraries build these streams and their buffers, we measure removals on MLIR-AIR's fused prefill, which reimplements FastFlowLM's designs~\citep{wang2026mlirair}.
Its decoded configuration places the GEMMs on columns 1--6 and attention on columns 0 and 7, as FastFlowLM's fused prefill does, so the two share the column groups whose turns our passes remove.
Appendix~A states how the attribution was chosen, and what the rule registered before it labels the same capture.

\subsection{Textbook Classes on a Grid}
\label{subsec:grid}

% VALUE: the waits are false dependences in the textbook sense, of two causes (order, name) at two granularities (the CP's stream, an engine's loop); the analysis's classes are these columns, a DMA chain is a loop on a DMA engine, and the grid places every known instance, with two cells empty; the classes are cited, the claim is where lowering reintroduces them
The expert designs lose end-to-end time on the NPU because work waits on other work that it does not consume.
Such a wait is a \emph{false dependence}, which is an ordering that the lowered program imposes although no data flows between the two pieces of work, namely a name or order dependence in the classes of Section~\ref{subsec:reading}.
A false dependence has one of two causes.
An \emph{order} dependence is a wait placed where the written program order put it rather than where data requires it, and reordering removes it.
A \emph{name} dependence arises where two pieces of work share a buffer, lock, or channel that they need not share, as in the anti and output dependences of compilers~\citep{kuck1981dependence}, and renaming the storage removes it~\citep{tomasulo1967,lam1988software}.
These are the analysis's classes of Section~\ref{subsec:reading}, and every blocking edge falls into exactly one of them or is a true dependence.
We find false dependences at two granularities, in the CP's instruction stream and inside an engine's loop, where a BD chain with locks counts as a loop on its DMA engine.

\subsection{Problem Formulation}
\label{subsec:formulation}

\textbf{Resources.}
% VALUE: three kinds of resources: column groups (one operator at a time, data-driven), the CP (one in-order server that issues and blocks), and the host (work between commands)
The array offers a set $\mathcal{G}$ of disjoint column groups, each running one operator at a time, which in the open prefill share only DRAM bandwidth with each other.
The CP is a single in-order server that executes issue instructions, each at a small cost, and blocks at each synchronization until the transfer it names completes.
The host CPU runs the work between operators that the array does not perform, such as normalizations, and it submits and collects commands.

\textbf{Operators.}
% VALUE: each operator is defined by its group, its device time, its host work, and its instruction stream split into segments; dependencies pass through DRAM and need a synchronization
Each operator $o \in \mathcal{O}$ runs on group $g(o)$ for a device-busy time $p_o$, and may need host work of duration $h_o$ after it completes.
Its instruction stream is a sequence of \emph{segments} $s_{o,1}, \dots, s_{o,n_o}$, where each segment consists of synchronizations followed by the issue instructions they gate, and the first segment has no synchronizations.
A dependency graph $E \subseteq \mathcal{O} \times \mathcal{O}$ orders the operators.
Since operators hand data over through DRAM, with no lock on the device between them, a consumer's first issue must follow the producer's final synchronization.
When host work lies between producer and consumer, the consumer must also wait for that host work, and the two cannot share a command.

\textbf{Decisions.}
% VALUE: the essential decisions are the spatial assignment, the CP's instruction order, and the assignment of buffers, which together decide which waits are false; the command partition and the queue depth manage host boundaries and are reported apart
A schedule makes three essential decisions.
The first is the spatial assignment $g(\cdot)$ of operators to column groups, which determines what can run concurrently.
The second is the CP's instruction order, namely a partition of $\mathcal{O}$ into a sequence of commands $C_1, \dots, C_K$ and, for each command, an interleaving $\sigma_k$ of its operators' segments that keeps each operator's segments in their own order.
The third assigns each use of a buffer to a slot in memory, since two uses that share a slot must run one after the other even when neither consumes the other's data.
Two further decisions manage the boundaries with the host: the number $D$ of commands the host keeps in flight, and how operators that do not overlap are packed into commands.
Both would disappear if the host work moved onto the array, so we report their effect separately from that of the essential decisions.

\textbf{Timing.}
% VALUE: the semantics of Section 3.1 as rules: commands in sequence with a boundary cost; within a command, a segment's work starts once issued and its predecessor has finished; a synchronization completes when its work has
A command starts on the device after its predecessor completes, plus a \emph{boundary cost} $\epsilon$ when it was already queued, or the dispatch floor $F$ when it arrives at an idle device.
Within a command, the CP walks $\sigma_k$ in order.
The work of segment $s_{o,j}$ starts on $g(o)$ once the CP has issued it and the work of $s_{o,j-1}$ has finished, and a synchronization completes once the CP reaches it and the work it names has finished.
Operators that run at the same time on different groups take longer than alone by an overlap cost that grows with the shorter operator's duration, at a rate set by which group holds the critical path (Section~\ref{subsec:removal}).

\textbf{Objective.}
% VALUE: minimize the makespan, which for prefill is TTFT less a fixed head and tail
The objective is the makespan, i.e., the completion time of the last command, which for prefill is the TTFT less a fixed head and tail of work outside the layers.

\textbf{Lower Bound.}
\label{subsec:bound}
% VALUE: each of the three resources bounds the makespan, so their maximum bounds the gap of any schedule on a given assignment
Each resource bounds the makespan from below:
\begin{equation}
\label{eq:lb}
T \;\ge\; \max\Bigl(\max_{g \in \mathcal{G}} \sum_{o:\,g(o)=g} p_o,\;\; L_E,\;\; \sum_{k} c_k\Bigr),
\end{equation}
where $L_E$ is the longest path through $E$ weighted by $p_o$ plus, on host-crossing edges, $h_o$, and $c_k$ is the CP's own work in command $k$.
The first term is the busiest group's work, which no schedule on a fixed assignment can beat.
The bound therefore measures how far a schedule lies from what a given spatial assignment allows.

% DECISION: no NP-hardness claim until a reduction is written; with negligible issue cost and one layer's fixed per-chunk pattern the problem has the structure of a two-machine chain-reentrant shop (wang1997reentrant), and with non-negligible issue cost the CP acts as a shared server (glass2000dedicated, hall2000common) (vault ch3-formulation, Relation to classical scheduling).


\subsection{Bounding a Removal}
\label{subsec:removal}

% VALUE: removing a dependence shortens a phase by at most the time it keeps work on disjoint resources from overlapping, given every other edge; resources are typed (column groups, the CP and its per-command boundary, the DRAM read rate up to its cap, channels borrowed across groups); in a loop the critical cycle determines the time per iteration, so a removal off that cycle gains nothing; the bound is Amdahl's law for an ordering, and it needs only the program's order and measured durations
Removing a false dependence $d$ speeds a phase up by at most $T / (T - O(d))$, where $T$ is the phase's time and $O(d)$ is the time during which $d$ keeps work on disjoint resources from overlapping, given every other edge of the happens-before graph.
The resources are typed, namely the column groups, the CP with its cost at each command boundary, the DRAM read rate up to its cap, and the channels that one group borrows from another's columns.
Work on one resource cannot overlap itself, so $O(d)$ counts only the overlap that the resources allow, and it is zero when $d$ lies off the longest path.
In a loop, the graph repeats, and the maximum cycle mean over its cycles determines the time per iteration, as in the throughput analysis of synchronous dataflow graphs~\citep{ghamarian2006throughput}.
Which test applies therefore follows from the granularity of Table~\ref{tab:grid}: the longest path within a command, and the maximum cycle mean inside an engine's loop.
Both give the same necessary condition on a set $S$ of removals: unless $S$ cuts every path or cycle that attains the maximum, one of them survives with its length unchanged, so the phase is still bounded by it and $S$ gains nothing.
The condition is necessary and not sufficient, for two reasons that this machine supplies.
After a cut, the next longest path or cycle bounds what remains, so the gain is what separates them rather than the whole of $O(S)$.
And the groups share capacity, the DRAM read cap and the shim tiles' channels, so a set that does cut every critical path gains only what that capacity leaves: Llama-3.1-8B's decode already reads its cache at the rate two shim tiles sustain, so renaming every buffer on its loop's cycle hides only the serialized compute (Section~\ref{subsec:decode-eval}).
% VALUE: the test says which candidate sets cannot pay, from the graph alone, and says nothing about how much a set that can pay is worth; the magnitude needs the durations and the capacity, which the event model supplies
We therefore use the condition as a test of which candidate sets cannot pay, and leave the magnitude to the event model of Section~\ref{subsec:pricing}.
% SOURCE: the acyclic condition is the minimum cut of a critical subnetwork in project crashing (Kelley 1961; Fulkerson 1961), the cyclic one the iteration bound and maximum cycle mean (Ghamarian 2006; Stuijk 2008); both are cited, never claimed (Section~\ref{sec:related}).
% DECISION: the condition is stated as necessary only, after review r5 showed that a longest-path or cycle criterion is valid on an uncapacitated graph and this machine has a shared DRAM cap, a shared command processor and a per-command boundary cost; the capacity half is the measured regime of this section, and the 8B at cap and the loss at 512-token appends are the two negative instances inside the paper.
The bound applies Amdahl's law to an ordering rather than to a component, and it needs only the program's order and the measured durations of its operations, not a timing trace (Section~\ref{sec:related}).
What the ordering case adds is the typed resources: a removal frees work onto a column group, onto the CP, or onto a DRAM read rate that every group shares, and only the first of those is private, so the share of a phase a removal can recover is not read off the program's order alone.

% VALUE: the DRAM cap makes the allowed overlap depend on which group holds the critical path: co-running costs a bandwidth-bound group a fixed fraction of its partner's duration and a compute-bound group almost nothing, so one regime prices a removal lower than the other
How much overlap the DRAM read rate allows depends on which group holds the critical path.
We measure this on pairs of one attention operator and one GEMM, issued in one command on disjoint columns.
Where the GEMM holds the critical path, on four pairs (five runs) reading 42.9--52.3~GB/s against a measured cap of 53.9--55.3~GB/s, co-running costs it 8.4--10.5\% of the attention operator's device time.
Where attention holds the critical path, co-running costs at most 15~$\mu$s on the five pairs we measure and does not grow with the GEMM's duration.
Two operators of equal duration therefore overlap to within $1.81$--$1.84\times$ of the longer one across those penalties in the first case, and $2.00\times$ in the second.
Per-command read rates during a whole prefill identify the two regimes directly: on Llama-3.2-1B at 4{,}096 tokens, commands that carry only GEMMs read 50.0~GB/s at the median, which is 90--93\% of the cap, whereas commands that carry only attention read 8.3~GB/s, about 15\% of it.
Commands that carry both read 48.0~GB/s, so the GEMM remains the operator near the cap.
Between the existing order and the composed one, the GEMM group's rate over the time its work is outstanding falls from 48.6 to 45.6~GB/s, with the five repetitions of each fully separated, which is the direction the penalty predicts at one cell of one model rather than a second estimate of its size.
% SOURCE: per-command read rates from the ML Timeline records, Llama-3.2-1B scratch 4,096, bytes from the TXN BD chains (amd-npu 71901c50 metrics/retro-2026-10-21/dram-retro.txt, verified from the bare): shipped+Ar GEMM-only n = 12,855 commands p10 41.3 median 50.0 p90 52.8 GB/s; shipped+Ar attention-only n = 2,560 p10 8.2 median 8.3 p90 8.8; composer both groups n = 2,560 p10 35.0 median 48.0 p90 52.4; composer GEMM-only n = 1,230 median 47.8; over each group's outstanding time, G 48.6 (shipped+Ar) vs 45.6 (composer) and A 8.3 vs 8.2, per-rep ranges 48.57-48.59 against 45.54-45.62 and 8.32-8.33 against 8.20, fully separated; read cap 53.9-55.3 GB/s (vault lab-metric-fields (1) and its amendment 1).
% DECISION: the per-command rates identify the regimes and the G drop is reported as the penalty's direction only, scoped to one cell of one model, at npu-gap's request; the penalty's magnitude stays the pair-table fit.
% SOURCE: computed in aie-cosched-paper-0 tmp/regime/{pairs,model,final}.py from lab-prefill-overlap (3)'s pre-registered pair table (10 pair-runs on Llama-3.2-1B, 5 attention chunk indices x 3 GEMM shapes, medians of 20, DRAM measured during each concurrent run, cap 53.9-55.3 GB/s): with the GEMM on the critical path the penalty is 3 us + 0.085 x the co-runner's duration (R2 = 0.993, 5 runs, ratio 0.084-0.105); with attention on it the penalty is 21 us - 0.015 x the co-runner (R2 = 0.896, 5 runs, ratio -0.002 to 0.029); penalty against the pair's total DRAM rate correlates at only r = 0.54, so the regime of the critical-path operator is the predictor and total bandwidth is not (vault decisions log, "Regime analysis, step 1").

To choose among schedules without running each on the device, we price a schedule with an event simulation of the device, the CP, and the host, whose every term is measured (Table~\ref{tab:params}).
On the device, command $k$ ends at
\begin{equation}
\label{eq:cmd}
e_k = \max\bigl(e_{k-1} + \epsilon,\; q_k + F\bigr) + b_k,
\end{equation}
where $q_k$ is the time the host queues it, so a queued command pays the boundary cost $\epsilon$ and a command that arrives at an idle device pays the dispatch floor $F$.
A command's busy time $b_k$ is the sum of its GEMMs' busy times plus a gap $\gamma$ per additional GEMM, and a command that also carries attention takes $\max(a, g) + \beta \min(a, g)$ for attention work $a$ and GEMM work $g$.
Attention's busy time grows linearly with the chunk index, as the number of earlier key blocks does.
The host pays an issue cost per command and a post-processing cost per operator, and it waits on the oldest command once $D$ are in flight.
The TTFT is the simulated span plus a fixed head and tail, namely the embedding, the first normalization, and the LM head.
Because each term is measured separately, an error in one term cannot hide behind another, and the event model reports the device time, the host's exposed time, and the head and tail separately.
