\section{Conclusion}
\label{sec:conclusion}

% DECISION: no outlook and no hardware wish list; the transfer argument and the hardware remedy stay in the appendix's Discussion (author, outline v10.1 decisions: conclusion only).
On a spatial NPU whose work one in-order command processor issues, that processor's instruction order is the array's schedule, and the toolchain fixes it in the instruction streams it emits.
False dependences in this order, and inside the loops of single operators, ration a concurrency that the hardware provides, while the device reads as busy for nearly all of a prefill.
Because nothing reorders work across the array's engines, we read the order from compiled streams, class each wait, price candidate schedules from timings of each operator run alone, and rewrite only what the streams show to be legal, with kernels, driver, and firmware unchanged.
The reorder across column groups is what shortens prefill, by $1.14$--$1.46\times$ from scratch and $1.17$--$1.51\times$ on appends against the fastest existing schedule we measured, and renaming decode's buffers shortens each token by $1.16$--$1.27\times$ at a 16K-token context, so that whole agent turns run $1.15$--$1.32\times$ faster with bit-identical outputs.
On appends, the composed schedules close a median 65\% of the distance from the hand-alternated program to the lower bound.
What remains is the price of overlap under the shared DRAM read cap and the command processor's and the host's work that the schedule does not hide.
