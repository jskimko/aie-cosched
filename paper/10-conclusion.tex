On a spatial NPU whose work one in-order command processor issues, that processor's instruction order is the array's schedule, and it is fixed in the instruction streams a toolchain emits.
False dependences, in this order and inside the loops of a single operator, ration a concurrency the hardware provides, while the busy share a developer can compute for the existing prefill reads 92--97\%.
Because nothing reorders work across the array's engines, we read that order from the compiled streams, class each wait, and price schedules and their lower bound from timings of each operator run alone.
In OPCORD, a composer reorders issue across column groups, and two compiler passes reorder issue within an operator and rename a loop's buffers, all under checkers that refuse an illegal rewrite, with the kernels, driver, and firmware unchanged and the outputs bit-identical.
The composer's reorder is what shortens prefill, because the existing program with attention's columns alternated by hand already carries the reorder within an operator.
Against that program, each side on its faster split, the time to the first token falls by $1.14$--$1.46\times$ from scratch and $1.20$--$1.51\times$ on appends.
At a 16{,}384-token context, OPCORD shortens the time per decoded token by $1.16$--$1.27\times$ against the unmodified decode design, and an agent's turn by $1.15$--$1.32\times$ against the existing program on its faster split.
Its cost is a plan per prompt shape and one set of operator timings per LLM and split, each paid once.
On appends, the composed schedules close a median 65\% of the hand-alternated program's distance to the lower bound, whose binding term is the column groups' own busy time.
They still sit $1.17$--$1.63\times$ above the bound, and the rest lies in the price of overlap under the DRAM read cap and in command-processor and host work that the schedule does not hide.
