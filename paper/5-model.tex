\section{Pricing Schedules}
\label{sec:pricing}

% VALUE: the order is read from the streams and only durations are unknown, so a schedule, its split, and the dependences it removes are priced from per-operator probes before it runs; the bounds limit what any candidate can gain, and the event model prices each candidate
Because a compiled design's order is read from its instruction streams (Section~\ref{sec:order}), only the durations of its work are unknown, so we price a schedule, including its split and the dependences it removes, from probes of each operator dispatched alone, before the schedule runs.
A lower bound and a bound per removal limit what any candidate can gain, and an event model prices each candidate.

\subsection{Problem Formulation}
\label{subsec:formulation}

\textbf{Resources.}
% VALUE: three resources: column groups (one operator at a time, sharing only the DRAM read rate), the CP (one in-order server that issues and blocks), and the host (work between commands)
The array offers a set $\mathcal{G}$ of disjoint column groups, each running one operator at a time, which in the open prefill share only the DRAM read rate.
The CP is one in-order server that issues instructions at a small cost each and blocks at each synchronization until the transfer it names completes.
The host runs the work between operators that the array does not, such as normalizations, and submits and collects commands.

\textbf{Operators.}
% VALUE: an operator is its group, its device time, its host work, and its stream's segments; operators hand data over through DRAM, so a consumer waits for its producer's last synchronization and for any host work between them
Each operator $o \in \mathcal{O}$ runs on group $g(o)$ for a device-busy time $p_o$, may need host work of duration $h_o$ after it completes, and issues the segments $s_{o,1}, \dots, s_{o,n_o}$ that Section~\ref{subsec:reading} defines on its stream.
A dependency graph $E$ orders the operators, and because they hand data over through DRAM with no lock between them, a consumer's first issue must follow its producer's final synchronization and any host work between the two, which also keeps them in separate commands.

\textbf{Decisions.}
% VALUE: three essential decisions (the spatial assignment, which reduces to the split; the CP's instruction order; the buffer assignment); the queue depth and the packing manage only the host boundary and are reported apart
A schedule makes three essential decisions.
The spatial assignment $g(\cdot)$ determines which operators can run at once, and in the LLMs we evaluate it reduces to the \emph{split}, namely the number of columns that attention takes.
The CP's instruction order partitions $\mathcal{O}$ into commands $C_1, \dots, C_K$ and interleaves each command's segments in an order $\sigma_k$ that keeps every operator's segments in their own order.
The buffer assignment maps each use of a buffer to a slot in memory, since two uses of one slot run in turn even when neither consumes the other's data.
The number $D$ of commands in flight and the packing of commands manage only the boundary with the host and would disappear if the host's work moved onto the array, so we report their effect apart.

\textbf{Timing.}
% VALUE: the command semantics as rules: commands in sequence after a boundary cost or the dispatch floor; within a command, a segment's work starts once issued and its predecessor has finished; co-running operators pay an overlap cost
A command starts once its predecessor completes, after a \emph{boundary cost} $\epsilon$ if it was already queued, or after the dispatch floor $F$ if it reaches an idle device.
Within a command, the CP walks $\sigma_k$ in order, and the work of segment $s_{o,j}$ starts once it is issued and $s_{o,j-1}$'s work has finished, and a synchronization completes once it is reached and the work it names has finished.
Operators running at once on different groups each pay an overlap cost (Section~\ref{subsec:removal}).

\textbf{Objective.}
% VALUE: minimize the makespan, which for prefill is TTFT less the head and tail outside the layers
The objective is the makespan (i.e., the completion time of the last command), which for prefill is the TTFT less the head and tail of work outside the layers.

\textbf{Lower Bound.}
\label{subsec:bound}
% VALUE: each resource bounds the makespan, so their maximum bounds any schedule on a given assignment; it needs only the probes and the graph
Each resource bounds the makespan from below:
\begin{equation}
\label{eq:lb}
T \;\ge\; \max\Bigl(\max_{g \in \mathcal{G}} \sum_{o:\,g(o)=g} p_o,\;\; L_E,\;\; \sum_{k} c_k\Bigr),
\end{equation}
where $L_E$ is the longest path through $E$ weighted by $p_o$, plus $h_o$ on the edges that cross the host, and $c_k$ is the CP's own work in command $k$.
Since no schedule on a fixed assignment beats its busiest group's work, the bound measures how far a schedule lies from what that assignment allows, from the probes and the graph alone.

% DECISION: no NP-hardness claim until a reduction is written; with negligible issue cost and one layer's fixed per-chunk pattern the problem has the structure of a two-machine chain-reentrant shop (wang1997reentrant), and with non-negligible issue cost the CP acts as a shared server (glass2000dedicated, hall2000common) (vault ch3-formulation, Relation to classical scheduling).

\subsection{Bounding a Removal}
\label{subsec:removal}

% VALUE: one removal is worth at most the overlap it blocks on typed resources, given every other edge; zero off the longest path; in a loop the maximum cycle mean governs; Amdahl's law for an ordering, from the order and measured durations, not a trace
Removing a false dependence $d$ speeds a phase up by at most $T / (T - O(d))$, where $T$ is the phase's time and $O(d)$ is the time during which $d$ keeps work on disjoint resources from overlapping, given every other edge of the happens-before graph.
The resources are typed, namely the column groups, the CP with its cost at each command boundary, the DRAM read rate up to its cap, and the channels that one group borrows from another's columns, and since none overlaps its own work, $O(d)$ is zero when $d$ lies off the longest path.
In a loop, the maximum cycle mean of the repeating graph determines the time per iteration instead~\citep{ghamarian2006throughput}.
The bound is thus Amdahl's law applied to an ordering, computed from the program and the probes without a timing trace (Section~\ref{sec:related}).

% VALUE: for a set of removals the textbook critical-path condition applies (cited, one sentence, never a finding); we use it as a test that discards sets that cannot pay; on this machine it is necessary, not sufficient (the next longest path; shared capacity); the decode instance is in the evaluation
A set $S$ of removals gains nothing unless it cuts every path or cycle that attains the maximum, because any one left keeps its length, which is the textbook condition that interaction-cost analysis applies to microarchitectural bottlenecks~\citep{fields2003interaction}.
We apply it as a test on the recovered graph with measured costs, which discards each candidate set that leaves such a path or cycle uncut.
On this machine the condition is necessary but not sufficient, because a cut gains only down to the next longest path or cycle.
Moreover, because the groups share the DRAM read cap and the shim tiles' channels, a set that cuts every critical path gains only what that shared capacity leaves.
Section~\ref{subsec:decode-eval} shows both cases in decode attention.

% VALUE: the DRAM cap makes the allowed overlap depend on which operator holds the critical path: a bandwidth-bound GEMM pays a fixed share of its partner's time, attention almost nothing, so two equal operators run together at most 1.81-1.84x faster than in sequence rather than 2.00x; in a prefill the GEMMs are the ones near the cap; the same cap bounds reordering decode's stream
How much overlap the shared read rate allows depends on which operator holds the critical path, as pairs of one attention operator and one GEMM issued in one command on disjoint columns show.
Where the GEMM holds it and reads near the cap, co-running costs the GEMM 8.4--10.5\% of the attention operator's device time, whereas where attention holds it, the cost stays below 15\us{} whatever the GEMM's duration.
Two operators of equal duration therefore run together at most $1.81$--$1.84\times$ faster than in sequence in the first regime, against $2.00\times$ in the second.
In a whole prefill, the GEMMs are the operators near the cap (Appendix~\ref{app:dram-regimes}), and the same cap limits what reordering decode's stream could gain to about $1.13\times$.

% VALUE: the bound is prescriptive (build a removal only where its bound exceeds its cost); since it never falls below one it cannot predict a loss, which the event model prices instead (512-token appends)
A removal is therefore worth building only where its bound exceeds its cost, which for a rename is the local memory, BDs, locks, and channels it takes, and for a reorder the synchronization and planning it adds.
Because the bound never falls below one, it cannot predict a loss.
At 512-token appends, the composed prefill runs at $0.88$--$0.93\times$ the speed of the existing order because of per-command costs that the event model prices and the bound does not see (Appendix~\ref{app:pricing-derivations}).

% VALUE: to choose among schedules without running each, an event simulation of the device, the CP, and the host prices a schedule from measured terms only (eq:cmd; per-command busy with the two overlap regimes; the host program, for the existing program as for ours), and reports device time, host exposure, and the head and tail apart
To choose among schedules without running each, we price a schedule with an event simulation of the device, the CP, and the host, whose every term is measured (Table~\ref{tab:params}).
Queued commands run one at a time (Section~\ref{subsec:semantics}), so command $k$ ends at
\begin{equation}
\label{eq:cmd}
e_k = \max\bigl(e_{k-1} + \epsilon_k,\; q_k + F\bigr) + b_k,
\end{equation}
where $q_k$ is the time the host queues it and the boundary cost $\epsilon_k$ depends on whether commands $k-1$ and $k$ carry attention.
The busy time $b_k$ sums the command's GEMMs with a gap $\gamma$ per additional GEMM.
With attention work $a$ beside GEMM work $g$, it becomes $\max(a, g) + \alpha_r + \beta_r \min(a, g)$, with one line for each regime $r$ of Section~\ref{subsec:removal}, chosen by the longer of the two.
The host pays an issue cost per command and a post-processing cost per operator, and it waits on the oldest command once $D$ are in flight.
The existing program runs through the same simulation as its own host program, so both sides of every comparison are priced alike.
The event model adds the head and tail to the span and reports the device time, the host's exposed time, and the head and tail separately, so an error in one term cannot hide behind another.

% VALUE: only the per-operator busy times depend on the LLM and the split, measured once per configuration by probing each operator alone; the structural and host terms are measured once by microbenchmarks; no constant is fitted to an LLM's end-to-end runs
Only the operators' busy times depend on the LLM and the split, so they are the terms we measure once per configuration, by dispatching each GEMM alone and each attention chunk alone at several cached-context lengths.
Between probed points the event model interpolates, and beyond them it refuses to price.
The structural terms, namely $F$, the boundary costs, $\gamma$, and the overlap lines, are measured once on the platform by microbenchmarks on dummy data, and the host's costs and the head and tail by microbenchmarks at each LLM's dimensions.
No constant is therefore fitted to an LLM's end-to-end runs, and every LLM of Section~\ref{subsec:accuracy} tests the event model rather than supplying its constants.
