\textbf{NPU and AI Engine Compilers.}
% VALUE: compilers and mapping frameworks decide what a design computes and where it runs, and one places a kernel's synchronization while lowering it, with the fewest events; each generates a design from a program, and reconfiguration work serves the modular end of the spectrum, whereas we take fused designs as compiled, closed ones included, and remove false dependences, which cost time even where no synchronization is redundant
MLIR-AIR and IRON compile operators and fused multi-operator designs onto the AIE array~\citep{wang2026mlirair,hunhoff2025iron}, Stream explores layer-fused mappings with memory- and communication-aware cost models~\citep{symons2025stream}, and other work automates the mapping through compilation flows~\citep{zhuang2025aries,danopoulos2025aie4ml} and programming models for dataflow designs~\citep{chen2024allo,fang2025dato}.
AscendNPU-IR inserts a kernel's synchronization as it lowers, pairing sets and waits from a memory-dependence analysis so that the fewest hardware events are used~\citep{ascend-autosync}.
These tools generate a design from a program, and work on reconfiguration reduces the cost that modular designs pay between operators (Section~\ref{subsec:spectrum}), whereas we take fused designs as compiled, closed ones included, and remove the false orders whose removal the condition says can pay, which a count of redundant synchronizations does not find.
% SOURCE: AscendNPU-IR's auto-sync feature, from its own documentation; the fewest-synchronizations contrast answers review MUST 4 (vault paper-cosched-decisions-log, scope wording 2026-10-21). Stream emits one design per fused group on its AIE backend and describes no concurrency across fused groups (vault src-stream-dse, arXiv v2 read 2026-10-14).

\textbf{Operator Scheduling and Concurrency.}
% VALUE: IOS / Nimble overlap operators on GPU streams, scheduled ahead of time; Rammer fixes a spatio-temporal schedule at compile time; Pathways orders an island's computations with a centralized scheduler and dispatches in parallel; LATTICE reorders traced NPU command graphs with a modeled makespan; DynaFlow, XLA's latency-hiding scheduler, and SambaNova schedule or overlap kernels from a program; all construct a schedule, whereas on XDNA 2 the schedule already exists as the CP's order in compiled binaries, closed ones included, and we price which false orders to remove per prompt length
IOS and Nimble run independent operators concurrently on GPU streams~\citep{ding2021ios,kwon2020nimble}, Rammer fixes a spatio-temporal schedule of a DNN's operators at compile time~\citep{ma2020rammer}, and Pathways orders all computations on an island of accelerators through a centralized scheduler~\citep{barham2022pathways}.
% SOURCE: Pathways §4.4 "a centralized scheduler per island that consistently orders all of the computations in the island"; §4.5 "parallel asynchronous dispatch ... exploits the statically known resource usage of regular compiled functions to run most of the host-side work for a computation's nodes in parallel" (arXiv 2203.12533v1 full text, workspace tmp/mlsysaw/Pathways.txt, read 2026-10-23).
DietCode generates tensor programs from which its runtime selects one per input shape, within each operator~\E{cite: DietCode (MLSys'22)}.
LATTICE reorders NPU command graphs taken from traces jointly with memory planning and reports a modeled makespan~\citep{liu2026lattice}.
DynaFlow decouples an LLM's operators from their execution schedule through a programmable scheduling interface, XLA's latency-hiding scheduler orders operations from profiled latencies, and SambaNova's compiler overlaps work across kernel calls~\E{cite: DynaFlow; XLA LHS with PGLE; SambaNova (MLSys'26)}.
Unlike these systems, which construct a schedule from a program or a traced graph, we start from the schedule that already exists as the command processor's order in compiled binaries, closed ones included, and price which of its false orders to remove per prompt length.
% SOURCE: LATTICE (arXiv 2607.17422v3, abstract read 2026-10-22): three stages, the last recovering pipeline parallelism; six command traces from a DaVinci NPU; reports peak memory, extra DDR traffic, spill count and modeled makespan (vault src-lattice).

\textbf{Binary Analysis and Rewriting.}
% VALUE: analysis and rewriting after compilation exist for CPUs and GPUs (Kotha et al. analyse binaries; BOLT lays out code from profiles; CuAsmRL reorders a compiled GPU kernel's schedule by a measured search); each works on one processor's instruction stream, whereas we analyse and rewrite the command streams that coordinate several kinds of engines, with legality decided from every agent's access sets
Analysis and rewriting after compilation are established for CPUs and GPUs, where binaries are analysed and parallelized without their source, code layout is optimized from profiles, and a compiled GPU kernel's instruction schedule is reordered by a search over measured candidates~\E{cite: Kotha et al. (MICRO'10); BOLT; CuAsmRL (CGO'25)}.
Each of these works on one processor's instruction stream, whereas we analyse and rewrite the command streams that coordinate several kinds of engines, and decide legality from the access sets of every agent that touches state.

\textbf{Performance Analysis and Models.}
% VALUE: what-if tools take order and durations from traces and simulate transformed graphs; GPA attributes stalls inside a kernel; interaction cost prices a set of events together; analytical and SDF models predict or bound time from a given mapping or graph; here the program fixes the order, only durations are measured, and the quantity bounded is what removing one wait is worth
To predict what an optimization gains, Daydream and dPRO build dependency graphs from run-time traces and simulate the transformed graphs~\citep{zhu2020daydream,hu2022dpro}, and xPU-Shark replays production traces in a microarchitecture simulator~\citep{zarkadas2025xpushark}.
GPA attributes GPU instruction stalls within a kernel and estimates each fix's speedup~\citep{zhou2021gpa}, interaction-cost analysis costs a set of events together~\citep{fields2003interaction}, and analytical and SDF models predict or bound time from a given mapping or graph~\citep{parashar2019timeloop,kwon2019maestro,ghamarian2006throughput}.
In contrast, the NPU's program fixes the order between its engines, so only durations are measured, and the quantity we bound is what removing one wait is worth before it is rewritten, while our event model prices the orders and splits a compiled design could take, per prompt length, from each operator's time alone.

\textbf{LLM Inference on Edge Accelerators.}
% VALUE: edge LLM work offloads phases, schedules across an SoC's processors, or hand-tunes kernels and buffering; GPU serving partitions or overlaps prefill and decode across devices, batches, or one kernel; here one request's prefill and decode take turns on one array whose kernels are already tuned
On mobile NPUs, llm.npu offloads prefill through chunked static graphs~\citep{xu2025llmnpu}, and HeteroMosaic and Agent.xpu schedule LLM work across an SoC's processors~\citep{jun2026heteromosaic,wei2025agentxpu}.
On XDNA~2, FastFlowLM runs many LLM families with its own runtime~\citep{fastflowlm-repo}, its authors' Gemma3 mapping double-buffers decode attention's keys and values~\citep{du2026gemma3}, and a FlashAttention case study maps the fused kernel by hand~\citep{wang2026flashattention}.
GPU serving systems run prefill and decode on separate GPUs~\citep{zhong2024distserve,patel2024splitwise}, mix prefill chunks into decode batches~\citep{agrawal2024sarathi}, or run both attentions in one kernel~\citep{kamath2025pod}, and NanoFlow overlaps operations within one GPU through nano-batches~\citep{zhu2025nanoflow}, whereas on a client NPU one request's prefill and decode take turns on one array under kernels that OPCORD leaves unchanged.

\textbf{GPU Streams and Statically Ordered Machines.}
% VALUE: the closest prior instance of the same false dependence: before Kepler, streams shared one compute queue, a blocked operation blocked other streams, and breadth-first issue was the remedy, until Hyper-Q's hardware queues removed it; the TSP and ReGate leave timing or idleness to the compiler; XDNA 2 sits between, its program fixing each engine's order but not its duration, so the remedy must be written into one in-order stream; the transfer point, stated as a possibility: where one in-order issuer feeds spatially partitioned engines, issue order may need to be emitted and priced per input size
Before Kepler, a GPU's kernels from every stream shared one compute queue, so a blocked operation blocked later operations of other streams, and issuing work breadth first across streams was the recommended remedy~\citep{rennich2012streams}.
Kepler's Hyper-Q then added hardware queues that remove these false dependences among streams~\citep{nvidia-kepler-tuning}.
At the other extreme, Groq's TSP lets its compiler determine when every instruction executes~\citep{abts2020tsp}, and ReGate's compiler manages an NPU's idle periods to power-gate its units~\citep{xue2025regate}.
XDNA~2 sits between them, since its program fixes the order of each engine's work but not its duration, so with one in-order command processor per hardware context the breadth-first remedy must be written into one instruction stream.
Other accelerators in which one in-order issuer feeds spatially partitioned engines may face the same choice, and there the order of issue may likewise need to be emitted and priced per input size rather than fixed.
% SOURCE: Rennich 2012 webinar (read 2026-10-22): "Fermi hardware has 3 queues: 1 Compute Engine queue, 2 Copy Engine queues"; "a blocked operation blocks all other operations in the queue, even in other streams"; "issue order matters! Issue depth first / Issue breadth first". Kepler Tuning Guide section 1.4.2.2 "Hyper-Q" (read 2026-10-21): "removes the false dependencies that can be introduced among CUDA streams in cases of suboptimal kernel launch or memory copy ordering across streams in Fermi or GK104".
