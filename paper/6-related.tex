\textbf{Operator Scheduling and Concurrency.}
\CLS{D}IOS and Nimble run independent operators concurrently on GPU streams~\citep{ding2021ios,kwon2020nimble}, and IOS fits a schedule to each batch size by measuring candidate stages on the device.
\CLS{D}LATTICE reorders NPU command graphs from traces~\citep{liu2026lattice}, taking their dependences as given.
\CLS{D}Unlike these systems, which construct a schedule from a program or a traced graph, OPCORD starts from the one that the CP's order in compiled binaries already fixes, closed ones included, and derives there the dependences that keep operators on disjoint column groups of one array from running at once.
\CLS{D}In open designs, it chooses that order with the configuration per prompt length, pricing every candidate and measuring only near ties.

\textbf{GPU Work Queues.}
\CLS{D}On Fermi GPUs, one hardware work queue placed the order dependences of Section~\ref{sec:background} between streams, and kernels of different streams ran at once when issued breadth first~\citep{rennich2012streams}, as our composer issues them (Section~\ref{subsec:order}).
\CLS{D}XDNA~2's program fixes the order of each engine's work but not its duration, and because each hardware context has one in-order CP and a second context shares the whole array in time, the breadth-first order must be written into one instruction stream.
