\section{Introduction}
\label{sec:intro}

Neural processing units (NPUs) such as the AMD XDNA~2 bring large language model (LLM) inference, and the agents built on it, to client machines~\citep{rico2024xdna,linux-amdnpu}.
Such an NPU is now standard equipment, because a platform requirement of 40 trillion operations per second put one into mainstream laptops~\citep{copilotplus-reqs}.
% SOURCE: the Copilot+ PC hardware requirement of 40+ TOPS for the NPU (copilotplus-reqs).
It runs each operator of an LLM on a group of columns of a spatial array, and one in-order command processor (CP) issues the work of every group.
In the expert prefill that MLIR-AIR builds for Llama-3.2-1B~\citep{wang2026mlirair}, which we call the \emph{existing program}, attention's columns and the columns of the matrix multiplications (GEMMs) take turns, although neither consumes the other's current work, and they still take turns after attention's own two columns are alternated by hand (Figure~\ref{fig:timeline}, top).
The measure a developer can compute, which divides the operators' summed time by the wall time, still reads the device as busy for 92--97\% of the time to first token (TTFT).
% SOURCE: busy 92-97% of TTFT at 512 / 2,048 / 4,096 tokens, each operator's isolated time less the dispatch floor, summed over the prefill (amd-npu e3acc8a prefill-e2/decomp.txt; Section 3, Figure busy).
Issued in another order, the same operators run together and reach the first token $1.45\times$ sooner (Figure~\ref{fig:timeline}, bottom).
% SOURCE: Figure 1 data, figs/data/fig1-intervals-1b.json (cell scratch:0:4096): the existing program with attention's columns alternated, TTFT 1,625.5 ms (median run of 5), against the composed schedule, 1,118.2 ms, 1.454x; both on the two-column split; work outstanding on both groups 0 of 1,625.5 ms against 523.2 of 1,118.2 ms, from the exact intervals (amd-npu 57621ff4; vault lab-split-sweep (18)).
However, while compilers and mapping frameworks~\citep{hunhoff2025iron,symons2025stream} optimize what each operator computes and where it runs, how operators are composed and issued through the CP has received far less attention.

% VALUE: (2) the obvious fixes recover nothing: packing operators into one command creates no overlap on an in-order CP; a second hardware context shares the array in time; alternating attention's columns by hand removes one wait inside that operator and leaves the groups taking turns; in decode, attention's loop keeps one buffer per role and MLIR-AIR's double buffering declines it; each fix is sound locally, the waits come from how the whole program orders and names its work
% DECISION: packing several operators per command is cited as standard practice (batching), never presented as ours.
None of the fixes a developer would reach for first recovers this overlap.
Packing several operators into one command, as CUDA Graphs~\citep{nvidia-cudagraphs} and XRT's run lists~\citep{xrt-repo} do, amortizes launch cost but creates no overlap, because a synchronization on one column group delays every later issue, whichever group it feeds.
A second hardware context does not help either, since the driver gives every context the whole array and co-resident contexts share it in time~\citep{xdna-driver}.
% SOURCE: packing neutral and queued commands non-overlapping, 1.007-1.029 (vault lab-prefill-overlap (5)(b)); every hardware context is allocated all eight columns per the driver's source, and a one-column design on two contexts takes 1.97x one alone (Section 3).
Alternating attention's two columns by hand removes a wait inside that one operator, but the column groups still take turns.
The same kind of wait recurs in decode, where attention's loop keeps one buffer each for a block's keys, values, and scores, so each block's transfer waits for the compute on the previous block.
MLIR-AIR's double-buffering pass declines that loop, correctly for what it sees, because the loop's running maximum and accumulator live across blocks.
% SOURCE: the declining transformation is the build's own comment on air-label-scf-for-to-ping-pong (vault lab-decode-long-context (5)).
Each fix is sound for the part of the program it sees, whereas the waits come from how the whole program orders and names its work.

% DECISION: the lead insight is that the CP's instruction order is the array's schedule, fixed in the emitted streams; "rationed by false dependences" is its consequence. The dependence classes, reordering and renaming are cited, never claimed.
The insight of this work is that the CP's instruction order is the array's schedule, and that a toolchain fixes this order in the instruction streams it emits.
Once configured, the array computes data-driven and no hardware or runtime scheduler reorders work across its engines, so every wait in a design, and every column a wait holds idle, can be read from those streams.
The waits above are textbook order and name dependences~\citep{bernstein1966analysis,kuck1981dependence}, in which work waits on other work whose results it does not consume.
The hardware therefore provides the concurrency, and these false dependences ration it, in the CP's stream and inside an operator's loop.
Pathways~\citep{barham2022pathways} orders the computations of an island of accelerators through a centralized scheduler at run time, whereas this device has none, so the order must be written into the instruction stream itself.
% SOURCE: Pathways §4.4 "The PATHWAYS runtime includes a centralized scheduler per island that consistently orders all of the computations in the island" (arXiv 2203.12533v1, read 2026-10-23).
IOS~\citep{ding2021ios} and Rammer~\citep{ma2020rammer} schedule operators at compile time from the program they are given, whereas we start from binaries a toolchain has already emitted, closed ones included.

% VALUE: (4) this work, one step per contribution with its result: recover and class the waits from three toolchains, legality from the streams alone; price candidates from per-operator timings with an event model and a bound, which picks the faster split; OPCORD rewrites legally, the composer's cross-group reorder is the source of the prefill gains and no existing design performs it, the passes automate the expert edits inside the compiler; headline results against the fastest existing schedule measured
In this work, we schedule a compiled design from the instruction streams its toolchain has already emitted.
First, we recover the CP's order from the streams of three toolchains, open and closed, class each wait as a true, name, or order dependence, and decide from the streams alone which reorders and renames are legal.
Second, we price a candidate schedule from timings of each operator run alone, with an event model and a lower bound, so that the split of columns between attention and the GEMMs and the order of issue are chosen without running the candidates.
The event model names the faster split in all 36 cases we test and predicts TTFT with a median error of 2.2\%.
% SOURCE: split choices 36 / 36, median |TTFT error| 2.146% over the append cells of Llama-3.2-1B, Qwen3-4B, Gemma3-4B and Llama-3.1-8B (amd-npu 78ec55b7 score-2026-10-21.json; Section 7, Model Accuracy).
Third, OPCORD rewrites compiled designs with these choices, under checkers that refuse any rewrite they cannot show legal, with kernels, driver, and firmware unchanged.
Its composer issues every column group's work before the CP waits on any of it, and this reorder across groups, which no hand-written or shipped design performs, is the source of the prefill gains.
Two MLIR-AIE passes automate inside the compiler what experts do by hand, reordering issue within an operator and renaming decode attention's buffers into rings, so that each block's transfer overlaps the previous block's compute.
Against the fastest existing schedule we measured for each design, OPCORD shortens TTFT across five LLMs by $1.14$--$1.46\times$ from scratch and $1.19$--$1.51\times$ on appends to a cached context, decode by $1.16$--$1.27\times$ at a 16K-token context, and a whole agent turn by $1.15$--$1.32\times$, with bit-identical outputs.

In summary, the primary contributions of this work are as follows:
\begin{itemize}
    \item A method for scheduling a spatial array from the instruction streams its toolchain has already emitted, which recovers the command processor's order as the array's schedule, classes each wait by its textbook dependence, and decides from the streams alone whether a reorder or a rename is legal.
    \item An event model and lower bound that price a schedule, the split of columns, and the removal of a dependence from timings of each operator alone, before the schedule runs.
    \item The design and implementation of OPCORD, a composer and two MLIR-AIE passes that remove false dependences from compiled designs with the kernels, driver, and firmware unchanged.
\end{itemize}
