\section{Introduction}
\label{sec:intro}

% VALUE: (1) context. Client NPUs run LLMs as compositions of per-operator designs on a spatial array, issued by one in-order CP; kernels and mappings are well served; the expert designs still leave columns idle in prefill and read KV at half rate in decode; gap: how the composition is issued has received far less attention
Neural processing units (NPUs) such as the AMD XDNA~2 in Ryzen\texttrademark{} AI processors bring large language model (LLM) inference to client machines~\citep{rico2024xdna}.
Such an NPU is now standard equipment rather than a specialist part, because a platform requirement of at least 40 trillion operations per second put one into mainstream laptops, and this array delivers 50.
% VERIFY: cite Microsoft's Copilot+ NPU requirement of at least 40 TOPS and AMD's 50 TOPS for XDNA 2; sources read 2026-10-21 (windowscentral.com/hardware/laptops/amd-ryzen-ai-300-announce; pcworld.com/article/2353351); add the bib entries and the \citep before submission.
So a loss in how these machines are programmed is paid on a large installed base, and the toolchains that program them are open.
Their AI Engine array is spatial, so each operator of a model runs on its own group of columns, and the host composes the operators' work into a sequence of commands that a single in-order command processor (CP) executes~\citep{rico2024xdna,linux-amdnpu}.
Compilers and mapping frameworks already map single operators and fused groups onto the array~\citep{wang2026mlirair,hunhoff2025iron,symons2025stream}, and expert end-to-end designs exist for prefill and decode~\citep{wang2026mlirair,fastflowlm-repo}.
Yet these expert designs leave much of the array idle, and nothing a developer can measure on the device says so.
In MLIR-AIR's prefill of Llama-3.2-1B, the device is busy for over 90\% of the time-to-first-token (TTFT), but attention and the matrix multiplications (GEMMs) run on disjoint columns that take turns, and attention's share of TTFT grows from 12\% to 49\% between 512 and 4{,}096 tokens.
In decode, long-context attention reads its key-value (KV) cache at half the DRAM read rate that the platform sustains.
However, while prior work has optimized what each operator computes and where it runs, how the operators are composed and issued through the command processor has received far less attention.
This paper's subject is that composition: what it costs, why the loss went unnoticed, and what removing it recovers.
% VALUE: the four reasons the loss survived, which is the paper's lead contribution: no occupancy metric exists, the computable one reads busy, a partial fix measures no change, and a shipped compiler pass declines the one in decode on a correct local ground
The loss survived for four reasons, each of which we measure.
No counter on this device reports what any column is doing, and the instrument we build to look, timing instructions inserted into the command stream, reports what the command processor observes rather than what a column computes, so column occupancy here can be bounded and not measured.
The quantity a developer can compute, summed operator time over wall time, reads 92--97\% of TTFT.
Removing part of such a loss changes nothing measurable, so a search that keeps only the changes that help by themselves stops at the first attempt.
And where several of these waits sit on one cycle, a transformation already in the compiler declines them for a correct local reason: MLIR-AIR's double-buffering pass leaves decode attention single-buffered because its running maximum and accumulator live across blocks, and \E{1.39$\times$} stays on the floor.
Tuning the array's partition first does not lead here either, since the split that is fastest for the shipped program is not the one the reordered program wants at three of the configurations we measure, although the two agree once the shipped program's own attention columns are interleaved by hand.
This matters more on a client part than in a datacentre: with a prefix cached, prefill is 1.4--9.0\% of an agent's LLM time on a server, against \E{6--54\%} of a turn here~\citep{yuan2026agentic,zhu2026tracelab}.

Expert designs fix the split of the array by hand and issue one operator per command, so the column groups execute one after another (Figure~\ref{fig:order}a).
Packing several operators into one dispatch is standard practice for amortizing launch overhead, as in CUDA Graphs~\citep{nvidia-cudagraphs} and XRT's run lists~\citep{xrt-repo}.
On an in-order CP, however, packing alone creates no overlap, because a synchronization on one group delays the issue of every later instruction, whichever group it feeds (Figure~\ref{fig:order}b).
The same delay occurs inside a single operator, where the existing attention stream waits on one column before it starts the other, and inside decode attention, whose single-buffered loop makes each transfer of the KV cache wait for the compute on the previous block.
Each of these waits is a false dependence: work waits on other work whose results it does not consume.
Furthermore, the split that suits a short prompt computed from scratch does not suit a long prompt appended to a cached context, as in an agent's turn, so one hand-fixed split leaves part of the array idle in one regime or the other.

% VALUE: (3) this work: remove the false dependences on compiled designs, below the compiler, by reordering issue across operators, renaming buffers, and partitioning per regime, with legality derived from the instructions; each with its headline number (robust ones stated, the rest placeholders until the freeze); combined result on agent turns stated plainly
In this work, we treat the CP's instruction stream as the schedule of the spatial array and remove the false dependences of an existing design below its compiler, with no change to its kernels or driver.
First, our composer reorders issue: it issues every group's work before the CP waits on any group and places each synchronization at its predicted completion, so that disjoint column groups run concurrently (Figure~\ref{fig:order}c).
Against the existing host program with its attention columns already alternated, and with each side on its own faster split, the composed schedule lowers TTFT by 1.14--1.46$\times$ for prompts computed from scratch and by 1.33--1.49$\times$ for appends to a cached context on three dense models, and by 1.17--1.29$\times$ on Gemma3, whose most layers attend within a local window, with bit-identical outputs.
Second, the composer renames buffers into rings sized from its plan, so that operators of several chunks overlap, and our loop pass applies the same rule inside decode attention, which lowers the time per decoded token at a 16{,}384-token context by 1.27$\times$ on Llama-3.2-1B and 1.16$\times$ on Qwen3-4B, and by up to 1.39$\times$ at longer contexts, close to the rate of this design's KV transfer alone on both models.
Against FastFlowLM, the production engine for this device, which serves the same models from the same quantized weights, the composed schedule lowers TTFT by 1.31--1.86$\times$ across three models and both regimes, while the existing program our passes rewrite takes between 0.67 and 1.11 times that engine's time.
Third, the composer chooses the split of columns between attention and the GEMMs for each regime, which favors two attention columns for prompts computed from scratch and four for appends to a long context.
On the same append, the four-column split lowers the time of the composed schedule by a further 1.9$\times$ on both models, and suspending one resident split to resume the other takes 7--8~ms, 0.2\% of a 4{,}096-token append on Qwen3-4B, before any move of the cached context.
\E{Together, these shorten a whole agent turn, a tool output of 512--4{,}096 tokens appended to a 16{,}384-token context and 250 decoded tokens, by 1.15--1.32$\times$ against the faster existing split on two models, and by 1.28--1.50$\times$ against the existing default at the traces' median tool output. At such steps decode is most of the turn, so renaming in decode carries the gain, and reordering issue adds 1.09--1.10$\times$ only for tool outputs of 4{,}096 tokens.}

% VALUE: (4) insight: concurrency is free in the hardware but rationed by one in-order CP whose instruction order is the schedule; a consequence is that the losses are invisible one change at a time, so the set to remove must be identified from the graph; the model takes per-operator probes and a schedule and returns its TTFT, with its accuracy, its split choices, and the distance to a lower bound
The insight behind these results is that concurrency on a spatial array is free in the hardware but rationed by one in-order command processor.
A consequence decides how such a loss can be found at all: because several of these waits can lie on one critical path or cycle, removing any proper subset of them leaves the time unchanged, so measuring one change at a time reports nothing and the set must be identified from the dependence graph instead.
Commands queued on one hardware context never overlap, whereas one command that issues two groups' work before it waits on either runs them in 1.00--1.06$\times$ the time of the longer one.
The CP's instruction order is therefore the schedule, and its cost can be computed before anything runs.
We capture it in an event model that takes each operator's device time, measured once per configuration, and a candidate schedule, and returns the schedule's TTFT.
The model picks the faster split in all 16 configurations of the two models it was built on and, with its rule fixed before the runs, in all 16 of two further models, at a median error of 1.3--1.5\% and at most 7.5\%.
Once the order is right, the binding term of a lower bound computed from the same probes is a column group's busy time rather than the CP, and the composer lies within 1.09--1.30$\times$ of that bound.
Because the order is fixed in the program, we also read it from the compiled instruction streams of open and closed stacks, attribute each wait to its textbook dependence class, and bound what removing the wait is worth before the removal is measured.

In summary, the primary contributions of this work are as follows:
\begin{itemize}
    \item The finding that these losses are not reachable one transformation at a time: where several false dependences lie on the same critical path or cycle, removing a proper subset leaves the time unchanged, which is why MLIR-AIR's own double-buffering transformation declines decode's attention loop on a correct local ground and leaves \E{1.39$\times$} on the floor.
    \item What a pass must establish before it may rewrite the schedule of a binary it did not produce: legality conditions over buffer ranges, lock protocols, descriptor reuse, and the routes a group borrows, each checkable from the design's own instructions, together with the dependence structure they are checked against, recovered from the instruction stream and round-tripped byte for byte on 593 streams of three toolchains.
    \item Passes that remove each class of these dependences, two of them inside the open-source compiler, evaluated end to end for edge LLM inference from prefill and cached appends to decode and whole agent turns, each against the same stack without the removals, against its per-phase floor, and beside the production engine.
    \item The price of removing them on this machine: the memory a buffer ring costs, the bandwidth that concurrency costs with its ceiling of $1.84\times$ against an ideal $2.00\times$, the queue depth that trades dispatch cost against readiness, the column split that must follow the workload, and the two regimes in which removal does not pay.
\end{itemize}
Our passes and their legality checkers implement these removals, and the two that run inside MLIR-AIE are upstream, so every design that compiler builds can take them, including designs we never examined.
The composer replaces only the dispatch loop of a design's host program and builds every split from the design's unchanged source, and our loop pass runs as an opt-in step inside the existing compiler, so both keep the kernels, driver, and firmware unchanged.
