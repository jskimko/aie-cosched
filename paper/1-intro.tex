\section{Introduction}
\label{sec:intro}

% VALUE: (1) stakes and symptom: client NPUs are standard equipment and run LLMs; a spatial dataflow NPU runs each operator's flow on a group of tiles while one in-order CP issues every group's work, so the order in the compiled dispatches is the schedule the array runs; in the original prefill the groups take turns while the measure a developer can compute reads busy; issued in another order the same operators run together (Figure 1); gap: issue order through the CP has received far less attention than what each operator computes and where
% DECISION: the symptom is "the measure a developer can compute reads 92-97% busy", never "invisible to every metric".
Neural processing units (NPUs) such as those in AMD Ryzen\texttrademark{} AI processors bring large language model (LLM) inference to client machines~\citep{rico2024xdna}, and Microsoft's Copilot+ PCs require an NPU of at least 40 trillion operations per second~\citep{copilotplus-reqs}.
% SOURCE: the Copilot+ PC hardware requirement of 40+ TOPS for the NPU (copilotplus-reqs).
AMD's XDNA~2 NPU is a spatial dataflow array, on which a design runs each LLM operator as a flow on its own group of tiles, laid out in today's designs as whole columns, which we call a column group.
Yet one in-order command processor (CP) issues the work of every group, so the order of issues and waits compiled into the dispatches is the schedule that the array runs.
In the fused prefill of MLIR-AIR (AIR)~\citep{wang2026mlirair}, attention's columns and those of the matrix multiplications (GEMMs) take turns (Figure~\ref{fig:timeline}, top, for Llama-3.2-1B), although attention on one 128-token chunk neither feeds nor reads the GEMMs of later chunks.
We call this design with its host program the \emph{original program}.
The measure a developer can compute, which divides the operators' summed time by the wall time, still reads the device as busy for 92--97\% of the time to first token (TTFT).
% SOURCE: busy 92-97% of TTFT at 512 / 2,048 / 4,096 tokens, each operator's isolated time less the dispatch floor, summed over the prefill (amd-npu e3acc8a prefill-e2/decomp.txt; Section 3.2).
Issued in another order on the same columns, the same operators run together and reach the first token \FigOneGain$\times$ sooner (Figure~\ref{fig:timeline}, bottom).
Compilers and mapping frameworks~\citep{hunhoff2025iron,symons2025stream} optimize what each operator computes and where it runs, and the toolchains we study lower the host program's order of issue as it is written.
The insight of this work is that the CP's instruction order is the array's schedule, fixed in the artifact that a toolchain emits.
Every wait in a design can therefore be read from that artifact, together with the columns it holds idle and whether removing it could free overlap, so the waits that leave the array idle can be bounded and removed after compilation.

% VALUE: (2) why the waits exist and why they persist: developers trade modular designs (one operator per configuration, reconfiguration between operators) for fused ones (several operators in one configuration), which avoid reconfiguration but inherit an operator-at-a-time order; that order is fixed when the design and its host program are written, and the toolchain's lowering keeps it; the obvious fixes recover nothing (packing, a second hardware context); unlike GPUs, whose hardware queues removed such waits (the precedent itself in Related Work), this NPU has one in-order CP per context, so the order must be rewritten in the stream; a closed production stack's released designs likewise drive each column group from its own dispatches, but over the whole prompt, so their turns are true (pass-0, aa4df07, 232dafe)
% DECISION: packing several operators per command is cited as standard practice (batching), never presented as ours. No claim about how FastFlowLM chose its order; it is described by what it ships.
Modular designs give each operator its own configuration and pay to reconfigure the array between operators.
Fused designs such as this one keep several operators resident in one configuration and so avoid that cost, but they inherit an order of issue fixed when the design and its host program are written.
Packing operators into one dispatch, as CUDA Graphs~\citep{nvidia-cudagraphs} and XRT's run lists~\citep{xrt-repo} do, amortizes launch cost but recovers none of the lost overlap, because a wait on one group delays every later issue.
Nor does a second hardware context, which shares the whole array in time~\citep{xdna-driver}.
% SOURCE: packing neutral and queued commands non-overlapping, 1.007-1.029 (vault lab-prefill-overlap (5)(b)); every hardware context is allocated all eight columns per the driver's source, and a one-column design on two contexts takes 1.97x one alone (Section 3).
Unlike GPUs, whose hardware queues removed this kind of wait (Section~\ref{sec:related}), this NPU has one in-order CP per hardware context, so the order must be rewritten in the stream itself.
% SOURCE: FastFlowLM's flash prefill issues each command to one column group, 84-85% of W in single-group commands, one all-column command at 0.4-0.5% (aie-cosched aa4df07, passes/flm_command_cut.py, results/2026-10-25-flm-command-cut); in-command bound 1.000x with 82-87% exposure (terms4, rows 3c70af2; exposure a3ef131); the lowering preserves the program's order (mlir-air AIRRtToNpuPass.cpp; fused_prefill device.py preserve_shim_dma_order).

% VALUE: (3) the insight and the characterization: the CP's order is the array's schedule, fixed in the artifact, so every wait can be read from it; the waits are textbook false dependences and removing those on the critical path is the textbook remedy (cited); what this platform adds is when removal pays (overlap on resources a rewrite cannot duplicate, with no true dependence, including through the host) and that the design's cut and the prompt length set how much, so the order that pays changes with length and must be priced
% DECISION: false dependences, their classes, reordering and renaming are textbook and cited; the claim is the condition on this platform and its dependence on the cut and the shape, never "false dependences cost time".
The waits above are textbook order dependences, and decode attention's loop, which keeps one buffer per role, adds textbook name dependences~\citep{bernstein1966analysis,kuck1981dependence}.
Both kinds are false dependences (Section~\ref{subsec:losses}), and removing one can save time only if it lies on the critical path~\citep{fields2003interaction}.
What this platform adds is when removing one frees overlap, which happens only where two clauses hold.
The first is that the work it frees runs on core tiles and DMA channels that the work it waited on does not use, which are resources a rewrite cannot duplicate.
The second is that no true dependence, on the device or through the host, lies between the two.
Both clauses name resources and dependences that the artifacts and the host's accesses establish, so they can be decided before any duration is measured.

How a design cuts its work into configurations, dispatches, and buffers, and the length of the prompt, set how much work meets this condition.
In the current releases of a closed production stack, FastFlowLM (FLM)~\citep{fastflowlm-repo}, the per-operator engine that runs our five LLMs gives each operator its own configuration of nearly the whole array, so consecutive operators share their columns.
Its flash designs run each layer's attention once over the whole prompt, so every GEMM feeds or reads it.

% VALUE: why the order must be priced per prompt length: the original program's chunks make the balance between the groups move with the prompt, and the split moves with it
The original program, by contrast, runs fixed-size chunks, in which attention's work grows with the chunk's position while the GEMMs' work stays fixed.
The balance between the groups therefore shifts with the prompt length, and with it whether the overlap repays a new order's per-dispatch costs.
The issue order that pays therefore changes with the prompt and must be priced per length rather than fixed, as must the configuration, whose split of the columns between attention and the GEMMs moves with the same balance because more attention columns shorten attention but lengthen every GEMM.

In this work, we build OPCORD, which removes from compiled designs the false dependences whose removal pays.
Designs from open compilers such as AIR and IRON, on which researchers and industry build independently, inherit the order their toolchain emits, so OPCORD serves this common path rather than one stack, in today's designs and in each design a toolchain emits later.
A team that holds a closed stack's source can recover that loss in its own designs the same way.
First, because the order sits in binaries whose source may be closed, its analysis reads a design's artifacts as a dependence graph over every agent that touches state, accepts a reorder or a rename only where the artifacts and the host's accesses show it legal, and bounds what removing each false dependence can gain.
On a closed stack's binaries, OPCORD stops at the analysis and replays only rewrites that leave the host program unchanged, to check a bound against measurement.
Second, because the artifact fixes the order of the work but not its durations, an analytical event model, with constants measured once by microbenchmarks, prices each candidate order and configuration per prompt length from timings of each operator run alone.
When two candidates are priced close, OPCORD can settle the choice by a short measurement while it plans the prompt length.
Third, a composer reorders issue across dispatches, a stream pass within one operator's stream, and a loop pass renames decode attention's buffers into rings.
Because OPCORD rewrites designs it did not compile, each stands behind a checker that refuses any rewrite it cannot show legal, with kernels, driver, and firmware unchanged.

% VALUE: the evidence in brief: headline gains against the baseline, the absolute standing, choice quality, exactness and legality, and the condition's scope across the census
Against the original program on its fastest supported configuration that we measure, OPCORD shortens TTFT across five LLMs by \PrefillGainLo--\PrefillGainHi$\times$ at prompts of 1K to 32K tokens, with bit-identical outputs.
Against the unmodified decode design, its loop pass shortens decode by \DecodeGainLo--\DecodeGainHi$\times$ at contexts of about 30K tokens, again with bit-identical outputs.
On AIR's designs, OPCORD also reaches the first token sooner than FLM's current release, on every LLM and prompt length we compare.
Its choice of order and configuration stays within \ChoiceOpcordMax\% of the measured minimum on every LLM and prompt length it prices, whereas each fixed rule we test loses \ChoiceAlwaysMax--\ChoiceFourSTwoMax\% on some of them.
Its analysis re-emits every stream we read from three stacks byte for byte, and its checkers refuse every illegal rewrite we inject.
Across the designs we read, every overlap gain we measure falls where the condition says one can arise, and FLM's two prefill engines leave little overlap to recover, as the condition predicts.

In summary, the primary contributions of this work are as follows:
\begin{itemize}
    \item We show that on a spatial NPU whose work one in-order command processor issues, the order compiled into a design's artifacts is the array's schedule: fused designs serialize independent work through that order and their buffers, the usual remedies of packing dispatches and adding a hardware context recover none of it, and how much rescheduling can recover is set by how a design cuts its work and by the prompt length, as a condition checkable from the artifacts predicts.
    \item We develop an analysis that reads compiled NPU programs, closed ones included, as dependence graphs over every agent that touches state, accepts a reorder or a rename only where the artifact and the host's accesses show it legal, and bounds what each false dependence can recover.
    \item We design and implement OPCORD, a post-compilation rescheduler that, building on this analysis, rewrites issue order and buffers behind legality checkers and chooses the order and the configuration per prompt length with an analytical event model, leaving kernels, driver, and firmware unchanged.
\end{itemize}
