Neural processing units (NPUs) such as the AMD XDNA~2 bring large language model (LLM) inference to client machines, on a spatial array of AI Engine columns whose work one in-order command processor (CP) issues~\citep{rico2024xdna,linux-amdnpu}.
Such an NPU is now standard equipment rather than a specialist part, because a platform requirement of at least 40 trillion operations per second put one into mainstream laptops~\citep{copilotplus-reqs}.
A loss in how these machines are programmed is therefore paid on a large installed base.
% SOURCE: the Copilot+ PC hardware requirement of 40+ TOPS for the NPU (copilotplus-reqs).
Each operator of an LLM runs on a group of columns, and the host composes the operators' work into commands whose instruction streams the CP executes in order.
The expert prefill that MLIR-AIR builds for Llama-3.2-1B~\citep{wang2026mlirair}, which we call the \emph{existing program}, issues each operator as its own command, so its attention columns and the columns of its matrix multiplications (GEMMs) take turns, although neither consumes the other's current work.
The groups still take turns in what we call the \emph{alternated baseline}, which is the existing program with attention's two columns alternated by hand, run on whichever division of the columns between attention and the GEMMs, or \emph{split}, is faster (Figure~\ref{fig:timeline}, top).
The measure a developer can compute, which divides the operators' summed time by the wall time, still reads the device as busy for 92--97\% of the time to first token (TTFT), and the runtime reports nothing about what any column is doing.
% SOURCE: busy 92-97% of TTFT at 512 / 2,048 / 4,096 tokens, each operator's isolated time less the dispatch floor, summed over the prefill (amd-npu e3acc8a prefill-e2/decomp.txt; Section 3, Figure busy). No per-column report: xrt-smi reports "Estimated Power : N/A" and has no telemetry report on this device (XRT 2.25.0, examined 2026-10-21; vault lab-decode-long-context (39), lab-metric-fields (1)).
Issued in another order, the same operators run together and reach the first token $1.45\times$ sooner than in the alternated baseline (Figure~\ref{fig:timeline}, bottom).
% SOURCE: Figure 1 data, figs/data/fig1-intervals-1b.json (hold-2/1b-R, cell scratch:0:4096, record timers at 1,800 MHz): the existing program with attention's columns alternated, TTFT 1,625.5 ms (median run of 5), against the composed schedule, 1,118.2 ms, 1.454x; both on the two-column split (amd-npu 57621ff4; vault lab-decode-long-context (41)). The same cell's split-sweep ratio is 1.45 (vault lab-split-sweep (18)).
However, while compilers and mapping frameworks~\citep{hunhoff2025iron,symons2025stream} optimize what each operator computes and where it runs, how the operators are composed and issued through the CP has received far less attention.

None of the fixes a developer would reach for first recovers this concurrency.
Packing several operators into one command, as CUDA Graphs~\citep{nvidia-cudagraphs} and XRT's run lists~\citep{xrt-repo} do, amortizes launch cost but creates no overlap, since a synchronization on one column group delays every later issue, whichever group it feeds.
A second hardware context gives none either, because the driver allocates every context the whole array, so co-resident contexts share it in time~\citep{xdna-driver}.
Alternating the work of attention's two columns by hand, as the alternated baseline does, removes the wait inside that one operator, whose existing stream starts its second column only after waiting on its first, but the column groups still take turns.
The same kind of wait recurs in decode, where attention reads its key-value (KV) cache at half the DRAM read rate the platform sustains.
Its loop holds one buffer each for a block's keys, values, and scores, so each block's transfer waits for the compute on the previous block.
MLIR-AIR's double-buffering pass declines that loop for a correct local reason, since the loop's running maximum and accumulator live across blocks, and the three buffers that could be renamed therefore stay single-buffered.
Each fix is sound for the part of the program it sees, whereas the waits come from how the whole program orders and names its work.

% SOURCE: decode attention reads KV at 28.4 GB/s = 51% of the same-batch read cap (vault lab-decode-long-context (5)); the declining transformation is the build's own comment on air-label-scf-for-to-ping-pong (lab-decode-long-context (5)).

The insight of this work is that the CP's instruction order is the array's schedule, and that a toolchain fixes this order in the instruction streams it emits.
Once configured, the array computes data-driven, and no hardware or runtime scheduler reorders work across its engines.
Every wait in a design, and every column a wait holds idle, can therefore be read from those streams without a timing trace.
Read this way, the waits above are textbook order and name dependences~\citep{bernstein1966analysis,kuck1981dependence}, in which work waits on other work whose results it does not consume.
The concurrency is therefore provided by the hardware and rationed by these false dependences, both in the CP's stream and inside an operator's loop.
Pathways~\citep{barham2022pathways} orders all computations on an island of accelerators through a centralized scheduler at run time, which this device lacks, so here the order has to be written into the instruction stream itself.
% SOURCE: Pathways §4.4 "The PATHWAYS runtime includes a centralized scheduler per island that consistently orders all of the computations in the island" (arXiv 2203.12533v1, workspace tmp/mlsysaw/Pathways.txt, read 2026-10-23).
IOS~\citep{ding2021ios} and Rammer~\citep{ma2020rammer} schedule operators at compile time from the program they are given, whereas we start from binaries a toolchain has already emitted, closed ones included, which lets us read the order of a production stack we cannot rebuild.

% DECISION: the Llama-3.2-1B 3.21x (existing S4 vs S2) and 4.27x (composer S4 vs existing S2) at 16k + 4k were taken while the existing order ran in an intermittent slow state at mid-range positions (vault lab-split-sweep (18)); neither is quoted.
In this work, we schedule a compiled design from the streams its toolchain emitted, in three steps.
First, we recover the CP's order from the streams of three toolchains, open and closed, into a graph of what must finish before what starts, class each wait as a true, name, or order dependence, and state which reorders and renames the streams alone show to be legal.
Re-emitting streams of all three toolchains byte for byte checks that this analysis starts from exactly the instructions each one dispatches.
Second, because a stream leaves only the durations unknown, we price a candidate schedule, a split, or the removal of a wait from \emph{probes}, namely timings of each operator dispatched alone, without running the candidate.
An event model computes that price, and a lower bound from the same probes shows how much any schedule could still gain.
On appends across four LLMs, the event model names the faster split in all 36 choices and predicts TTFT with a median error of 2.15\%.
% SOURCE: split choices 36 / 36, median |TTFT error| 2.146%, max 7.311%, over the append cells of Llama-3.2-1B, Qwen3-4B, Gemma3-4B, and Llama-3.1-8B (amd-npu 78ec55b7 prefill-overlap/cp-predict/score-2026-10-21.json, scorer cp_score.py 86ba24b6; 7-eval Model Accuracy).
Third, OPCORD rewrites compiled designs with these choices.
Its composer reorders issue across operators so that every column group's work is issued before the CP waits on any of it.
A stream pass applies the same reorder within one operator's stream, and a loop pass renames decode attention's buffers into rings so that each block's transfer overlaps the previous block's compute.
Legality checkers refuse, with a reason, any rewrite they cannot show legal, and the kernels, driver, and firmware stay unchanged.

The two passes automate, inside the compiler and legally on compiled designs, what experts do by hand.
The stream pass reproduces the hand alternation of attention's two columns, which the alternated baseline already carries, so its gain over that baseline is zero by construction.
The loop pass's renaming shortens each decoded token by $1.27\times$ on Llama-3.2-1B and $1.16\times$ on Qwen3-4B at a 16{,}384-token context against the unmodified decode design, and at long contexts it reaches the time per token of FastFlowLM, whose designs are tuned by hand~\citep{fastflowlm-repo}.

The value of the passes is their reach, since they judge designs that nobody tuned and rewrite them where the rewrite is legal.
On designs we never examined, we claim their judgments, not gains.
The event model contributes the choices, namely the split for prompts from scratch and for appends and whether a removal pays, priced without running them.
Together, the reorder and the renaming shorten a whole agent turn at a 16{,}384-token context, which appends a tool output and decodes 250 tokens, by $1.15$--$1.32\times$ against the existing program on its faster split.

In summary, the primary contributions of this work are as follows:
\begin{itemize}
    \item A method for scheduling a spatial array from the instruction streams its toolchain has already emitted, by recovering the command processor's order as the array's schedule, classing each wait by its textbook dependence, and stating what those streams alone establish about the legality of a reorder or a rename.
    \item An event model and lower bound that price a schedule, the split of columns, and the cost of removing a dependence from probes of each operator alone, without running the schedule.
    \item The design and implementation of OPCORD, a composer and two MLIR-AIE passes that remove these dependences from compiled designs with the kernels, driver, and firmware unchanged, refusing with a reason any rewrite they cannot show legal.
\end{itemize}
OPCORD consists of an analysis that recovers a design's ordering and classifies each wait, a composer that plans and issues the rewritten schedule, and two MLIR-AIE passes, each with a legality checker.
