\section{OPCORD}
\label{sec:method}

% VALUE: design opener: OPCORD removes the false dependences of §3.3 in steps, each answering a property of the platform: a blocking in-order CP (reorder issue, by the composer across operators and the stream pass within one), one buffer per role in decode's loop (the loop pass's rings), an order and a split that pay differently with the prompt length (both chosen per length by the event model), designs it did not compile (checkers that refuse with a reason)
% DECISION: the opener follows the FPGA'27 design opener, each property of the platform followed by the mechanism that answers it, with one subsection per property (STYLE.md, Paper structure, Design; contract §6).
% DECISION: the legality conditions themselves live in Section~\ref{sec:order}; this section states only how OPCORD acts on them, namely checkers that accept a rewrite or refuse it with a reason (contract §6).
OPCORD runs the analysis of Section~\ref{sec:order} on each design, takes from it the segments and the legality conditions, provides a rewrite only for the kinds of false order whose bound leaves room, and answers each property of the platform behind the waits of Section~\ref{subsec:losses} with one mechanism.
Because a synchronization blocks the in-order CP, our composer and stream pass issue every group's work before the CP waits on any (Section~\ref{subsec:order}).
Because decode attention's loop keeps one buffer per role, our loop pass renames those buffers into rings (Section~\ref{subsec:rings}).
Because the issue order and the split that pay change with the prompt length, the composer chooses both per length with an event model (Sections~\ref{subsec:split} and~\ref{subsec:pricing}).
Because OPCORD rewrites designs it did not compile, checkers refuse, with a reason, any rewrite they cannot show legal (Section~\ref{subsec:checkers}).

\subsection{Reordering Issue}
\label{subsec:order}



% VALUE: the composer reorders issue across operators: it list-schedules the host program's dependency graph chunk by chunk rather than stage by stage, pairing each attention operator with ready GEMMs of matching work; a composed command keeps each operator's segments in order and every instruction once, so only when work is issued and awaited changes
\label{subsec:compose}
% DECISION: subsec:compose names the composer's part of the reorder and resolves to this subsection; the conditions the former composing subsection stated are in Section~\ref{sec:order}.
Our \emph{composer} list-schedules the producer-consumer order between the host program's operators chunk by chunk, from the design's per-operator streams and probes, and emits commands whose order we call the \emph{composed order}.
The existing host program runs a layer stage by stage instead, so the CP issues no GEMM beside attention (Section~\ref{subsec:losses}).
The composer thus changes the design's cut into commands (Section~\ref{subsec:spectrum}) while keeping its configuration.
Each command pairs the ready attention operator of the lowest layer and chunk with ready GEMMs whose estimated work matches it.
A command concatenates its operators' segments under the conditions of Section~\ref{subsec:legality}, so composing changes when work is issued and awaited, never what the work is.
% SOURCE: merged.plan (amd-npu a0ee2ed prefill-overlap/merged.py, now opcord/compose/merged.py at aie-cosched opcord-runtime 446fa1c): qkv(L, c) after down(L-1, c); attn(L, c) after qkv(L, 0..c); o after attn; gate and up after o; down after gate and up; GEMMs added in the same order until their estimated work reaches the attention operator's; an optional cap on the GEMMs per attention command.
% SOURCE: txn.segments and txn.compose (a0ee2ed prefill-overlap/txn.py, now opcord/compose/txn.py); compose asserts each stream's segment order, every op kept once, and equal headers.

% VALUE: within a command, the composer opens every group's work and then places each synchronization at its predicted completion, followed by the issue it gates, so no synchronization holds back another group's work; attention's two columns count as two groups; the order is fixed at build time and runs without the host; its price is the shared DRAM read rate, priced in Section 5.4
Packing the operators into one command in turn would still leave the GEMM group idle while the CP walks attention's synchronizations (Figure~\ref{fig:order}a), so the composer issues the opening segments of every group first.
It then places each synchronization in order of its \emph{predicted completion}, estimated from the probes, followed by the issue it gates.
Attention's two columns count as two groups for this order, so their segments alternate as well.
The estimates fix this order when the command is built, and the CP executes it without the host.
Running both groups at once makes a group that reads at the shared DRAM read cap also carry its co-runner's reads (Section~\ref{subsec:pricing}), so a design already near the cap gains little.
% SOURCE: merged.cp_order (a0ee2ed, now opcord/compose/merged.py): the opening segments of both attention columns and of the first GEMM, then synchronizations by predicted completion; mid-stream fractions (0.25, 0.5) of attention's estimate, the lowest of five placements tried; the in-turn order takes 1.26x as long on the same 38 commands (lab-prefill-overlap (16)).
% DECISION: tradeoffs are stated beside the decision that incurs them rather than collected in a section (author, 2026-10-21).

% VALUE: within one operator's stream, the stream pass (an MLIR-AIE pass on the runtime sequence, compiled or lifted) applies the same reorder, interleaving the columns' segments; it is the rule by which Section 3.2's columns were alternated, and it emits that alternation byte for byte rather than discovering it
Our \emph{stream pass} applies the same reorder within one operator's stream, as an MLIR-AIE pass on its runtime sequence, compiled or lifted from a recording, and interleaves the columns' segments so that each column's work is issued before the CP waits on another.
This is the rule by which we alternated attention's columns in Section~\ref{subsec:losses}, and the pass emits that alternation byte for byte on all 42 streams we alternated by hand.

\subsection{Renaming Buffers}
\label{subsec:rings}

% VALUE: decode attention's keys, values, and scores each sit in one buffer, so each block waits for the previous; only the running maximum and accumulator carry; the loop pass renames every other buffer into a two-slot ring that each core acquires once per block, so the cores pipeline across blocks; it classes buffers by their conflicts across iterations and leaves the carried state, which is why the compiler's transformation declines the loop and ours does not; kernels, arithmetic order, tokens, and logits unchanged
Of the buffers in decode attention's loop (Section~\ref{subsec:losses}), only the running maximum and the accumulator carry data across blocks, so our \emph{loop pass} renames each of the others, namely the keys, the values, and the scores passed between the two cores, into a \emph{ring} of two slots.
Each core acquires and releases a slot once per block, so the first core computes block $i+1$ while the second folds block $i$.
Whereas MLIR-AIR's double-buffering transformation declines the whole loop for its carried state, our pass classes every buffer of the lowered loop by its conflicts across iterations and leaves the carried state in place.
The kernels and the order of their arithmetic are unchanged, so the decoded tokens and every step's logits stay bit-identical, and the time per position falls from the KV transfer plus the compute to the larger of the two.

% SOURCE: single buffering, the build's own comment ("air-label-scf-for-to-ping-pong declines it, because the running max and accumulator are live across blocks") (vault lab-decode-long-context (5)).

% VALUE: the prefill needs no renaming: the existing program already gives each chunk its own buffers, so with commands in flight no use waits for another; the composer's rings only bound memory, at no change in time, and remove no dependence
The prefill needs no renaming, because the existing host program already gives every chunk its own buffers, so no use waits for another even with several chunks in flight.

\subsection{Pricing and Choosing}
\label{subsec:pricing}

% VALUE: the problem in words: a schedule makes three essential decisions (the split; the order in which the CP interleaves each command's segments, each operator's kept in order; the buffer assignment); operators hand data over through DRAM, so a consumer issues after its producer's last synchronization and any host work, in a separate command; D and packing manage only the host boundary and are reported apart; the objective is the makespan
% DECISION: no NP-hardness claim until a reduction is written; with negligible issue cost and one layer's fixed per-chunk pattern the problem has the structure of a two-machine chain-reentrant shop (wang1997reentrant), and with non-negligible issue cost the CP acts as a shared server (glass2000dedicated, hall2000common) (vault ch3-formulation, Relation to classical scheduling).
\label{subsec:formulation}
A schedule of a compiled design makes three essential decisions, namely the split, which sets which operators can run at once (Section~\ref{subsec:prefill}), the order in which the CP interleaves each command's segments, keeping every operator's segments in their own order, and the slot that each use of a buffer takes, since two uses of one slot run in turn even when neither consumes the other's data.
Because operators hand data over through DRAM with no lock between them, a consumer issues only after its producer's final synchronization and any host work between the two, in a separate command.
The number $D$ of commands in flight and the packing of commands manage only the boundary with the host, so we treat them as host policy, which the composer chooses with the split, and the objective is the makespan, which for prefill is the TTFT less the work before the first decoder layer and after the last.

% VALUE: to choose among orders and splits without running each, an event simulation of the device, the CP, and the host prices a schedule; its form follows the platform (one in-order queue of commands, a host timeline with waits, column groups that overlap within a command) and its parameters are the operators' own timings plus a few machine constants measured once by microbenchmarks; the existing program runs through the same simulation, so both sides are priced alike; device time, host exposure, and head and tail reported apart
% COMMENT: this subsection describes the event model's rebuilt form (setup by column group, overlap bounded by bytes over the read cap, the head as a probed operator), which npu-gap is implementing in development; confirm every term against the implementation before the freeze.
To choose among orders and splits without running each, we price a schedule before it runs, from the probes of Section~\ref{subsec:removal}, with an event simulation of the device, the CP, and the host, which we call the \emph{event model}, analytical in form, following the platform's structure, with parameters that are measured.
Queued commands run one at a time (Section~\ref{subsec:semantics}), so command $k$ ends at
\begin{equation}
\label{eq:cmd}
e_k = \max\bigl(e_{k-1} + s_k,\; q_k + F\bigr) + \tau_k,
\end{equation}
where $q_k$ is the time the host queues it and $s_k$ is the transition into it, which is the setup $s_\mathrm{same}$ within one column group, and otherwise the setup $s_g$ of its group less the window $w_h$ at the end of the previous command, on group $h$, during which other columns can already start, never below zero.
Within a command, each column group's time is the sum of its operators' timings alone, with the same-group setup between consecutive operators.
When groups overlap, a group whose own reads already run at the read cap $R$ absorbs every byte its co-runners read, so the command takes
\begin{equation}
\label{eq:overlap}
\tau_k = \max_{g}\Bigl(t_{k,g} + [\,g \text{ at the cap}\,]\sum_{h \ne g} \frac{\beta_{k,h}}{R}\Bigr),
\end{equation}
where $t_{k,g}$ is group $g$'s time and $\beta_{k,h}$ the DRAM bytes that group $h$ reads in command $k$, counting every re-read.
Whether a group runs at the cap is measured, by comparing its bytes over $R$ with its time alone, and in the designs we evaluate the GEMMs do and attention does not.
On the host side, each command costs an issue and each operator a post-processing step, and the host waits on the oldest command once $D$ are in flight.
The existing program runs through the same simulation as its own host program, so both sides of every comparison are priced alike.
Finally, the event model adds the work before the first decoder layer and after the last, which it prices as ordinary operators, and reports the device time, the host time left unhidden, and that work separately, so an error in one term cannot hide behind another.
% SOURCE: GEMM-only commands read 90-93% of the cap and attention-only about 15% during Llama-3.2-1B's 4,096-token prefill (amd-npu 71901c50 metrics/retro-2026-10-21/dram-retro.txt; vault lab-metric-fields (1) and its amendment 1); the read cap from the 8x2 bracket, 53.93 GB/s at the calibration hold (amd-npu d94266bf prefill-overlap/calib/run-2026-10-22/batch.log), re-read at every batch.
% SOURCE: the overlap form (ruling 2026-10-24): moved read bytes from the dispatched streams (aie-cosched f7eedbc, README 7e00ac9); bytes over R against time alone 0.87-1.06 for every GEMM set and about 0.15 for attention, so any threshold between 0.2 and 0.87 classifies alike; on the 30-cell co-run grid of 2026-10-22 the residual is a median 0.016 ms, the rest a fixed part of 0.030-0.041 ms carried by the transition term (npu-gap, 2026-10-24). The transition form (ruling 2026-10-24): s = s_same within a group, max(0, s_g - w_h) across groups; from the 10-22 sequences a GEMM after attention waits about 47 us and attention after a GEMM starts about 8 us early (npu-gap, device.json fit), to be pinned by microbenchmark v2. opcord/model/event_model.py simulate() (one in-order queue; host program with waits); the rebuilt form, constants schema version 2 (npu-gap, opcord dev checkout; vault decisions log "The model rebuilt from a logical base", 2026-10-24); bytes per operator instance from the instruction streams' buffer descriptors (pass-0 tools/bprime_check byte model).

% VALUE: the operators' timings and bytes depend on the LLM and the split and are measured once per configuration by running each operator alone or read from its streams; the few machine constants (dispatch floor, setup within and across groups, host issue and post, read cap) are measured once by microbenchmarks, all non-negative, none fitted to an LLM's end-to-end runs; precedent: analytical models whose parameters are machine constants measured by microbenchmarks
Only the operators' timings and bytes depend on the LLM and the split, so we measure the timings once per configuration by dispatching each GEMM alone and each attention chunk alone at several cached-context lengths, and read the bytes from the operators' streams.
Between measured points the event model interpolates, and beyond them it refuses to price.
The machine constants, namely $F$, the setups and windows of the transitions, the host's issue and post-processing costs, and $R$, are measured once by microbenchmarks on dummy data, as analytical models of communication and of memory-bound kernels measure theirs~\E{cite: Hockney; LogP; roofline}.
No constant is fitted to an LLM's end-to-end runs, so every LLM and prompt length that Section~\ref{subsec:decision} scores tests the event model rather than supplying its constants.
% SOURCE: microbenchmarks (npu-gap prefill-overlap/microbench.py): dispatch floor from empty commands; setup from back-to-back sequences mixing same-group and cross-group pairs, non-negative least squares on one set and checked on another; read cap from co-runs on both sides of the crossover between the longest group and bytes over the cap; per split build (S1, S2, S4 of Llama-3.2-1B) with a Qwen3-4B transfer check; values \E{pending}.
% COMMENT: bib entries needed (read each source first): Hockney's model, LogP / LogGP, the roofline model.

% VALUE: before a prompt length runs, the composer prices every candidate (split, existing or composed order, host policy) with the event model and runs the cheapest, settling near-ties by a short measurement; more attention columns shorten attention and lengthen the GEMMs, so the split that pays moves with the balance of the two groups; because the existing order is a candidate, the composer keeps it where composing is priced higher, as at prompts of one or two chunks
Before a prompt length runs, the composer prices every candidate with the event model, namely each split, the existing order and the composed one, and each number $D$ of commands in flight and packing of commands, and it runs the cheapest unless the near-tie rule below applies.
More attention columns shorten attention, whose time grows with the prompt, but lengthen every GEMM, so the split that pays moves with the balance between the two groups (Section~\ref{subsec:pays}).
Because the existing order is among the candidates, the composer keeps it wherever composing is priced higher, as at prompts of one or two chunks.
% SOURCE: opcord/plan/planner.py choose(model, L, N): candidates every split with a committed probe (S1, S2, S4), arms ship / shipar / comp, composer policies depth {1, 2, 4, 8} x GEMM cap {none, 4} x packing {1, 4}, each priced by event_model.predict, cheapest returned with the whole table; measure-when-close (planner.decide) as in Section~\ref{subsec:pricing}.
% SOURCE: the four-column split's GEMMs are 27% (1B) and 35% (Qwen3-4B) slower than on six columns, and its attention slope per chunk 3.0-3.1x lower than the default split's existing stream (vault lab-split-sweep (4)-(5)).
% DECISION: resident splits, switching at a turn boundary, and relayout belong to agent workloads, an extension under spine v18; their text is archived in the vault.

% VALUE: the event model's error is stated on the difference between candidates, so its choice is right whenever two candidates differ by more than about twice that error and costs at most about that much otherwise; where the top candidates fall inside a frozen band, a short measurement at plan time settles the tie, and the unaided choice is always reported
Because a choice compares candidates, we state the event model's error on the difference between two candidates' times rather than on each time alone.
Its choice is then right whenever two candidates differ by more than about twice that error, and otherwise costs at most about that much.
Where the top candidates fall inside a band of 5\% for orders of one kind or 15\% between a composed and an existing order, the composer runs each candidate briefly when it plans the prompt length and keeps the faster, and we always report the event model's unaided choice beside it (Section~\ref{subsec:decision}).

\subsection{Implementation}
\label{subsec:impl}

% VALUE: the analysis and both passes with their checkers in MLIR-AIE (C++), the loop pass as an opt-in step of the compiler driver that leaves every output byte-identical when off; the composer, the event model, and the split switch as a Python runtime package replacing the host program's dispatch loop on the design's own hardware context; no kernel, driver, or firmware change, and every reconfiguration point stays where the stack put it
The analysis of Section~\ref{sec:order} and both passes, with their checkers, are about 6{,}700 lines of C++ in MLIR-AIE~\citep{mlir-aie-repo}.
The loop pass is an opt-in step of the compiler's driver that runs on the lowered design that the stack's own passes produce and, switched off, leaves every instruction stream and configuration the compiler emits byte-identical to the existing build.
The composer, with the event model and the switch between splits, is a runtime package of about 2{,}700 lines of Python that replaces the dispatch loop of the design's host program and submits to the design's own hardware context, so OPCORD changes no kernel, driver, or firmware.
