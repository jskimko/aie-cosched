\section{OPCORD}
\label{sec:method}

% VALUE: design opener: OPCORD removes the false dependences of §3.3 in steps, each answering a property of the platform: a blocking in-order CP (reorder issue, by the composer across operators and the stream pass within one), one buffer per role in decode's loop (the loop pass's rings), a faster split that changes with the regime, from scratch or append (split chosen per regime by the event model), designs it did not compile (checkers that refuse with a reason)
% DECISION: the opener follows the FPGA'27 design opener, each property of the platform followed by the mechanism that answers it, with one subsection per property (STYLE.md, Paper structure, Design; contract §6).
% DECISION: the legality conditions themselves live in Section~\ref{sec:order}; this section states only how OPCORD acts on them, namely checkers that accept a rewrite or refuse it with a reason (contract §6).
OPCORD removes the false dependences of Section~\ref{subsec:losses} in steps, each in response to a property of the platform.
A synchronization blocks the in-order CP and every issue behind it, so our composer issues every column group's work before the CP waits on any group, and our stream pass does the same within one operator (Section~\ref{subsec:order}).
Because decode attention's loop keeps one buffer per role, each block's transfer waits for the previous block's compute, which our loop pass removes by renaming those buffers into rings (Section~\ref{subsec:rings}).
The faster split of the columns changes between the two \emph{regimes} of prefill, namely prompts computed from scratch and appends to a cached context, so the composer chooses the split per regime with the event model (Section~\ref{subsec:split}).
Since OPCORD rewrites designs it did not compile, a checker tests each rewrite against the legality conditions of Section~\ref{sec:order} and refuses, with a reason, any rewrite it cannot show legal (Section~\ref{subsec:checkers}).

\subsection{Reordering Issue}
\label{subsec:order}



% VALUE: the composer reorders issue across operators: it list-schedules the host program's dependency graph chunk by chunk rather than stage by stage, pairing each attention operator with ready GEMMs of matching work; a composed command keeps each operator's segments in order and every instruction once, so only when work is issued and awaited changes; an append plans only its new chunks
\label{subsec:compose}
% DECISION: subsec:compose names the composer's part of the reorder and resolves to this subsection; the conditions the former composing subsection stated are in Section~\ref{sec:order}.
The existing host program runs a layer stage by stage, so no GEMM is ready to run beside attention.
Our \emph{composer} instead list-schedules the host program's dependency graph chunk by chunk, from the design's per-operator streams and probes, and emits commands that we call the \emph{composed schedule}.
Each command pairs the ready attention operator of the lowest layer and chunk with ready GEMMs whose estimated work matches it, and an append to a cached context plans only its new chunks.
A command concatenates its operators' segments under the conditions of Section~\ref{subsec:legality}, so composing changes when work is issued and awaited, never what the work is.
% SOURCE: merged.plan (amd-npu a0ee2ed prefill-overlap/merged.py, now opcord/compose/merged.py at aie-cosched opcord-runtime 446fa1c): qkv(L, c) after down(L-1, c); attn(L, c) after qkv(L, 0..c); o after attn; gate and up after o; down after gate and up; GEMMs added in the same order until their estimated work reaches the attention operator's; an optional cap on the GEMMs per attention command.
% SOURCE: txn.segments and txn.compose (a0ee2ed prefill-overlap/txn.py, now opcord/compose/txn.py); compose asserts each stream's segment order, every op kept once, and equal headers.
% SOURCE: append = Merged.prefill(ids, start=L) on the same plan rules; attention estimates linear in the absolute chunk index (vault lab-agent-step (1)).

% VALUE: within a command, the composer opens every group's work and then places each synchronization at its predicted completion, followed by the issue it gates, so no synchronization holds back another group's work; attention's two columns count as two groups; the order is fixed at build time and runs without the host; its price is the shared DRAM read rate, priced in Section 5
Because packing the operators into one command in turn would still leave the GEMM group idle while the CP walks attention's synchronizations (Figure~\ref{fig:order}b), the composer issues the opening segments of every group first.
It then places each synchronization in order of its \emph{predicted completion}, estimated from the probes, followed by the issue it gates.
Attention's two columns count as two groups, so their segments alternate as well.
The estimates fix this order when the command is built, and the CP executes it without the host.
Running both groups at once costs the GEMMs a share of attention's time under the shared DRAM read rate (Section~\ref{subsec:removal}), so a design already near the cap gains little.
% SOURCE: merged.cp_order (a0ee2ed, now opcord/compose/merged.py): the opening segments of both attention columns and of the first GEMM, then synchronizations by predicted completion; mid-stream fractions (0.25, 0.5) of attention's estimate, the lowest of five placements tried; the in-turn order takes 1.26x as long on the same 38 commands (lab-prefill-overlap (16)).
% DECISION: tradeoffs are stated beside the decision that incurs them rather than collected in a section (author, 2026-10-21); the size of the penalty and the 1.81-1.84x ceiling are stated once, in Section~\ref{subsec:removal}.

% VALUE: within one operator's stream, the stream pass (an MLIR-AIE pass on the runtime sequence, compiled or lifted) applies the same reorder: monotone mode only hoists issues; full mode interleaves the columns' segments round-robin by index, the rule that produced the hand-alternated streams, so it emits that alternation byte for byte rather than discovering it
Our \emph{stream pass} applies the same reorder within one operator's stream, as an MLIR-AIE pass on its runtime sequence, whether compiled or lifted from a recording.
Its monotone mode only moves each segment's issue to just before the first wait of another column, whereas its full mode also interleaves the columns' segments round-robin by index.
Full mode is the rule by which we alternated attention's streams by hand for the alternated baseline, so the pass emits that alternation, byte for byte on all 42 such streams.

\subsection{Renaming Buffers}
\label{subsec:rings}

% VALUE: decode attention's keys, values, and scores each sit in one buffer, so each block waits for the previous; only the running maximum and accumulator carry; the loop pass renames every other buffer into a two-slot ring that each core acquires once per block, so the cores pipeline across blocks; it classes buffers by their conflicts across iterations and leaves the carried state, which is why the compiler's transformation declines the loop and ours does not; kernels, arithmetic order, tokens, and logits unchanged
Of the buffers in decode attention's loop (Section~\ref{subsec:losses}), only the running maximum and the accumulator carry data across blocks, so our \emph{loop pass} renames each of the others, namely the keys, the values, and the scores passed between the two cores, into a \emph{ring} of two slots.
Each core acquires and releases a slot once per block, so the first core computes block $b+1$ while the second folds block $b$.
Whereas MLIR-AIR's double-buffering transformation declines the whole loop for its carried state, our pass classes every buffer of the lowered loop by its conflicts across iterations and leaves the carried state in place.
The kernels and the order of their arithmetic are unchanged, so the decoded tokens and every step's logits stay bit-identical.
% SOURCE: aie-cosched-rename (mlir-aie 41b4947f09e; on cosched-flag through the aiecc flag), classes and rings in vault lab-cosched-passes (33): 12 buffers renamed on the 1B census build (K, V, score per attention pair); the class rule renames only buffers whose every cross-iteration conflict is WAR or WAW (lab-cosched-passes (57), P6 plan); tokens and every step's logits bit-identical across the existing design, the hand edit, and the pass, 1B P = 0 to 32,517 and Qwen3-4B P = 2,048 to 28,800 (vault lab-decode-long-context (22), amd-npu a6bc94b and 455740b).
% SOURCE: single buffering, the build's own comment ("air-label-scf-for-to-ping-pong declines it, because the running max and accumulator are live across blocks") (vault lab-decode-long-context (5)).
% DECISION: the rename is our loop pass's output on the lowered design, not a hand edit; the hand edit appears only as the reference the pass reproduces (Appendix~\ref{app:loop-pass}).

% VALUE: the prefill needs no renaming: the existing program already gives each chunk its own buffers, so with commands in flight no use waits for another; the composer's rings only bound memory, at no change in time, and remove no dependence
The prefill needs no renaming, because the existing host program already gives every chunk its own buffers, so no use waits for another even with several chunks in flight.
The composer replaces that naming with rings sized from the plan's live intervals only to bound the memory it takes, which leaves the time unchanged and removes no dependence (Appendix~\ref{app:rings}).
% SOURCE: shipped naming is one slot per role per chunk; R-ship (the composed schedule at shipped's per-chunk naming) equals the composer with rings within 0.1% (0.99996-1.00074, amd-npu 71081d1) and holds 4-7x the rings' buffer bytes (vault lab-prefill-overlap (29), third revision); merged.colour and Layout (a0ee2ed, now opcord/compose/merged.py).

\subsection{Partitioning per Regime}
\label{subsec:split}

% VALUE: the split is a hand-fixed build parameter of the existing design; the legal splits S1, S2 (default), S4 follow from the KV heads; each split is its own configuration built from the unchanged source, with outputs bit-identical to the default split, so the existing program and the composer each run on any of them
The existing design fixes its split by hand, as a parameter of its build.
Since each attention group serves an equal share of the KV heads, an LLM with 8 KV heads admits attention on 1, 2, or 4 columns, which we call the splits $S_1$, $S_2$, and $S_4$, with $S_2$ the default.
We build each split as its own configuration from the unchanged source, with outputs bit-identical to those of the default split, so the existing program and the composed schedule can each run on any of them.
% SOURCE: mlir-air a3e26261 fused_prefill/device.py: Attn(col=...) per group in Config.attn, GCOL0, GNC = 1, 6 as module constants; spec() splits kv_heads evenly, so 1, 2, or 4 attention columns with 8 KV heads (vault lab-split-sweep (1)).
% SOURCE: out-of-tree split modules; logits bit-identical to the default split in every configuration on both models (vault lab-split-sweep (2), (4), (5)).

% VALUE: the composer prices every candidate (split, existing or composed order, host policy) with the event model and runs the cheapest; more attention columns shorten attention and lengthen the GEMMs, and the group that binds decides the direction (GEMMs from scratch, attention on long appends); because the existing order is a candidate, it runs where composing is priced higher
Before a prompt runs, the composer prices every candidate with the event model (Section~\ref{subsec:pricing}), namely each split, the existing order and the composed one, and each host policy (Appendix~\ref{app:host}), and it runs the cheapest.
More attention columns shorten attention, whose time grows with the context, but lengthen every GEMM.
The GEMMs therefore bind for prompts computed from scratch, which favours fewer attention columns, whereas attention binds on appends to a long cached context, which favours more (Section~\ref{subsec:bound-eval}).
Because the existing order is among the candidates, the composer keeps it wherever composing is priced higher.
% SOURCE: opcord/plan/planner.py choose(model, L, N) at aie-cosched opcord-runtime 446fa1c: candidates every split with a committed probe (S1, S2, S4), arms ship / shipar / comp, composer policies depth {1, 2, 4, 8} x GEMM cap {none, 4} x packing {1, 4}, each priced by event_model.predict, cheapest returned with the whole table (vault lab-split-sweep, N6 and N7; decisions log D24 N3).
% SOURCE: the four-column split's GEMMs are 27% (1B) and 35% (Qwen3-4B) slower than on six columns, and its attention slope per chunk 3.0-3.1x lower than the default split's existing stream (vault lab-split-sweep (4)-(5)).
% DECISION: this states the current planner (N3); the evaluation's present cells used the measured-arm policy of the earlier composer, and the final sweep runs through choose() (vault decisions log D24; eval re-run planned).

% VALUE: chosen splits stay resident and a conversation switches at a turn boundary, moving its cached context to the new split's attention groups; the price of a per-regime split is memory or a switch with a relayout, priced in the appendix; neither applies within one regime
Each chosen split stays resident in its own hardware context, and a conversation switches at a turn boundary by suspend and resume, moving its cached context to the attention groups of the new split.
A per-regime split therefore costs either a second copy of the weights or a switch with a relayout, which Appendix~\ref{app:relayout} prices; neither applies within one regime.
% SOURCE: one copy of the weights per resident split (vault lab-metric-fields (1)); warm switch by suspend and resume (lab-split-sweep (5)); relayout measured (lab-split-sweep (38)); the numbers are in Appendix~\ref{app:relayout}.

\subsection{Legality Checkers}
\label{subsec:checkers}

% VALUE: the composer and both passes each carry a checker that tests the legality conditions of Section 4 (pointed to, not restated) on the facts its rewrite touches; the composer's checks stop the composition rather than drop an operator; the stream pass checks every inverted pair and leaves the stream unchanged on a finding, saying whether illegal or not shown legal; the loop pass refuses a buffer it cannot show renamable and confirms its own output
The composer and both passes each carry a checker that tests the legality conditions of Section~\ref{subsec:legality} on the facts its rewrite touches.
The composer checks that every two operators it interleaves meet the condition between whole operators, that no ring slot is reused early, and that each split fits a shim BD's fields.
A check that does not hold stops the composition with its reason rather than dropping an operator.
The stream pass checks every pair of instructions that its rewrite inverts, from the routes, BDs, and buffer ranges it derives from the configuration.
On any finding it leaves the stream unchanged and names the condition, the pair, and whether the rewrite was shown illegal or could not be shown legal, so a reader can tell a hazard from a gap in what the stream reveals.
The loop pass refuses a buffer that fails the rename conditions or is used outside its block loop, and it re-checks each ring and the carried state on its output.
% SOURCE: composer checks: own-group register writes (shim BDs and DMA queues, own cores' locks, own cores' runtime parameters), disjoint argument slots or byte ranges, segment order and every op once, assert_no_hazard on ring slots, BD iteration wrap 6 bits and stride 20 bits per GEMM, check_posted for commands in flight; each turns red on a defeated input (lab-prefill-overlap (3), (4), (9); lab-split-sweep (5), (35)); checks fail rather than drop, 26 / 26 (decisions log D24 N1).
% SOURCE: stream checker in C++ inside aie-cosched-schedule, route facts from the device IR (mlir-aie cosched-flag e20940fac7e); findings RANGE-OVERLAP, RANGE-UNKNOWN, BD-REUSE, PUSH-BEFORE-BD-WRITE, QUEUE-OVERFLOW, NOT-PERMUTATION, CHANNEL-ORDER, BD-ORDER, SKELETON-MOVED and the route codes; any finding refuses the whole rewrite and the IR is unchanged; outcomes DECIDED (shown illegal) against RESOURCE-UNPROVEN, RANGE-UNKNOWN, TOOL-FAILED, PASS-ERROR (not shown legal) (vault lab-cosched-passes (57) steps 3-5, and the checker's reason list).
% SOURCE: loop pass input checks (one free / full lock pair, free lock starting at 1, BD and L1 budgets, every BD block ending in a next_bd, use inside a block loop, supported loop control) and output check (ring as made, carried state's users unchanged, budgets), mlir-aie aie-cosched-pass-0 e9fc225b2b6 / ba7ea1aa552, cherry-picked to cosched-flag (lab-cosched-passes (56), (57) step 2).

% VALUE: the passes' checkers are checked: an independent implementation of the stream checker agrees on every verdict, and every refused rename, forced, yields a design an independent check of the loop refuses (the composer's checks are tested by defeated inputs only); a pass that must accept or refuse every stream applies its legality condition to designs nobody has read; verdicts on unexamined designs are judgments, not gains
A second, independent implementation of the stream pass's checker agrees with it on every verdict over our prefill builds, and every rename the loop pass refuses, when forced, yields a design that an independent check of the loop refuses too (Appendix~\ref{app:checkers}).
A hand edit reaches only the streams someone reads, whereas a pass that accepts or refuses every stream applies the condition under which its rewrite is legal to designs nobody has read.
Section~\ref{subsec:census} reports the verdicts on designs we never examined, as judgments rather than gains.
% SOURCE: configured agreement C++ / Python on every prefill build (110 operators with no differing facts; Gemma3's differences all the oracle's TOOL-FAILED condition, counted apart), 0 DISAGREE; the 42 hand-alternated streams 162 / 162 AGREE; 10 negative controls with identical codes; every forced loop-pass refusal REFUSED by loopcheck with READS-DIFFER (decisions log, "P6 steps 1-5 done"; vault lab-cosched-passes (57) step 5 and forced refusals).

\subsection{Implementation}
\label{subsec:impl}

% VALUE: each part runs where its inputs exist: the analysis and both passes with their checkers in MLIR-AIE (C++), the loop pass as an opt-in step of the compiler driver that leaves every output byte-identical when off; the composer, the event model, and the split switch as a Python runtime package replacing the host program's dispatch loop on the design's own hardware context; no kernel, driver, or firmware change, and every reconfiguration point stays where the stack put it
Each part of OPCORD runs where its inputs exist, so what rewrites compiled code runs in the compiler and what depends on the prompt or on measured costs runs on the host.
The analysis of Section~\ref{sec:order} and both passes, with their checkers, are about 6{,}700 lines of C++ in MLIR-AIE~\citep{mlir-aie-repo}.
The loop pass is an opt-in step of the compiler's driver, and switched off, it leaves every instruction stream and configuration the compiler emits byte-identical to the existing build.
The composer, with the event model and the switch between splits, is a runtime package of about 2{,}700 lines of Python that replaces the dispatch loop of the design's host program and submits to the design's own hardware context.
OPCORD thus changes no kernel, driver, or firmware.
It also leaves every reconfiguration point where the stack put it, so the gains we report say nothing about moving those points.
Appendix~\ref{app:opcord} details the host boundaries and the loop pass's changes to the lowered design.
