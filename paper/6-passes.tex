\subsection{Reordering Issue}
\label{subsec:order}



% VALUE: why reorder: a synchronization blocks the in-order CP, so a wait on one group holds back every later issue to the others, an order dependence where that work does not read the awaited result; across operators, the original program runs a layer stage by stage, so the composer list-schedules the host program's dependency graph chunk by chunk instead (Algorithm 1); a composed dispatch keeps each operator's segments in order and every instruction once, so only when work is issued and awaited changes
\label{subsec:compose}
% DECISION: subsec:compose names the composer's part of the reorder and resolves to this subsection; the conditions the former composing subsection stated are in Section~\ref{sec:order}.
A synchronization on one group holds back every later issue to the others (Section~\ref{subsec:platform}), which is an order dependence wherever that work does not read the awaited result.
Across operators, the original program runs a layer stage by stage, so the CP issues no GEMM beside attention (Section~\ref{subsec:losses}).
Our \emph{composer} instead list-schedules the producer-consumer order between the host program's operators chunk by chunk, from the design's per-operator streams and probes, and emits dispatches whose order we call the \emph{composed order} (Algorithm~\ref{alg:compose}).
The composer thus changes the design's cut into dispatches (Section~\ref{subsec:spectrum}) while keeping its configuration.
A dispatch concatenates its operators' segments under the conditions of Section~\ref{subsec:legality}, so composing changes when work is issued and awaited, never what the work is.
% SOURCE: merged.plan (amd-npu a0ee2ed prefill-overlap/merged.py, now opcord/compose/merged.py at aie-cosched opcord-runtime 446fa1c): qkv(L, c) after down(L-1, c); attn(L, c) after qkv(L, 0..c); o after attn; gate and up after o; down after gate and up; GEMMs added in the same order until their estimated work reaches the attention operator's; an optional cap on the GEMMs per attention command.
% SOURCE: txn.segments and txn.compose (a0ee2ed prefill-overlap/txn.py, now opcord/compose/txn.py); compose asserts each stream's segment order, every op kept once, and equal headers.

\begin{algorithm}[t]
% VALUE: the composer's steps, whose reasons the prose gives: ready operators by layer and chunk; the lowest ready attention with ready GEMMs of matching estimated work, or the packing's GEMMs without attention; every group's opening segment first, attention's two columns as two groups; each synchronization in predicted-completion order, followed by the issue it gates; each dispatch checked, a failure refusing with its condition
% SOURCE: merged.plan (ready set in (layer, chunk, stage) order; the first ready attention; GEMMs while their summed estimate is below attention's; without attention, up to batch GEMMs; readiness once every producer is posted) and merged.cp_order (both attention columns' openings and the first GEMM's, then every synchronization by predicted completion, each followed by the issue it gates; GEMM i's synchronization followed by GEMM i+1's opening) at opcord-runtime 446fa1c; txn.compose's checks and the composer's checks of Section 3.3 fail rather than drop.
\caption{The composer, for one prompt length.}
\label{alg:compose}
\small
\begin{algorithmic}[1]
\renewcommand{\algorithmicrequire}{\textbf{Input:}}
\renewcommand{\algorithmicensure}{\textbf{Output:}}
\REQUIRE operator graph $G$, estimated work $w$, packing limit $k$
\ENSURE dispatches $D$ in the composed order, or a refusal
\STATE $D \gets [\,]$; $R \gets$ operators of $G$ without producers
\WHILE{$R \neq \emptyset$}
\STATE $a \gets$ the first attention operator in $R$, if any
\STATE $P \gets$ next GEMMs in $R$ until $w(P) \ge w(a)$, or $k$ if no $a$
\STATE $s \gets$ the issues before the first wait, for each column of $a$ and for $P$
\FORALL{synchronizations $y$, by predicted completion}
\STATE append $y$ and the issue it gates to $s$
\ENDFOR
\STATE \textbf{if} $s$ fails a legality condition \textbf{then refuse} with it
\STATE append $s$ to $D$; remove $a$ and $P$ from $R$
\STATE add to $R$ the operators whose inputs are ready
\ENDWHILE
\STATE \textbf{return} $D$
\end{algorithmic}
\end{algorithm}

% VALUE: the reasons behind Algorithm 1's steps across dispatches: GEMMs matched to attention by estimated work, because a dispatch in which both groups run lasts about as long as the longer group alone; without ready attention, the packing the host policy sets bounds the GEMMs per dispatch
The composer matches each dispatch's GEMMs to its attention operator by estimated work (lines~\mbox{3--4}), because a dispatch in which both groups run lasts about as long as the longer group alone (Section~\ref{subsec:semantics}), so matched estimates keep neither group idle for long.
Where no attention operator is ready, the packing that the host policy sets (Section~\ref{subsec:formulation}) bounds the GEMMs per dispatch.

% VALUE: the reasons behind Algorithm 1's steps within a dispatch: packing in turn leaves the GEMMs idle while the CP walks attention's synchronizations, so every group's work opens first, attention's two columns as two groups; synchronizations in predicted-completion order let each gated issue follow its own transfer; the order is fixed at build time and runs without the host; a dispatch failing the whole-operator condition stops the composition with its reason; its price is the shared DRAM read rate
Packing the operators into one dispatch in turn would still leave the GEMM group idle while the CP walks attention's synchronizations (Figure~\ref{fig:rewrites}a, before), so the composer opens every group's work first, counting attention's two columns as two groups, whose segments then alternate as well (line~5).
It then places the CP's synchronizations in the order in which the probes predict their transfers complete, so where the predictions hold, each gated issue follows its own transfer rather than another group's later one (lines~\mbox{6--8}).
The estimates fix this order when the dispatch is built, and the CP executes it without the host.
A dispatch that fails the condition of Section~\ref{subsec:legality} for whole operators stops the composition, with that condition as its reason (line~9).
Running both groups at once makes a group that reads at the shared DRAM read cap also carry its co-runner's reads (Section~\ref{subsec:semantics}), so a design already near the cap gains little.

Our \emph{stream pass} applies the same reorder within one operator's stream, so that column~7's work in attention no longer waits behind the CP's synchronizations on column~0, whose results it does not read (Figure~\ref{fig:rewrites}b).
The stream pass works as an MLIR-AIE pass on the runtime sequence, whether compiled or lifted from a recording.
The pass orders the segments by their index within their column and alternates the columns at each index, so the opening segments of all columns come first and each column's work is issued before the CP waits on another.
Its checker tests every pair of instructions that the new order inverts (Section~\ref{subsec:legality}) and leaves the stream unchanged on any finding.

\subsection{Renaming Buffers}
\label{subsec:rings}

% VALUE: decode attention's keys, values, and scores each sit in one buffer, so each block's transfer waits for the previous block's compute, a name dependence; only the running maximum and accumulator carry; the loop pass renames every other buffer into a two-slot ring: a second slot on the same tile, the free lock's initial count raised to two, each BD chain and core loop alternating the slots; it classes buffers by their conflicts across iterations and leaves the carried state, which is why the compiler's transformation declines the loop and ours does not
Decode attention's loop keeps one buffer per role, so each block's transfer waits until the previous block's compute releases the buffer, although it reads none of that compute's results (Section~\ref{subsec:losses}, Figure~\ref{fig:rewrites}c).
Only the running maximum and the accumulator carry data across blocks.
Our \emph{loop pass} therefore renames each of the others, namely the keys, the values, and the scores passed between the two cores, into a \emph{ring} of two slots.
Whereas AIR's double-buffering transformation declines the whole loop for its carried state, our pass classes every buffer of the lowered loop by its conflicts across iterations and leaves the carried state in place.
For each buffer it renames, the pass adds a second slot on the same tile, raises the initial count of the lock that marks a slot free from one to two, and alternates the two slots in every BD chain and core loop that uses the buffer.
% SOURCE: aie-cosched-rename (mlir-aie 41b4947f09e): each name-class buffer becomes a depth-2 ring, a second buffer on the same tile, the free-slot lock's init 1 -> 2, each BD chain extended (buffer -> its twin -> the old successor), and in each core loop the slot chosen per iteration (vault lab-cosched-passes (33), "The pass").
% SOURCE: single buffering, the build's own comment ("air-label-scf-for-to-ping-pong declines it, because the running max and accumulator are live across blocks") (vault lab-decode-long-context (5)).

% VALUE: each core acquires a slot once per block, so the cores pipeline across blocks and the time per position falls from transfer plus compute to the larger of the two; legality by pointer to the rename conditions, the output re-checked; kernels, arithmetic order, tokens, and logits unchanged
Each core acquires and releases a slot once per block, so the first core computes block $i+1$ while the second folds block $i$.
The time per position falls from the KV transfer plus the compute to the larger of the two.
The pass renames only buffers that the conditions of Section~\ref{subsec:legality} admit and re-checks each ring and the carried state on its output.
The kernels and the order of their arithmetic are unchanged, so the decoded tokens and every step's logits stay bit-identical.

\subsection{Pricing and Choosing}
\label{subsec:pricing}
\label{subsec:split}


% VALUE: the problem in words: a schedule makes three essential decisions (the split; the order in which the CP interleaves each dispatch's segments, each operator's kept in order; the buffer assignment); operators hand data over through DRAM, so a consumer issues after its producer's last synchronization and any host work, in a separate dispatch; D and packing manage only the host boundary and are reported apart; the objective is the makespan
% DECISION: no NP-hardness claim until a reduction is written; with negligible issue cost and one layer's fixed per-chunk pattern the problem has the structure of a two-machine chain-reentrant shop (wang1997reentrant), and with non-negligible issue cost the CP acts as a shared server (glass2000dedicated, hall2000common) (vault ch3-formulation, Relation to classical scheduling).
\label{subsec:formulation}
A schedule of a compiled design makes three essential decisions.
The configuration sets which operators can run at once (Section~\ref{subsec:prefill}).
The order sets how the CP interleaves each dispatch's segments, with each operator's segments kept in their own order.
The buffer assignment sets the slot that each use of a buffer takes, since two uses of one slot run in turn even when neither consumes the other's data.
Because operators hand data over through DRAM with no lock between them, a consumer issues only after its producer's final synchronization and any host work between the two, in a separate dispatch.
The number $D$ of dispatches in flight and the packing of dispatches manage only the boundary with the host, so we treat them as host policy, which the composer chooses with the configuration.
The objective is the makespan, which for prefill is the TTFT less the work before the first decoder layer and after the last.
Each configuration comes from the design's own build, changing only the split parameter, with outputs bit-identical to the default's, so either order can run on any of them.
% SOURCE: mlir-air a3e26261 fused_prefill/device.py: Attn(col=...) per group in Config.attn, GCOL0, GNC = 1, 6 as module constants; spec() splits kv_heads evenly, so 1, 2, or 4 attention columns with 8 KV heads (vault lab-split-sweep (1)).
% SOURCE: out-of-tree split modules; logits bit-identical to the default split in every configuration on both models (vault lab-split-sweep (2), (4), (5)).

% VALUE: to choose among orders and splits without running each, an event simulation of the device, the CP, and the host prices a schedule; its form follows the platform (one in-order queue of dispatches, a host timeline with waits, column groups that overlap within a dispatch) and its parameters are the operators' own timings plus a few machine constants measured once by microbenchmarks; the original program runs through the same simulation, so both sides are priced alike; device time, host exposure, and head and tail reported apart
% DECISION: this subsection states the frozen form (dev form, frozen 2026-10-25; amd-npu 12250226, FORM-A2.md; opcord-runtime 3bead38, opcord/model/event_model.py, constants opcord/model/constants/frozen.json), term by term as npu-gap checked it against the code; the rebuilt form (per-split setups and windows, overlap bounded by bytes over the read cap) scored worse and did not freeze (vault decisions log, event-model form, 2026-10-25).
To choose among orders and configurations without running each, we price a schedule from the probes of Section~\ref{subsec:overview} with an analytical event simulation of the device, the CP, and the host, which we call the \emph{event model} and whose form follows the platform's structure.
Queued dispatches run one at a time (Section~\ref{subsec:semantics}), so dispatch $k$ ends at
\begin{equation}
\label{eq:cmd}
e_k = \max\bigl(e_{k-1} + s_k,\; q_k + F\bigr) + \tau_k,
\end{equation}
where $q_k$ is the time the host queues it, after its issue cost, $F$ is the dispatch floor (Section~\ref{subsec:platform}), and $s_k$ is the transition from the previous dispatch, one constant per pair of dispatch kinds (attention or GEMM), negative where the next dispatch's start overlaps the end of the previous one.
A dispatch of GEMMs alone takes the sum of its operators' times alone plus a fixed cost $\gamma$ for each operator after the first.
A dispatch in which attention runs beside GEMMs takes
\begin{equation}
\label{eq:overlap}
\tau_k = \max(a_k, g_k) + c_r + d_r \min(a_k, g_k),
\end{equation}
where $a_k$ and $g_k$ are the two groups' times alone, $r$ marks which of the two is longer, $c_r$ is a fixed cost, and $d_r$ is the share of the shorter group's time that the overlap fails to hide.
On the host side, each dispatch costs an issue, by its kind, and each operator a post-processing step.
The original program runs through the same simulation, from a model of its host program's order, so both sides of every comparison are priced alike.
Its host waits stage by stage where that program does, whereas the composer's host waits on the oldest dispatch once $D$ are in flight.
Finally, the event model adds the work before the first decoder layer, interpolated between that work's own probes at measured prompt lengths, and keeps it apart from the layers' terms for both orders, so an error in it cannot hide behind them.

It prices the LM head from its chunks' probes, apart for the composed order and chunk by chunk within the simulated program for the original one.

The operators' timings depend on the LLM and the configuration, so we measure them once per configuration by dispatching each GEMM alone and each attention chunk alone at several cached-context lengths, and the host's post-processing costs and the work before the first layer once per LLM.
The event model interpolates between measured points, pricing each attention chunk at its position in the prompt, and refuses to price beyond the measured contexts, while an operator with a sliding window takes, past the window, the median of its times measured there.

\subsection{Implementation}
\label{subsec:impl}

% VALUE: the analysis and both passes with their checkers in MLIR-AIE (C++), the loop pass as an opt-in step of the compiler driver that leaves every output byte-identical when off; the composer, the event model, and the split switch as a Python runtime package replacing the host program's dispatch loop on the design's own hardware context; no kernel, driver, or firmware change, and every reconfiguration point stays where the stack put it
The analysis of Section~\ref{sec:order} and both passes, with their checkers, are about 6{,}700 lines of C++ in MLIR-AIE.
The loop pass is an opt-in step of the compiler's driver that runs on the lowered design that the stack's own passes produce.
Switched off, it leaves every instruction stream and configuration the compiler emits byte-identical to the stack's own build.
The composer, with the event model and the switch between configurations, is a runtime package of about 2{,}700 lines of Python that replaces the dispatch loop of the design's host program.
It submits to the design's own hardware context, so OPCORD changes no kernel, driver, or firmware.
