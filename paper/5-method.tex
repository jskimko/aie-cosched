\section{Composing Concurrent Commands}
\label{sec:method}

% VALUE: the composer takes an existing design's per-operator streams, column map, dependency graph, and time estimates, and emits composed commands that run the same kernels, weights, and configuration with bit-identical outputs; it replaces only the host's dispatch loop and makes the two essential decisions, the order within commands and the split, plus the buffer placement they need
We build a composer that takes an existing design's per-operator instruction streams, its map of operators to columns, the dependency graph of its host program, and an estimate of each operator's device time.
From these, it emits a sequence of composed commands that runs the same kernels and weights, and produces bit-identical outputs.
The composer replaces only the host program's dispatch loop and changes no kernel, compiler, driver, or firmware.
It decides which operators share a command (Section~\ref{subsec:plan}), the CP's instruction order within each command (Section~\ref{subsec:order}), where each operator's buffers live (Sections~\ref{subsec:arenas} and~\ref{subsec:rings}), and which split of the columns to use for each regime (Section~\ref{subsec:split}).
Each composed command passes a static legality check before any dispatch (Section~\ref{subsec:compose}), and the event model of Section~\ref{subsec:pricing} prices each candidate.
% SOURCE: amd-npu a0ee2edf44e0 (tag composer-v1.1), prefill-overlap/txn.py (111 lines), merged.py (616), component_model.py (180); Python, on the engine's hardware context.

\subsection{Composing Instruction Streams}
\label{subsec:compose}

\textbf{Segments.}
% VALUE: a composed command is an interleaving of operators' segments that keeps each operator's own order and every instruction once, so only the timing of issue and waits changes
The composer splits each operator's instruction stream, already reduced to its own columns, into the segments of Section~\ref{subsec:formulation}.
A composed command concatenates segments of several operators in a chosen order, keeping each operator's segments in their own order and every instruction exactly once.
Under these rules, an interleaving changes only when each operator's work is issued and awaited, never what the work is.
% SOURCE: txn.segments and txn.compose (amd-npu a0ee2ed prefill-overlap/txn.py); compose asserts each stream's segment order, every op kept once, and equal headers.

\textbf{Legality.}
% VALUE: two operators may interleave only if they cannot disturb each other's device state, which the composer checks statically from the instructions themselves
Two operators may interleave in one command only if they cannot disturb each other's state on the device, which the composer checks from the instructions themselves.
Every register write of an operator must address a column of its own group, and the writes may touch only shim BDs and DMA queues, the operator's own cores' locks, and runtime parameters in its own cores' memory, never core programs, core resets, or memory tiles.
Interleaved operators must patch disjoint argument slots or, as Section~\ref{subsec:arenas} describes, disjoint byte ranges of one slot's buffer.
No operator may write a buffer that another operator in the same command reads or writes.
Operators on the same group, such as several GEMMs, are composed in sequence rather than interleaved, so their writes to that group's registers keep the order of separate commands.
% SOURCE: each check turns red on a defeated input (swapped groups, an unstripped stream, a synchronization before an issue op, a patch onto another group's argument, a duplicated column, a reordered or dropped segment) (lab-prefill-overlap (3), (4)).

\subsection{Argument Arenas}
\label{subsec:arenas}

% VALUE: the existing design binds one buffer per argument slot, so a command holds only one GEMM; we retarget only a patch's byte offset, never its slot, so any number of GEMMs share the GEMM slots through arenas, under an offset bound the composer respects
The configuration's kernel declares a fixed set of argument slots, and the existing design gives each operator kind its own: three slots for a GEMM's input, weights, and output, and three for each attention group.
With one buffer per slot, a command that carries attention can hold only one GEMM.
An address patch names a slot and a byte offset within that slot's buffer.
Retargeting a patch to another slot faults in the IOMMU, whereas changing its byte offset is safe and keeps outputs bit-identical.
We therefore allocate the GEMM inputs, weights, and outputs as sub-buffers of three parent buffers, which we call \emph{arenas}, bound to the GEMM slots, and rewrite only each GEMM's patch offsets.
Any number of GEMMs then share three slots.
The offset field bounds an arena to $2^{31}$ bytes, so the composer splits the weights into arenas of whole layers below that bound, and the GEMMs of one command must share a weight arena.
% SOURCE: nine slots, nargs = 3 + 3 x len(cfg.attn) (mlir-air a3e26261 engine.py:107); address patch = opcode 0x81, argument index at word 8, byte offset at word 10.
% SOURCE: slot moves complete with wrong output and AMD-Vi IO_PAGE_FAULT lines; offset moves inside a parent buffer are bit-identical; two GEMMs at distinct offsets in shared arenas are bit-identical (amd-npu 61c64f9 prefill-overlap/retarget/, lab-prefill-overlap (8)).

\subsection{Planning Commands}
\label{subsec:plan}

% VALUE: the composer list-schedules the dependency graph chunk by chunk rather than stage by stage, so each attention operator meets independent GEMMs of earlier chunks, and it sizes each command so its GEMM work matches the attention work
The existing host program runs each layer stage by stage, so every output projection waits behind the layer's entire attention, and no GEMM is ready to run beside attention.
The composer instead list-schedules the dependency graph chunk by chunk.
At each step, it takes the ready attention operator of the lowest layer and chunk and adds ready GEMMs, in the same order, until their estimated work reaches that of the attention operator.
The GEMMs then run in sequence on columns 1--6 while attention runs on columns 0 and 7.
A step without a ready attention operator packs up to a fixed number of ready GEMMs into one command, following standard practice for amortizing dispatch cost (Section~\ref{subsec:prefill}).
Operators separated by host work never share a command, and a GEMM whose weights lie in another arena waits for a later command.
For an append to a cached context, the composer plans only the new chunks, and their attention estimates use each chunk's absolute index.
% SOURCE: merged.plan (a0ee2ed): qkv(L, c) after down(L-1, c); attn(L, c) after qkv(L, 0..c); o after attn; gate and up after o; down after gate and up; an optional cap on the GEMMs per attention command; a fixed number of GEMMs per command without attention.

\subsection{Instruction Order}
\label{subsec:order}

% VALUE: within a command, the CP opens every group's work first and then places each synchronization at its predicted completion, followed by the issue it gates, so no synchronization holds back another group's work; the order is fixed before dispatch from the estimates
Within a command, the order of synchronizations decides how long each group waits for its next issue (Figure~\ref{fig:order}).
In turn, the CP would issue the first GEMM, then walk the attention stream to its end, and only then issue the second GEMM, so the GEMM group idles behind attention's synchronizations.
The composer instead issues the opening segments of both attention columns and of the first GEMM, and then places every synchronization in order of its \emph{predicted completion}, each followed by the issue it gates.
A GEMM's synchronizations are predicted to complete after the sum of the estimates of the GEMMs before it, and attention's mid-stream synchronizations at fixed fractions of its estimate.
Attention's two columns are treated as two groups, so their segments alternate, which removes the serialization measured inside the attention operator (Section~\ref{subsec:semantics}).
The order is static: the estimates fix it when the command is built, and the device executes it without host involvement.
When issue costs are negligible, the estimates are exact, and the host work is hidden, the CP never blocks on a later-completing operator while an earlier one's successor waits, so the order matches the list schedule of the groups without a CP.

\subsection{Buffer Rings}
\label{subsec:rings}

% VALUE: with commands in flight and chunks interleaved, each buffer role needs several slots; the composer derives each ring's depth from the plan's live intervals and checks that no slot is reused before its reader is done
Once operators of several chunks are in flight, a GEMM's input and output buffers cannot be reused per stage as in the existing host program.
For each buffer role, the composer derives a ring of slots in the arenas from the plan: each use of a buffer lives from its producer's write to its last reader's completion, and interval colouring assigns slots so that no two overlapping uses share one.
A separate check asserts, over the whole plan, that no slot is reused before its previous reader has completed.
The depths follow from the plan and are not set by hand.
For example, every QKV input of a layer is written before the layer's first QKV command completes, so that ring needs one slot per chunk.
% SOURCE: merged.colour, assert_no_hazard, and Layout (a0ee2ed); the hazard check turns red on an overlapping slot; ring depths at 4,096 tokens: shared 2048-wide input 32, 8192-wide input 4, outputs 4-18 (lab-prefill-overlap (9)).

\subsection{Host Boundaries}
\label{subsec:host}

% VALUE: host work between commands forces boundaries; keeping D commands in flight hides the host work and the boundary cost but delays which operators are ready, so the depth and the packing trade overlap against readiness
The existing host program computes normalizations, rotary embeddings, and residuals on the CPU, so a dependence that crosses the host forces a command boundary.
The composer keeps $D$ commands in flight: it queues the next command before it waits on the oldest, and it processes a command's outputs on the host while later commands run.
A command can therefore carry only operators whose inputs come from commands at least $D$ positions earlier.
A deeper queue hides more of the boundary cost and of the host work, but it leaves fewer operators ready to share a command with attention.
The composer models this delay directly, so the queue depth and the packing of GEMMs are chosen for each prompt length (Section~\ref{sec:eval}).

\subsection{Choosing the Split}
\label{subsec:split}

% VALUE: the split of columns between attention and GEMMs is a build-time parameter of the existing design, fixed by hand; the legal splits follow from the heads, each split is a separate configuration built in seconds, and the composer needs only more argument slots to serve it
The existing design fixes the split of columns between attention and the GEMMs by hand: attention groups are listed per column, and the GEMMs take a contiguous block of the remaining columns.
Since each attention group serves an equal share of the KV heads, a model with 8 KV heads admits attention on 1, 2, or 4 columns, with the GEMMs on the other 7, 6, or 4.
We build each split as its own configuration from the unchanged design source, which takes seconds, and each split's outputs are bit-identical to those of the default split.
The composer serves every split with one change, namely three argument slots per attention group instead of a fixed six.
A split also changes each GEMM's width per column, so the composer checks every GEMM's encoded iteration count and stride against the shim BD's field limits before it uses the split.
% SOURCE: mlir-air a3e26261 fused_prefill/device.py: Attn(col=...) per group in Config.attn, GCOL0, GNC = 1, 6 as module constants; spec() splits kv_heads evenly, so 1, 2, or 4 attention columns with 8 KV heads (vault lab-split-sweep (1)).
% SOURCE: out-of-tree split modules, builds of 13-14 s; logits bit-identical to the default split in every configuration on both models (vault lab-split-sweep (2), (4), (5)).
% SOURCE: BD iteration wrap 6 bits (at most 64 rounds), stride 20 bits (words); the four-column split's LM-head GEMM runs 48 rounds; decoded from aie-rt xaie2pgbl_params.h fields with a round-trip check (vault lab-split-sweep (5)).

% VALUE: the composer picks the split per regime with the event model from one probe per split, and keeps the chosen splits resident so a deployment switches between them at a turn boundary for a suspend and resume; a cached context stays with the split that computed it
For each split, the composer probes every operator alone once and predicts the TTFT of each regime with the event model (Section~\ref{subsec:pricing}), and it picks the split with the lower prediction.
More attention columns shorten attention, whose time grows with the context, but lengthen every GEMM, so the choice depends on the prompt length and on the cached context.
A deployment keeps each chosen split resident in its own hardware context, with its own copy of the weights, and switches between them at a turn boundary by suspending one context and resuming the other.
The KV cache of a cached context is laid out by the attention groups of the split that computed it, so a conversation that changes split must lay out or recompute its context again, which we do not evaluate.
% SOURCE: per-split probes at n = 2,048, prediction with component_model.simulate (amd-npu 0f61651 prefill-overlap/g1_split_model.py, vault lab-split-sweep (6)-(7)); switch = suspend + resume + first prefill in one process, both splits' weights resident (vault lab-split-sweep (5)).
% SOURCE: the four-column split's GEMMs are 27% (1B) and 35% (Qwen3-4B) slower than on six columns, and its attention slope per chunk 3.0-3.1x lower than the default split's existing stream (vault lab-split-sweep (4)-(5)).
