\section{Background}
\label{sec:background}

% VALUE: the array computes in parallel once configured, but the host reaches it only through instruction streams that one in-order CP executes
Once configured, the AI Engine array of an XDNA~2 NPU computes on all of its columns at once, yet the host reaches it only through instruction streams that one in-order command processor executes.

\subsection{AMD XDNA~2 NPU}
\label{subsec:platform}

\textbf{AI Engine Array.}
% VALUE: 8 columns of shim, memory, and compute tiles; DMAs follow BDs, locks hand buffers over; a design is one configuration; once configured it runs data-driven, so disjoint columns compute at once; defines the column group
The AMD XDNA~2 neural processing unit (NPU) in Ryzen\texttrademark{} AI processors has an array of AI Engine (AIE) tiles in 8 columns~\citep{linux-amdnpu}, each holding, from the bottom, a shim tile that moves data to and from DRAM, a memory tile, and 4 compute tiles, which are VLIW, SIMD vector cores with local memory~\citep{amd_am027,linux-amdnpu}.
Direct memory access (DMA) engines move data over a stream switch network by following buffer descriptors (BDs), which can chain to one another, and locks hand each buffer from its producer to its consumer~\citep{amd_am027}.
A design is one configuration of the array, namely its core programs, stream routes, BDs, and locks, which a compiler such as MLIR-AIE~\citep{hunhoff2025iron,mlir-aie-repo} or MLIR-AIR~\citep{wang2026mlirair} emits.
The configured array runs data-driven, so cores on different columns compute independently whenever their input locks are released, and we call the columns that one operator occupies its \emph{column group}.
% SOURCE: the XDNA 2 topology is the kernel documentation's, which states 4 rows of compute tiles in 8 columns, 1 memory-tile row per column, and 4,096 KB of L2 (docs.kernel.org/accel/amdxdna/amdnpu.html, read 2026-10-21; the same citation FCPR Section 2.1 uses for the column count). Confirmed on the Ryzen AI Max+ 395 NPU of this paper's machine. NOTE: Rico et al. (IEEE Micro 2024) is the FIRST XDNA generation (5 columns, 10 TOPS) and must not be cited for an XDNA 2 figure.
% SOURCE: BD chaining is mechanism 6 of Table mech (4-method); locks on DMA BDs and core locks are mechanisms 7 and 10.

\textbf{Command Processor.}
% VALUE: the host reaches the array only through commands whose instruction streams one in-order CP executes; register write, address patch, issue (returns at once), synchronization (blocks), so the CP's order decides when each column receives work; contrast with prior CP work on reconfiguration
The host never drives the array directly but submits \emph{commands}, each carrying an \emph{instruction stream} that the NPU's command processor (CP) executes in order~\citep{rico2024xdna,linux-amdnpu}.
A \emph{register write} configures shim BDs, DMA queues, locks, or a core's runtime parameters, and an \emph{address patch} writes a host buffer's address into a shim BD.
An \emph{issue} pushes a BD into a shim DMA queue and returns at once, so the transfer proceeds while the CP moves on, whereas a \emph{synchronization} blocks the CP until a named transfer completes.
The CP's instruction order therefore decides when each column receives work, and a synchronization on one column delays every later issue, whichever column it targets.
Prior work characterizes and reduces the cost of configuring accelerators~\citep{vandelm2026configwall} and models the time of an array reconfiguration as the CP's critical path~\citep{fcpr2027}, whereas we study the order in which the CP issues work within one configuration.

% SOURCE: the existing prefill's operators write only shim BDs and queues (row 0, 0x1D000/0x1D200), their own cores' lock registers (0x1F000), and runtime-parameter words in their cores' memory (0x3C00 GEMM, 0x2000 attention); no program loads, core resets, or memory-tile writes (decoded from the shipped streams, lab-prefill-overlap (3)).

\textbf{Host Runtime.}
% VALUE: commands go to a hardware context that holds one configuration and runs them in submission order; argument slots bind buffers for address patches; each command costs a fixed dispatch floor F that queuing partly hides
The host submits commands through XRT~\citep{xrt-repo} and the amdxdna driver~\citep{xdna-driver} to a \emph{hardware context}, which holds one configuration and runs its commands in submission order.
Each command binds host buffers to the \emph{argument slots} that the configuration's kernel declares, and an address patch names its buffer by a slot and a byte offset.
Submitting and completing a command costs a fixed time that we call the \emph{dispatch floor} $F$, which is about 0.1\ms{} on our platform.
Queuing further commands before waiting on the first hides part of $F$ behind the device's work.
% SOURCE: XRT empty dispatch (4 KB bypass), 93.0-98.5 us at every bracket of lab-prefill-device (3); 92-99 us in lab-prefill-overlap (3).

\textbf{Software Stacks.}
% VALUE: three stacks (MLIR-AIR from loop nests, IRON close to the metal, FastFlowLM as binaries only) reach the array through the same commands and streams, so one analysis reads all three, closed ones included
% DECISION: no claim about how any stack chose its order ("hand-tuned", "expert"); FastFlowLM is described by what it ships.
Three stacks produce LLM designs for XDNA~2.
MLIR-AIR maps loop nests onto the array as fused multi-operator designs~\citep{wang2026mlirair}, IRON offers a close-to-metal Python interface to MLIR-AIE~\citep{hunhoff2025iron}, and FastFlowLM ships its designs and the engines that issue them as binaries~\citep{fastflowlm-repo}.
All three reach the array through the same commands and instruction streams, so one analysis can read the designs of each, closed ones included (Section~\ref{subsec:closed}).
% SOURCE: FastFlowLM's engines reach the runtime through libhrx and ship as compiled libraries and xclbins (FastFlowLM 44d01787, lib/hrx/libgemma4e_flash.so; vault lab-cosched-passes (14)).

\subsection{LLM Inference on the NPU}
\label{subsec:prefill}

% VALUE: prefill and TTFT; the decoder layer's operators; the existing expert prefill puts GEMMs and attention on disjoint column groups of one configuration (its default split), so its operators differ only in their streams; it runs a layer stage by stage over 128-token chunks with host work between commands
\emph{Prefill} processes a prompt to produce the first output token, and its latency is the TTFT.
Each decoder layer applies a QKV projection, attention, an output projection, and a gated feed-forward network of gate, up, and down projections.
MLIR-AIR's open fused prefill~\citep{wang2026mlirair}, which reimplements designs of FastFlowLM~\citep{fastflowlm-repo}, places every operator of a layer in one configuration, with the GEMMs on columns 1--6 and attention on columns 0 and 7, which is its default \emph{split}, namely the number of columns that attention takes (Section~\ref{subsec:split}).
Its cores loop indefinitely and take their work from runtime parameters, so its operators differ only in their instruction streams, each of which keeps only its own operator's columns.
The host runs each layer stage by stage over chunks of 128 tokens, finishing every chunk's QKV projection before any attention and every attention before the remaining projections, and its CPU computes the normalizations, rotary embedding, and residual additions between commands.

% VALUE: decode is a separate design that generates one token per step and whose attention reads the KV cache of the whole context, so its per-token time grows with the context
\emph{Decode} generates one token per step with a separate design, namely MLIR-AIR's fused decode, in which every layer's attention reads the KV cache of the whole context, so its time per token grows with the length of the context.
