\section{Background}
\label{sec:background}

\subsection{AMD XDNA~2 NPU}
\label{subsec:platform}

% VALUE: the array: 8 columns of shim, memory and core tiles; DMAs follow chained BDs on channels with task queues, locks hand buffers over, routes cross switches whose ports buffer data; a configuration and a design; each operator's columns are its column group
% SOURCE: the XDNA 2 topology is the kernel documentation's, which states 4 rows of compute tiles in 8 columns, 1 memory-tile row per column, and 4,096 KB of L2 (docs.kernel.org/accel/amdxdna/amdnpu.html, read 2026-10-21). Confirmed on the Ryzen AI Max+ 395 NPU of this paper's machine. Rico et al. (IEEE Micro 2024) is the first XDNA generation (5 columns) and is not cited for an XDNA 2 figure.
% SOURCE: tile anatomy, DMA channels with task queues (pp. 24, 35, 59), and the stream switch with its ports (pp. 18-19) (AM027 v1.1).
% DECISION: column groups are how today's LLM designs map their flows, not a hardware rule (author, 2026-10-24).
\textbf{AI Engine Array.}
\CLS{E}An AMD XDNA~2 NPU is a spatial dataflow array of AI Engine tiles in 8 columns~\citep{linux-amdnpu}.
\CLS{E}Each column holds a shim tile that reaches DRAM, a memory tile, and 4 core tiles with local memory.
\CLS{E}Direct memory access (DMA) engines move data by following chainable buffer descriptors (BDs), and locks hand each buffer from its producer to its consumer~\citep{amd_am027}.
\CLS{E}Each DMA channel takes work from its own \emph{task queue}, and data travels between tiles on \emph{routes} through the tiles' stream switches, whose ports buffer data in flight.
\CLS{E}A \emph{configuration} is the array's core programs, stream routes, BDs, and locks, which a compiler such as MLIR-AIE~\citep{mlir-aie-repo} or AIR~\citep{wang2026mlirair} emits, and a \emph{design} is one or more configurations with the host program that issues their dispatches.
\CLS{E}We call the columns that one operator occupies its \emph{column group}.

% VALUE: the CP: a dispatch's instruction stream runs in order; issue returns at once, a synchronization blocks; so a synchronization delays every later issue, and nothing reorders across engines (that order is the array's schedule: the intro's insight, measured in Section 3)
% SOURCE: no reordering across engines: XRT run list, /opt/xilinx/xrt/include/xrt/experimental/xrt_kernel.h:21 (XRT 2.25.0); the in-order and blocking behavior rests on the paired measurements of Section 3.1.
\textbf{Command Processor.}
\CLS{E}The host drives the array through \emph{dispatches}, and each is a command buffer whose \emph{instruction stream} the NPU's CP executes in order.
\CLS{E}An \emph{issue} pushes a BD into a shim DMA channel's task queue and returns at once, whereas a \emph{synchronization}, or wait, blocks the CP until a named transfer completes.
\CLS{D}A synchronization on one column therefore delays every later issue, whichever column it targets, and neither the host runtime nor the CP reorders work across engines (Section~\ref{subsec:semantics}).

% VALUE: the host side: dispatches go through XRT and the driver to a hardware context, which holds one configuration and has one CP that runs them in submission order; each dispatch costs a fixed floor F
% SOURCE: XRT empty dispatch (4 KB bypass), 93.0-98.5 us at every bracket of lab-prefill-device (3); 92-99 us in lab-prefill-overlap (3).
\textbf{Host Runtime.}
\CLS{E}The host submits dispatches through XRT~\citep{xrt-repo} and the amdxdna driver~\citep{xdna-driver} to a \emph{hardware context}, which holds one configuration at a time and has one CP that runs its dispatches in submission order.
\CLS{E}Submitting and completing a dispatch costs a fixed \emph{dispatch floor} $F$.

\subsection{Modular and Fused Designs}
\label{subsec:spectrum}

% VALUE: the partitionings of a design: into configurations (modular, each operator its own configuration; fused, several operators resident, which can run at once), into dispatches, and into buffers per loop role; the three stacks we read
% DECISION: the modularity-fusion spectrum is the author's framing (2026-10-24): modular designs trade reconfiguration time for ease of programming, fused designs avoid reconfiguration and inherit an order; neither end is called wrong. No claim about how any stack chose its order; FastFlowLM is described by what it ships.
% SOURCE: IRON's OperatorSequence keeps each operator its own aie.device and emits configure/run per runlist entry in runlist order (amd-iron 1fd3dab, iron/common/sequence.py:89-96, 286; iron/common/compilation/sequence.py:243-324). FastFlowLM's engines reach the runtime through libhrx and ship as compiled libraries and xclbins (FastFlowLM 44d01787, lib/hrx/libgemma4e_flash.so; vault lab-cosched-passes (14)).
\CLS{E}A design's first partitioning, into configurations, places it along a spectrum.
\CLS{E}At the spectrum's \emph{modular} end, a design gives each operator its own configuration and reconfigures the array between operators.
\CLS{E}At its \emph{fused} end, a design keeps several operators resident in one configuration, which avoids reconfiguration and lets operators on disjoint parts of the array run at once.
\CLS{E}A second partitioning splits a fused design's work into dispatches, and a third decides whether each role in a loop keeps one buffer or several.
\CLS{E}IRON~\citep{hunhoff2025iron}, an interface to MLIR-AIE that can also express fused designs, composes an LLM as a sequence of operators that each reconfigure the whole array, whereas AIR generates fused designs.
\CLS{E}FLM~\citep{fastflowlm-repo} ships fused flash designs and a modular per-operator engine as binaries with the runtime that issues them.

\subsection{LLM Inference on the NPU}
\label{subsec:prefill}

% VALUE: the layer's operators, all GEMMs but attention; AIR's fused prefill in one configuration, the original program, the split and its supported configurations; 128-token chunks run stage by stage, attention reading earlier chunks; the host's post-processing steps between dispatches; decode is a separate fused design whose attention reads the whole context's KV cache
% SOURCE: mlir-air a3e26261 programming_examples/llms/shared/fused_prefill/: device.py (column map cols(cfg)), engine.py (strip_columns), dense.py (_mix_all, stage-major order), hostops.py.
% SOURCE: mlir-air a3e26261 fused_prefill/device.py: Attn(col=...) per group in Config.attn, GCOL0, GNC = 1, 6 as module constants; spec() splits kv_heads evenly, so 1, 2, or 4 attention columns with 8 KV heads (vault lab-split-sweep (1)); logits bit-identical to the default split in every configuration on both models (lab-split-sweep (2), (4), (5)).
% SOURCE: mlir-air 44e8d8f7 programming_examples/llms/shared/fused_prefill/device.py:24-30, M = 128 rows per chunk as a module constant, TM = 32 per core tile, HR = M // TM = 4 core rows of the 6 x 4 herd; no build flag (npu-gap D4, 2026-10-25), so no chunk-size baseline exists without changing the design.
\CLS{E}In each decoder layer, attention sits between the QKV projection and the remaining projections, all of which are GEMMs.
\CLS{E}AIR's open fused prefill places every operator of a layer in one configuration, by default with the GEMMs on columns 1--6 and attention on columns 0 and 7, and we call this design the \emph{original program}.
\CLS{E}We name its configuration by its \emph{split}, the number of columns attention takes, and call each value the build admits a \emph{supported configuration}.
\CLS{E}An LLM with 8 KV heads admits $S_1$, $S_2$, and $S_4$, with attention on 1, 2, or 4 columns and $S_2$ the default.
\CLS{E}The host runs each layer stage by stage over 128-token chunks, a size the design fixes, and finishes every chunk's QKV projection before any attention and every attention before the remaining projections.
\CLS{E}Attention on one chunk reads the QKV projections of that chunk and earlier ones.
\CLS{E}Between dispatches, the host's CPU post-processes the operators' outputs in steps such as normalization and residual addition.
\CLS{EL}\emph{Decode} uses a separate design, AIR's fused decode, whose attention reads the KV cache.

% VALUE: false and true dependences defined once, the false kinds (name, order) with their sources and the rewrite that removes each; the critical-path rule (cited), which Section 3's condition refines for this NPU
% DECISION: the kinds are defined once, here, with their sources (author, 2026-10-26), and called classical; Kuck names anti and output dependences (p. 208) but no order class; renaming is Tomasulo's (p. 29, doubling); the order kind is NVIDIA's single-work-queue false dependence (Kepler GK110 whitepaper: "false intra-stream dependencies", "tailor the launch order"); "false dependence" is an established term that the paper uses and does not coin, and no claim is made about who originated the classes.
% SOURCE: Kelley and Walker, p. 317: "All the activities in a critical-path are limiting in the sense that a delay in any one of them will cause a comparable delay in the completion of the project" (verify-citations-pdf.md).
\CLS{DL}Work that waits on other work whose results it does not consume has a \emph{false dependence}; where it consumes them, the dependence is \emph{true}.
\CLS{EL}One kind of false dependence is a classical anti or output dependence~\citep{kuck1981dependence}, a \emph{name} dependence on storage that two uses need not share, which renaming removes~\citep{tomasulo1967}.
\CLS{EL}The other is a wait that the issue order alone places between independent work, like those on a GPU with a single hardware work queue~\citep{nvidia-kepler-gk110}, which we call an \emph{order} dependence and which reordering removes.
\CLS{SL}Removing a false dependence can shorten a run only where it lies on the run's critical path~\citep{kelley1961critical}.
