\section{Background and Motivation}
\label{sec:background}

\subsection{AMD XDNA~2 NPU}
\label{subsec:platform}

\textbf{AI Engine Array.}
% VALUE: the array is columns of tiles that run data-driven once configured, so disjoint columns can compute at the same time; a design is one configuration
The AMD XDNA~2 neural processing unit (NPU) in AMD Ryzen\texttrademark{} AI processors contains an array of AI Engine (AIE) tiles in 8 columns~\citep{linux-amdnpu}.
Each column holds, from the bottom, a shim tile that moves data between the array and DRAM, a memory tile, and 4 compute tiles, which are VLIW, SIMD vector cores with local memory~\citep{amd_am027,linux-amdnpu}, so the array has 32 compute tiles and 4\,MB of memory-tile storage in all~\citep{linux-amdnpu}.
Direct memory access (DMA) engines in the tiles move data over a stream switch network, each transfer described by a buffer descriptor (BD), and locks synchronize producers and consumers~\citep{amd_am027}.
A design is one configuration of the array, namely its core programs, stream routes, BDs, and locks, which a compiler such as MLIR-AIE~\citep{hunhoff2025iron,mlir-aie-repo} or MLIR-AIR~\citep{wang2026mlirair} emits.
Once configured, the array executes data-driven: a core runs when its input locks are released, so cores on different columns compute independently whenever their inputs arrive.
% SOURCE: the XDNA 2 topology is the kernel documentation's, which states 4 rows of compute tiles in 8 columns, 1 memory-tile row per column, and 4,096 KB of L2 (docs.kernel.org/accel/amdxdna/amdnpu.html, read 2026-10-21; the same citation FCPR Section 2.1 uses for the column count). Confirmed on the Ryzen AI Max+ 395 NPU of this paper's machine. NOTE: Rico et al. (IEEE Micro 2024) is the FIRST XDNA generation (5 columns, 10 TOPS) and must not be cited for an XDNA 2 figure.

\textbf{Command Processor.}
% VALUE: the host reaches the array only through instruction streams that one in-order CP executes; an issue returns at once, a synchronization blocks the CP, so the CP's order decides when each column receives work
The host does not drive the array directly.
Instead, it submits commands, each carrying an instruction stream that the NPU's command processor (CP) executes in order~\citep{rico2024xdna,linux-amdnpu}.
The instructions this work uses are of three kinds.
\emph{Register writes} configure shim BDs and DMA queues, lock values, and runtime parameters in a core's memory.
An \emph{address patch} writes a host buffer's address into a shim BD, where the buffer is named by one of the command's argument slots plus a byte offset.
A \emph{synchronization} blocks the CP until a named DMA transfer signals its completion.
Pushing a BD into a DMA queue returns immediately, so the transfer proceeds while the CP moves on, and we call such instructions \emph{issue} instructions.
Consequently, the CP's instruction order decides when each column receives work, and a synchronization on one column delays every later issue, whichever column it targets.
The NPU can also be divided into partitions of contiguous columns that run independent applications~\citep{rico2024xdna}, whereas the work this paper studies runs in one partition.
Prior work models the time of an array reconfiguration as the CP's critical path, namely its commands and its waits on transfers~\citep{fcpr2027}, and the cost of configuring an accelerator has been characterized and reduced across several of them~\citep{vandelm2026configwall}.
% SOURCE: instruction encoding, mlir-air a3e26261 programming_examples/llms/shared/fused_prefill/insts.py: TXN v1.0 stream; address patch = opcode 0x81 (argument index at word 8, byte offset at word 10); synchronization = opcode 0x80.
% SOURCE: the existing prefill's operators write only shim BDs and queues (row 0, 0x1D000/0x1D200), their own cores' lock registers (0x1F000), and runtime-parameter words in their cores' memory (0x3C00 GEMM, 0x2000 attention); no program loads, core resets, or memory-tile writes (decoded from the shipped streams, lab-prefill-overlap (3)).

\textbf{Host Runtime.}
% VALUE: commands go to a hardware context, run in submission order, bind buffers through a fixed set of argument slots, and each costs a fixed dispatch time that queuing can partly hide
The host submits commands through XRT~\citep{xrt-repo} and the amdxdna driver~\citep{xdna-driver} to a \emph{hardware context}, which holds one configuration of the array.
A hardware context runs its commands in submission order.
Each command binds host buffers to the argument slots that the configuration's kernel declares, and the command's address patches refer to these slots.
Submitting and completing a command costs a fixed time, which we call the \emph{dispatch floor} $F$, independent of the work it carries: an empty command takes about 0.1\ms{} on our platform.
The host can queue further commands before it waits on the first, which hides part of the dispatch floor behind the device's work.
% SOURCE: XRT empty dispatch (4 KB bypass), 93.0-98.5 us at every bracket of lab-prefill-device (3); 92-99 us in lab-prefill-overlap (3).

\textbf{Software Stacks.}
% VALUE: three stacks produce LLM designs for the NPU: MLIR-AIR compiles from loop nests, IRON is a close-to-metal Python interface, and FastFlowLM ships hand-tuned designs as binaries; all three reach the array through the same commands and instruction streams, so one analysis can read all of them
Three stacks produce LLM designs for XDNA~2.
MLIR-AIR maps loop nests onto the array and builds fused multi-operator designs~\citep{wang2026mlirair}, IRON offers a close-to-metal Python programming interface to MLIR-AIE~\citep{hunhoff2025iron}, and FastFlowLM ships hand-tuned designs as binaries~\citep{fastflowlm-repo}.
All three reach the array through the same commands and instruction streams, so one analysis can read the designs of each (Section~\ref{subsec:closed}).
% SOURCE: FastFlowLM's engines reach the runtime through libhrx and ship as compiled libraries and xclbins (FastFlowLM 44d01787, lib/hrx/libgemma4e_flash.so; vault lab-cosched-passes (14)).

\subsection{LLM Inference on the NPU}
\label{subsec:prefill}

% VALUE: the existing expert prefill places GEMMs and attention on disjoint columns in one configuration, so its operators differ only in their instruction streams; it runs a layer stage by stage with host work between commands
Prefill processes a prompt to produce the first output token, and its latency is the time-to-first-token (TTFT).
Each decoder layer applies a QKV projection, attention, an output projection, and a gated feed-forward network of gate, up, and down projections.
The open expert prefill of MLIR-AIR~\citep{wang2026mlirair}, which reimplements designs of FastFlowLM~\citep{fastflowlm-repo}, places every operator of a layer in one configuration, with the GEMMs on columns 1--6 (24 cores) and attention on columns 0 and 7 (one group of 4 cores per column).
Its cores loop indefinitely and take their work from runtime parameters, so its operators differ only in their instruction streams, and each command keeps only the instructions for its own operator's columns.
The prompt is processed in chunks of 128 tokens, and the host runs a layer stage by stage: the QKV projections of all chunks, then each chunk's attention, then each chunk's remaining projections.
The host CPU computes the normalizations, the rotary position embedding, and the residual additions between commands.
% SOURCE: mlir-air a3e26261 programming_examples/llms/shared/fused_prefill/: device.py (column map cols(cfg); "one PDI serves every op and shape and the ops differ only in their insts"), engine.py (strip_columns), dense.py (_mix_all, stage-major order), hostops.py; README.md: "Some of the LLM implementations in this directory reimplement AMD NPU LLM designs originally developed by the FastFlowLM team".

% VALUE: an agent's turn appends new tokens to a cached context and then decodes; the prefill design serves appends because positions are absolute; decode is a separate design that reads the whole KV cache per token
An agent's turn appends a few hundred to a few thousand new tokens, such as a tool's output, to a long context whose KV cache is already computed, and then decodes a few hundred output tokens.
The prefill design serves such an \emph{append} unchanged, because its rotary embedding, KV append, and attention take absolute token positions, so chunk $c$ of an append to an $L$-token context attends to $L/128 + c + 1$ chunks of keys.
Decode generates one token per step with a separate design, MLIR-AIR's fused decode, in which every layer's attention reads the KV cache of the whole context.
% SOURCE: the engine's RoPE, KV append, and attention take absolute positions, and only prefill() starts at 0 (vault lab-decode-long-context (2), lab-agent-step (1)); appends are bit-identical to a full prefill of L + N tokens (lab-agent-step (2)).

% VALUE: agent steps are short appends to long cached contexts with short outputs; on GPU servers with prefix caching, prefill is a small share of agent LLM time, whereas on the NPU it is a large share of a turn, which is why prefill matters here
Traces of coding agents show that a median step appends 875 new tokens to a cached prefix of 119K tokens and generates 214 tokens~\citep{zhu2026tracelab}.
On GPU servers that keep the prefix cached, prefill accounts for only 1.4--9.0\% of an agent's LLM time~\citep{yuan2026agentic}.
On the NPU, prefill accounts for \E{6--54\%} of an agent's turn, depending on the cached context and the append, so the time from a tool's output to the first new token is a large part of what a user waits for (Section~\ref{subsec:turns}).
% SOURCE: TraceLab Section 1 (medians over ~4,300 Claude Code and Codex sessions, ~350,000 steps) and Table 8; Yuan et al. Section on prefill versus decode time and Fig. 9 (Qwen3.6-27B and Gemma4-31B on two H100 NVL GPUs with vLLM, no context thrashing); both PDFs read 2026-10-15.
% SOURCE: measured whole turns (append + 250 decode tokens), prefill share of the existing turn: Llama-3.2-1B 6-54% with the KV handoff, Qwen3-4B 7-48% before its handoff rerun, over L in {4k, 16k, 28k} and N in {512, 1k, 4k} (vault ch3-formulation, G2/G2b and Qwen3-4B measured turns).

\textbf{Column Groups in Prefill.}
% VALUE: the existing prefill issues one operator per command, so its column groups take turns; the device is busy almost all the time, but on one group at a time, and attention's growing share is time the GEMM columns sit idle
The existing prefill issues one operator per command, which amounts to about 1{,}500 commands for a 2{,}048-token prompt.
Figure~\ref{fig:busy} shows the resulting split of TTFT: device-busy time accounts for 92--97\% of it, and attention's share grows from 12\% to 49\% between 512 and 4{,}096 tokens.
Because the commands run in submission order, columns 1--6 idle while attention runs, and columns 0 and 7 idle while the GEMMs run, although neither group consumes the other's current work.
The device is thus busy almost all of the time, but on only one column group at a time.

\textbf{Columns of One Operator.}
% VALUE: the same loss occurs inside one operator: the existing attention stream starts column 7 only after waiting on column 0, which costs a third of attention's device time
The existing attention stream issues column~7's inputs only after two synchronizations on column~0's key and value transfers, which complete when column~0 is about half done.
Alternating the two columns' segments, so that both columns start before the CP waits on either, reduces attention's device-busy time to $0.67\times$ that of the existing order at every chunk of a 2{,}048-token prompt, with bit-identical outputs.
Each column's half alone takes the same time within 1\%, so the difference comes from the CP's instruction order rather than from an imbalance of work.
Since attention's share grows with the prompt, this loss grows with it.
% SOURCE: decoded from the shipped a_32_4_0_0 stream, mid-stream synchronizations at ops 70, 75 (column 0) and 92, 97 (column 7); column 7's issue (ops 81-91) follows column 0's two mid-stream synchronizations (vault lab-prefill-overlap (4)).
% SOURCE: (alternated - F) / (existing - F) = 0.666-0.668 on 7 pairs, chunks 2-14 at 2,048 tokens; column 7 alone / column 0 alone = 0.994-1.010 (amd-npu 17f7ec3 ovl4/, vault lab-prefill-overlap (5)c); at absolute chunks 16-255: Qwen3-4B 0.66-0.68; Llama-3.2-1B 0.66 / 0.57 / 0.41 / 0.43 / 0.68 / 0.67 / 0.66, lower at its mid-range chunks (vault lab-agent-step (4)).

\textbf{Transfers in Decode.}
% VALUE: decode's per-token time grows linearly with context and attention becomes most of it; attention reads the KV cache at half the platform's read rate because the single-buffered KV loop serializes each block's transfer behind the previous block's compute, not because of the transfer or its placement
The existing decode design places attention's cores on columns 3 and 4 and reads the KV cache through those columns' two shim tiles.
Its time per token grows linearly with the context, within 0.2\% between 2{,}048 and 32{,}704 tokens, and attention's share of that time grows from 13\% to 70\% over the same range.
During attention, the design reads the KV cache at 51\% of the DRAM read cap measured in the same batch.
The transfer is not the limit: a build that streams 30{,}720 further positions with no further compute reads them at the two shim tiles' full rate, 88\% of the cap.
Nor is the CP's order the limit, since each layer issues the next projection's weights before it waits on the KV cache.
Instead, the design's KV loop is single-buffered, because its running maximum and accumulator live across blocks and MLIR-AIR's double-buffering transformation declines such loops, so each block's transfer waits for the compute on the previous block, which adds 41\% of the time per position.
Spreading attention over more columns would therefore gain little, since the transfer alone already reads near the cap.

% SOURCE: footprint from the build's npu.air.mlir: KV readback on shims 3 and 4, attention cores on columns 3 and 4 (vault lab-decode-long-context (6)).

\textbf{The Closed Stack.}
% VALUE: in the one captured prefill, the closed stack issues one group per command as well, so its column groups take turns in the same way; its own decode mapping double-buffers keys and values, the transfer-side name dependences, and its score handoff is not described as buffered
In the one capture we analyse, FastFlowLM's prefill of Gemma-4-E2B issues one column group per command (Section~\ref{subsec:closed}), so its attention and GEMM columns also take turns, although the engine is tuned by hand. That label depends on how an instruction is attributed to a group: under the rule we registered first, which attributes by the column an instruction addresses, the same capture is mixed rather than serial, and we settled the rule we use after taking the capture. Appendix~A gives both labels and the evidence for the rule we chose.
In decode, its authors' Gemma3 mapping double-buffers the keys and values of attention~\citep{du2026gemma3}, the two name dependences on the transfer side, whereas its handoff of scores between the two attention cores is not described as buffered.
