\subsection{AMD XDNA~2 NPU}
\label{subsec:platform}

\textbf{AI Engine Array.}
% VALUE: a spatial dataflow array of 8 columns of shim, memory, and compute tiles; DMAs follow BDs, locks hand buffers over; a design is one configuration; once configured it runs data-driven, so a design maps each operator's flow onto a group of tiles that computes independently; today's LLM designs map those groups to whole columns (the column group), which the hardware does not require
The AMD XDNA~2 neural processing unit (NPU) in Ryzen\texttrademark{} AI processors is a spatial dataflow array of AI Engine (AIE) tiles in 8 columns~\citep{linux-amdnpu}.
Each column holds a shim tile that moves data to and from DRAM, a memory tile, and 4 compute tiles with local memory.
% SOURCE: tile anatomy (AM027): the shim tile is at the bottom of each column with the memory tile above it; the compute tiles are VLIW, SIMD vector cores; DMAs move data over a stream switch network.
Direct memory access (DMA) engines move data by following buffer descriptors (BDs), which can chain, and locks hand each buffer from its producer to its consumer~\citep{amd_am027}.
A configuration of the array is its core programs, stream routes, BDs, and locks, which a compiler such as MLIR-AIE~\citep{mlir-aie-repo} or MLIR-AIR emits, and a design is one or more configurations with the host program that issues their commands.
The configured array runs data-driven, so a design maps each operator's flow onto a group of tiles that computes independently whenever its input locks are released.
The LLM designs we study map each group to whole columns, which the hardware does not require, and we call the columns that one operator occupies its \emph{column group}.
% SOURCE: the XDNA 2 topology is the kernel documentation's, which states 4 rows of compute tiles in 8 columns, 1 memory-tile row per column, and 4,096 KB of L2 (docs.kernel.org/accel/amdxdna/amdnpu.html, read 2026-10-21; the same citation FCPR Section 2.1 uses for the column count). Confirmed on the Ryzen AI Max+ 395 NPU of this paper's machine. NOTE: Rico et al. (IEEE Micro 2024) is the FIRST XDNA generation (5 columns, 10 TOPS) and must not be cited for an XDNA 2 figure.
% SOURCE: BD chaining is mechanism 6 of the analysis's mechanism table; locks on DMA BDs and core locks are mechanisms 7 and 10.
% DECISION: column groups are how today's LLM designs map their flows, not a hardware rule (author, 2026-10-24).

\textbf{Command Processor.}
% VALUE: the host reaches the array only through commands whose instruction streams one in-order CP executes; register write, address patch, issue (returns at once), synchronization (blocks), so the CP's order decides when each group receives work
The host never drives the array directly but submits \emph{commands}, each carrying an \emph{instruction stream} that the NPU's command processor (CP) executes in order~\citep{linux-amdnpu}.
A \emph{register write} configures shim BDs, DMA queues, locks, or a core's runtime parameters, and an \emph{address patch} writes a host buffer's address into a shim BD.
An \emph{issue} pushes a BD into a shim DMA queue and returns at once, whereas a \emph{synchronization} blocks the CP until a named transfer completes.
The CP's instruction order therefore decides when each column receives work, and a synchronization on one column delays every later issue, whichever column it targets.
% SOURCE: instruction encoding, mlir-air a3e26261 programming_examples/llms/shared/fused_prefill/insts.py: TXN v1.0 stream; address patch = opcode 0x81 (argument index at word 8, byte offset at word 10); synchronization = opcode 0x80.
% SOURCE: the original prefill's operators write only shim BDs and queues (row 0, 0x1D000/0x1D200), their own cores' lock registers (0x1F000), and runtime-parameter words in their cores' memory (0x3C00 GEMM, 0x2000 attention); no program loads, core resets, or memory-tile writes (decoded from the shipped streams, lab-prefill-overlap (3)).

\textbf{Host Runtime.}
% VALUE: commands go to a hardware context that holds one configuration and runs them in submission order; argument slots bind buffers for address patches; each command costs a fixed dispatch floor F that queuing partly hides
The host submits commands through XRT and the amdxdna driver to a \emph{hardware context}, which holds one configuration and runs its commands in submission order.
Each command binds host buffers to the \emph{argument slots} that the configuration's kernel declares, and an address patch names its buffer by a slot and a byte offset.
Submitting and completing a command costs a fixed \emph{dispatch floor} $F$ of about 0.1\ms{} on our platform, which queuing further commands before waiting on the first partly hides behind the device's work.
% SOURCE: XRT empty dispatch (4 KB bypass), 93.0-98.5 us at every bracket of lab-prefill-device (3); 92-99 us in lab-prefill-overlap (3).

\subsection{Modular and Fused Designs}
\label{subsec:spectrum}

% VALUE: the design spectrum: a modular design gives each operator its own configuration, which is easy to program but reconfigures the array between operators (cited cost); a fused design keeps several operators resident in one configuration, which avoids reconfiguration, and its operators then queue their commands on one CP; a second cut, into commands (one operator per command or several), decides which waits the CP's order places between operators; where the stacks sit: IRON's runlists are modular, MLIR-AIR's fused prefill and Stream's fused designs are fused, FastFlowLM ships fused binaries; all reach the array through the same commands and streams
% DECISION: the modularity-fusion spectrum is the author's framing (2026-10-24): modular designs trade reconfiguration time for ease of programming, fused designs avoid reconfiguration and inherit an order; neither end is called wrong. No claim about how any stack chose its order ("hand-tuned", "expert"); FastFlowLM is described by what it ships.
A developer cuts an LLM's work at three levels, and the first cut, into configurations, places a design along a spectrum.
At one end, a \emph{modular} design gives each operator its own configuration, which is easy to write and to reuse, but the array is reconfigured between operators.
Prior work characterizes and reduces this cost~\citep{vandelm2026configwall} and models it as the CP's critical path~\citep{fcpr2027}.
At the other end, a \emph{fused} design keeps several operators resident in one configuration, which avoids reconfiguration, and its operators then run from one hardware context, whose commands queue on one CP.
A second cut splits a fused design's work into commands, each with one operator or column group or several, over one chunk of the prompt or all of it.
This cut decides which waits the CP's order places between operators.
A third cut decides whether each role in a loop keeps one buffer or several, and so which waits the loop places between its blocks.
IRON, a close-to-metal Python interface to MLIR-AIE~\citep{hunhoff2025iron} that can also express fused designs, composes an LLM's operators as an operator sequence that reconfigures the whole array for each one.
In contrast, MLIR-AIR and Stream~\citep{symons2025stream} generate fused designs.
FastFlowLM ships both fused flash designs and a modular per-operator engine as binaries, together with the runtime that issues them.
% SOURCE: how each tool builds its fused designs (Related Work names both as generating fused designs): MLIR-AIR maps loop nests onto fused multi-operator designs; Stream generates fused designs from its mapping search.
MLIR-AIR, IRON, and FastFlowLM, the three stacks we read, reach the array through the same commands and instruction streams (Sections~\ref{subsec:closed} and~\ref{subsec:census}), and so do Stream's designs, which compile through MLIR-AIE.
% SOURCE: IRON's OperatorSequence keeps each operator its own aie.device and emits configure/run per runlist entry in runlist order (amd-iron 1fd3dab, iron/common/sequence.py:89-96, 286; iron/common/compilation/sequence.py:243-324; pass-0 census check, decisions log 2026-10-24 late). Stream's fused design: iron/operators/swiglu_prefill_stream (PR #122, stream-dse 2.1.1 at d03bfd10) places gate, up, silu, mul and down on disjoint columns in one design. FastFlowLM's engines reach the runtime through libhrx and ship as compiled libraries and xclbins (FastFlowLM 44d01787, lib/hrx/libgemma4e_flash.so; vault lab-cosched-passes (14)); its flash prefill spends 82-87% of its time in commands whose configuration holds several operators (exposure a3ef131).

\subsection{LLM Inference on the NPU}
\label{subsec:prefill}

% VALUE: prefill and TTFT; the decoder layer's operators; the original fused prefill puts GEMMs and attention on disjoint column groups of one configuration (its default split, the number of columns attention takes), so its operators differ only in their streams; it runs a layer stage by stage over 128-token chunks with host work between commands
\emph{Prefill} processes a prompt to produce the first output token, and its latency is the TTFT.
Each decoder layer applies a QKV projection, attention, an output projection, and a gated feed-forward network of gate, up, and down projections.
MLIR-AIR's open fused prefill places every operator of a decoder layer in one configuration, with the GEMMs on columns 1--6 and attention on columns 0 and 7.
This placement is its default \emph{split}, where the split is the number of columns that attention takes.
The split is a parameter of the design's build, whose admitted values we call the \emph{supported splits}.
Since each attention group serves an equal share of the KV heads, an LLM with 8 KV heads admits attention on 1, 2, or 4 columns.
These are the splits $S_1$, $S_2$, and $S_4$, with $S_2$ the default.
The design's cores loop indefinitely on work taken from runtime parameters, so its operators differ only in their instruction streams, each of which keeps only its own operator's columns.
The host runs each layer stage by stage over chunks of 128 tokens, a size that the design fixes.
% SOURCE: mlir-air 44e8d8f7 programming_examples/llms/shared/fused_prefill/device.py:24-30, M = 128 rows per chunk as a module constant, TM = 32 per core tile, HR = M // TM = 4 core rows of the 6 x 4 herd; no build flag (npu-gap D4, 2026-10-25), so no chunk-size baseline exists without changing the design.
It finishes every chunk's QKV projection before any attention, and every attention before the remaining projections.
Between commands, its CPU computes the normalizations, rotary embedding, and residual additions.
% SOURCE: mlir-air a3e26261 programming_examples/llms/shared/fused_prefill/: device.py (column map cols(cfg); "one PDI serves every op and shape and the ops differ only in their insts"), engine.py (strip_columns), dense.py (_mix_all, stage-major order), hostops.py; README.md: "Some of the LLM implementations in this directory reimplement AMD NPU LLM designs originally developed by the FastFlowLM team".

% VALUE: decode is a separate design that generates one token per step and whose attention reads the KV cache of the whole context
\emph{Decode} generates one token per step with a separate design, namely MLIR-AIR's fused decode, in which every layer's attention reads the KV cache of the whole context.
