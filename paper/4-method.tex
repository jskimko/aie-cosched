\section{Scheduling a Compiled Design}
\label{sec:order}

% VALUE: the opening claim: nothing on XDNA 2 reorders work across engines, so a design's schedule and its waits can be read from the streams its stack emits, and the compiled design, open or closed, is the input to scheduling; arbitration is a resource and durations are left to measurement
% DECISION: the lead insight (the CP's instruction order is the array's schedule, fixed in the streams a toolchain emits) is stated in Sections 1 and 3; this opener states its consequence for the method; "rationed by false dependences" is never stated as the lead.
Because no hardware or runtime scheduler on XDNA~2 reorders work across engines, a design's schedule and every wait in it can be read from the instruction streams its stack emits, so we take a compiled design, open or closed, as the input to scheduling.
Arbitration on shared ports and locks, which serializes some work at run time, enters the analysis as a resource, and only durations, including the host's work between commands, are left to measurement.

\subsection{Reading a Stream}
\label{subsec:reading}
\label{subsec:model}

% VALUE: the analysis represents a dispatch as operations on engines (CP instructions, BD executions, core loop iterations), each with read and write sets over locations that include every exclusively held resource, so a structural hazard is a conflict on a location (examples in appendix-body.tex, cut 2026-10-24); under static control, of the CP, the cores, and the host, one dispatch at given runtime parameters has one static set of operations; a loop with data-dependent control is reported and left out, and every loop of the designs we rewrite is analysed; durations and host work are measured inputs (opening paragraph)
The analysis represents a dispatch as operations on engines, namely one per instruction of a command's stream on the CP, one per execution of a BD on a DMA channel, and one per iteration of a core's counted loop, each with a set of locations that it reads and a set that it writes.
Locations cover every resource that one operation holds exclusively, from memory bytes to BD slots, locks, DMA channels, task-queue slots, switch ports, and configuration registers, so a structural hazard is also a conflict on a location.
Under static control, the CP's stream is straight-line, every core loop's trip count depends on the dispatch's runtime parameters rather than on computed data, and the host's order of commands depends only on the LLM and the lengths of the context and the prompt, so a dispatch has one static set of operations.
A loop with data-dependent control is reported and left out, whereas every loop of the MLIR-AIR designs we rewrite is analysed (Section~\ref{subsec:census}).

Nested-control mechanics: appendix-body.tex, app:nested (cut 2026-10-24).

% VALUE: happens-before is completion before start, not issue order; each direct edge comes from one of 11 mechanisms at the stream, data-movement, or loop granularity and is attributed to exactly one (the attribution choices, edges per gated operation, and uncovered operations in appendix-body.tex, cut 2026-10-24); a segment is a run of synchronizations with the issue they gate; the evaluation checks the reading
From these operations, the analysis builds a \emph{happens-before} graph, in which an edge from $a$ to $b$ means that $b$ cannot start until $a$ has completed.
Issue order alone does not create such an edge, because a queue push is issued in order but its transfer completes later.
Each direct edge comes from exactly one of 11 ordering mechanisms, such as a synchronization, a BD chain, or a lock, at the granularity of the CP's stream, of data movement, or of a core loop, and Section~\ref{subsec:census} checks this reading against what each stack dispatches.
An operator's stream is a sequence of \emph{segments}, where each segment is a run of synchronizations followed by the issue instructions they gate and the first segment has none.

% VALUE: each direct edge is classed by the pairs of operations it alone orders: true if one is read after write, name if one is write after read or write, order otherwise, after Bernstein's conditions and compilers' anti and output dependences; renaming removes a name dependence, reordering an order dependence, a true one stays; loop-carried edges are classed alike (redundant and control counts in appendix-body.tex, cut 2026-10-24); a class assumes every other edge in place, which is why a rewrite is judged as a whole
For each direct edge, the analysis computes the pairs of operations that the edge alone orders, namely those ordered with it and not without it.
The edge is a true dependence if one of these pairs reads a location after the other writes it, a name dependence if none does but one writes after the other reads or writes, and an order dependence otherwise.
Loop-carried edges are classed in the same way on the loop's iterations.
Because each class is computed with every other edge in place, it says what removing that one edge could free, not whether a rewrite that removes several is legal (Section~\ref{subsec:legality}).

\subsection{Legality Conditions}
\label{subsec:legality}

% VALUE: a class does not make a rewrite safe, because a rewrite moves many instructions at once, so each rewrite is judged as a whole against conditions that the streams and their configuration decide without the source: a reorder keeps every instruction once and each operator's and each channel's order, and every pair it inverts must be independent on host bytes, BDs, task queues, ports, and its own group's fences; between whole operators, disjoint device state makes every interleaving legal at once; operators on one group stay in sequence
% DECISION: classes are the report and legality is the checker's; no edge is removed on the strength of its class alone (vault lab-cosched-passes (30), item 3).
A rewrite moves many instructions at once, so a class alone does not make it safe, and we judge each rewrite as a whole against conditions that the streams and their configuration decide without the design's source.
A reorder keeps every instruction exactly once and keeps each operator's segments and each channel's pushes in their own order.
Of each pair of instructions that it inverts, neither may write host bytes that the other reads or writes, neither may cross a lock, runtime-parameter, or configuration write of its own column group, and the two may share no stream-switch port.
No BD may be rewritten while a transfer still holds it, and no push may move above the write of its own BD or overflow its channel's task queue.
Between two whole operators, a stronger condition, that neither can disturb the other's state on the device, makes every interleaving of their segments legal at once.
It holds when each operator's register writes address only its own group's columns and touch only shim BDs and DMA queues, its own cores' locks, and runtime parameters in its own cores' memory, and when the two patch disjoint argument slots or disjoint byte ranges of one slot's buffer and neither writes a buffer that the other reads or writes.
Operators on the same group are composed in sequence instead, so their writes to that group's registers keep the order of separate commands.
% SOURCE: the composer's conditions: each check turns red on a defeated input (swapped groups, an unstripped stream, a synchronization before an issue op, a patch onto another group's argument, a duplicated column, a reordered or dropped segment) (lab-prefill-overlap (3), (4)); txn.compose asserts each stream's segment order, every op kept once, and equal headers (amd-npu a0ee2ed prefill-overlap/txn.py).
% SOURCE: the stream checker on every inverted pair: ranges (RANGE-OVERLAP), BDs (BD-REUSE, PUSH-BEFORE-BD-WRITE, QUEUE-OVERFLOW at the depth of mechanism 3), order invariants (NOT-PERMUTATION, CHANNEL-ORDER, BD-ORDER, SKELETON-MOVED), routes (ROUTE-1-PORT, ROUTE-SHIM-LOCK), and fences of the same group (FENCE-CROSSED for lock, switch, core, and LOADPDI writes; FENCE-CROSSED-UNPROVEN for its runtime-parameter words) (legality.py's pairwise inversion rule, vault lab-cosched-passes (10), (14), (36); the C++ checker inside aie-cosched-schedule, P6 closed, lab-cosched-passes (57), cosched-flag b46744f63c6).

% VALUE: a rename is legal only for a location whose every conflict across uses is WAR or WAW, so carried state stays, and only with a free added instance: no slot reused before its previous reader completes; in a loop, one lock pair whose protocol the added slot extends, within the tile's BDs and local memory; a condition the streams cannot decide refuses the rewrite with that condition; the conditions hold under the execution semantics and are not claimed sufficient for every design, and every rewrite run is also bit-identical
% DECISION: the conditions are stated as what the streams and their configuration can check, never as sufficient for every design (introduction).
A rename is legal only for a location whose conflicts across its uses are all write-after-read or write-after-write, so state carried from one iteration or chunk to the next stays in place.
Its added instance must also be free, with no slot reused before its previous reader has completed, and in a loop the buffer must be guarded by one pair of locks, whose protocol the added slot extends, with the slot fitting in the tile's BDs and local memory.
Where the streams cannot decide a condition, such as a buffer range they do not fix, the rewrite is refused with that condition as its reason.
Because the conditions hold only if the locations cover all the state an operation touches, we do not claim that they suffice for every design, and every rewrite we run also leaves the outputs bit-identical (Section~\ref{subsec:setup}).

\subsection{Closed Binaries}
\label{subsec:closed}

% VALUE: a closed stack ships binaries only, so its streams are recorded at the runtime's boundary and lifted with a byte-identical round trip; closed streams are read and judged (each issue attributed by the decoded routes) but not rewritten, and removals are made on the open reimplementation of the same designs
FastFlowLM ships its designs as binaries, so we record their instruction streams at the runtime's boundary and lift each into MLIR-AIE's runtime-sequence form, from which every stream recorded offline re-emits byte for byte.
We read, judge, and bound these streams, attributing each issue to a column group by the decoded routes, and we observe the host at the same boundary, through the buffers each command binds and the engine's own reads and writes of mapped buffers between commands.
On a closed stack, a rewrite could only swap a command's stream, reorder or merge commands that no closed host step separates, or narrow a wait where every host access to device results is trapped, so the closed host's own steps and its core loops stay as they are.
OPCORD therefore bounds every such rewrite (Section~\ref{subsec:removal}) and measures only those whose bound leaves room, whereas it rewrites the open designs in use (Section~\ref{sec:method}).
